# M4-P4 执行服务任务单

状态：冻结实现边界；本包只证明开发契约，不关闭 M4 或 Linux Gate。

## 1. 目标与前置

在已验收的 B4 OrderPlanner、P3 pre-trade risk、P1 OMS、P2A durable outbox、P2B
`GatewayTransport` 之上，实现一个同步、可恢复、依赖注入的执行编排服务：

1. `plan_and_stage` 通过公开 planner/risk 接口生成计划与逐规则审计；
2. 风险计数器、command、初始 aggregate、outbox、delivery 和 stage receipt 在一个
   SQLite 事务中提交；
3. `dispatch_pending` 使用 claim/lease/attempt fence，且只依赖
   `GatewayTransport` Protocol；
4. SENT callbacks、OMS aggregate CAS 与 delivery SENT 标记在同一事务中提交；
5. NOT_SENT 保留租约等待过期，UNKNOWN 终止自动重试，进程重启后从 canonical wire 恢复。

前置双身份闭包以提交 `38a1b4d` 为准：`OrderPlan.config_identity` 表示 planner
复合身份，`OrderPlan.trading_config_identity` 表示 P3 风控配置身份。服务不得改写任一身份。

## 2. 接口与持久化边界

- 公开模块：`quant.execution.service`。不从 `quant.execution` 顶层 re-export，避免
  `backtest -> execution -> service -> portfolio -> backtest` 循环依赖。
- 构造依赖：`ExecutionStore`、`GatewayTransport`、UTC `ServiceClock`、worker id、
  lease duration、显式 risk counter scope。
- 公开操作：`plan_and_stage(...) -> StagedExecution`；
  `dispatch_pending(limit=...) -> DispatchResult`。
- 所有 durable payload 使用严格、版本化、排序且无空白的 UTF-8 JSON；Decimal、date、
  UTC datetime、enum 显式编码。禁止 pickle、`asdict` 与宽松反序列化。

### 2.1 wire 的真实含义

- `m4-execution-stage-v1` 是 `RiskDecision` receipt：plan_id、规则结果、approved intent
  ids、command ids、projected counters 和 manual-approval 状态。
- `m4-order-command-v1` 是 `OrderCommand`，内含完整 `OrderIntent`。
- 两者均**不包含完整 `OrderPlan`**（不包含 plan decisions/rejections/residual cash）。重放先用
  同一公开输入重新运行 B4 得到 self-proving plan，再把 receipt/command 与 plan_id、intent
  做闭包核验。因此本包不无依据提升 wire 版本。

## 3. 失败语义与不变量

- 同一 plan 重复 stage：返回既有 receipt，不重新评估或重复增加 daily counters。
- 不同 plan 共用 counter scope：事务内读取并 CAS/写入 projected counters；冲突失败关闭。
- partial approval 只为 approved PAPER intents 建 command/outbox；manual approval/SHADOW
  可有 receipt 和 projected counters，但没有 sendable delivery。
- dispatch 前重新验证 delivery/outbox/command/aggregate 身份与 payload 闭包；失败时 adapter
  调用次数必须为零。
- adapter 抛错或返回不合约结果：跨界结果按 UNKNOWN 保守落盘；错误文本不得进入返回值或异常。
- SENT 的 callback 任一不满足 OMS 状态机、event identity、aggregate CAS 或 attempt fence，整个
  callback/event/aggregate/SENT 事务回滚。
- 两个 worker 只能由租约持有者提交当前 attempt；durable 闭包加载完成后、跨 adapter 边界前必须再次
  核验 owner/attempt/lease 和当前时钟，已过期持有者不调用 adapter，旧 attempt 不能写终态。

## 4. 已知窗口与禁止项

adapter 调用是外部副作用，SQLite 是本地事务，二者不存在原子提交：进程可能在 adapter 已接收请求、
但 SENT/UNKNOWN 尚未持久化之间崩溃。租约过期后会以同一 content-addressed command_id、递增 attempt
重试，语义为 at-least-once，不宣称 exactly-once。UNKNOWN 已持久化后禁止自动重试，由后续 P5
reconciliation/人工处置收敛。

最后一次 pre-dispatch fence 只能阻止调用开始前已经过期的持有者。一旦 `submit` 已开始，慢调用可能跨过
lease；此时旧 attempt 既不能写终态，也可能产生 `UNKNOWN_NOT_DURABLE`/`LEASE_EXPIRED_AFTER_DISPATCH`，
随后仍可能重试。这属于同一 dual-write/at-least-once 窗口，必须由 P5 broker reconciliation 收敛，
不把它表述为“所有 UNKNOWN 都必然 durable”。

禁止：后台线程、网络发现、具体 PaperGateway import、LIVE、取消单编排、修改 planner/risk/OMS/
gateway/store 合同、写正式 G1 目录或 journal。

## 5. 验收

测试至少覆盖：重复 stage、partial approval、counter 重启、stage 原子回滚、SENT/NOT_SENT/UNKNOWN、
adapter exception/malformed result、callback 原子回滚、重复 callback、双 worker 租约与 attempt、
manual approval、hostile durable payload、错误脱敏，以及 wire 不包含完整 OrderPlan 的事实。

Windows 原生与 WSL Miniforge base 均执行定向 Ruff、mypy、pytest；Windows 绿测不替代 Linux/ext4 Gate。
