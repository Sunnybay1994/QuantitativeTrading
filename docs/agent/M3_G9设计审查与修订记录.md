## 1. 审查结论

## 2. P0 设计问题与通用规则

### P0-1：工具绿测不能证明候选运行闭合

- 根因：把代码质量与某个 experiment 的运行证据混为一谈。
- 规则：G9 是质量证据和 G0–G8 identity closure 的合取；没有候选 artifact 必须失败。
- 回归：pytest/Ruff/mypy fake 全 0、artifact tree 为空，overall 必须 FAIL。

### P0-2：产物矩阵缺最终审计输入

- 根因：各任务只描述自己的主要表，未从最终验收反推最小 lineage manifest。
- 规则：补齐 experiment identity、label reconciliation、backtest manifest、REPRO 和 acceptance 行；
  每种 JSON 都有 schema version。
- 回归：缺任一 required output 的自洽 receipt 仍被 StageNode 精确比较拒绝。

### P0-3：信任 manifest 自报 identity

- 根因：内容 hash 只能证明“没被改”，不能证明“属于这个节点”。
- 规则：从 snapshot、配置、code/dependency 重算 provider/experiment/work，再比较 DAG node、receipt 和
  manifest；裸 `verify_stage_receipt` 不是 Gate 结论。
- 回归：复制合法 work 到另一 experiment 必须失败。

### P0-4：acceptance threshold 没有独立身份

- 根因：阈值被正确排除在 scientific hash 外，但旧验收报告没有防复用边界。
- 规则：acceptance key 单独包含 acceptance hash、tracking target、quality/evidence receipts。
- 回归：只改阈值不改 experiment，acceptance key 必须变化。

### P0-5：冷启动范围不明确

- 根因：路线图说“两次运行”，CLI 却是单 work。
- 规则：M3 首版要求每个 fold×horizon 都有独立进程 comparison；不得用一折 canary 代表完整配置。
- 回归：四个 work 少一个 comparison 即失败。

### P0-6：指标名称没有来源作用域

- 根因：evaluation 与 backtest 共用扁平 metric 名，聚合结果可能掩盖坏 fold。
- 规则：required metric 使用 `evaluation.*`/`backtest.1p0x.*` 限定名；coverage 逐 work 检查；表现正负
  不属于工程 Gate。
- 回归：pooled coverage 达标但一折不达标仍失败；负 IC/收益不单独失败。

### P0-7：现有 receipt 契约不足以作为最终证据

- 根因：E3 首版没有版本、严格字段/duplicate-key 检查和 expected StageNode 语义。
- 规则：实现反馈纳入 G8/G9 前置返工；所有 symlink（即使仍指向 root 内）拒绝，receipt 版本未知即失败。
- 回归：自报 hash 全对但 scope/key/output 集合错误、重复 JSON key或 root 内 symlink 均失败。

### P0-8：质量证据存在执行期漂移窗口

- 根因：旧设计只在命令前接收 caller 自报 code/dependency，质量命令运行期间代码或环境改变仍可能签发旧身份。
- 规则：G9A 在固定命令前后重算 code、dependency 与版本化配置 digest；任一漂移均不发布 quality receipt。
- 回归：pytest 运行中修改 source、配置或 dependency probe，四项 exit 0 仍必须失败。

### P0-9：plan 内缺稳定证据定位，issue 不可独立复验

- 根因：裸 `(stage,path)` 和 issue code 既不能表达 expected scope/key，也无法定位哪个 work/horizon 失败。
- 规则：用 `EvidenceLocatorV1` 表达 expected node/stage/scope/key/receipt；issue 使用稳定逻辑 subject 和 evidence
  digest，禁止异常原文和绝对路径。
- 回归：复制自洽 receipt 到另一 scope、同 code 出现在两个 work，报告必须分别定位且稳定排序。

### P0-10：远端 tracking 与本地 marker 混为一个事实

- 根因：本地 marker 只能证明曾经登记，不能证明当前 tracking target 仍有唯一匹配 FINISHED run。
- 规则：G9E 显式查询当前 target，规范化最小 remote observation 并把其 hash 纳入 acceptance identity；
  网络错误、0/2+ 或状态/hash 漂移均 FAIL，不得 SKIP 或创建 run。
- 回归：保留合法 marker 后删除/复制/改状态 remote run，G8 必须失败且 acceptance key 不复用旧 observation。

### P0-11：审计函数边检查边发布

- 根因：没有候选决策与 StageRunner 发布边界，失败路径可能残留可被误认的 report/complete。
- 规则：G9F 先构造只读 `AcceptanceDecisionV1`；只有十 Gate PASS 才可写空 temp，最终目录和 receipt 仍由
  G8B no-clobber runner 发布。FAIL writer 零文件。
- 回归：每个 Gate/remote/publish 故障点均不得留下 final 目录或成功 receipt；PASS 崩溃恢复沿用 G8B。

## 3. 不应过度建设

不引入 Airflow、分布式锁、PKI、Merkle tree、事件溯源库或通用规则引擎；个人 M3 使用规范 JSON、
SHA-256、root alias、原子 receipt、唯一 Stage registry 和模块内 validator 即足够。验收不联网重抓
Tushare，不解析 Markdown，不要求模型/Parquet 字节完全一致，也不把正收益当上线门槛。
