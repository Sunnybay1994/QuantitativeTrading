## 3. P1-A：readiness 严格 Benchmark Schema

### 现象—根因—规则（任务单 §4）

原先只做 required 列子集检查，股票专属列作为 Schema 超集可通过结构门禁。

### 实现要点

- `_benchmark_column_gate`：在依赖 Polars 操作前检查 **exact** 列集合  
  - 缺必需列 → `BENCHMARK_MISSING_FIELDS`  
  - 额外列 → `BENCHMARK_INVALID`  
- `_check_benchmark_schema`：调用生产 `BenchmarkBar1dSchema.validate`；异常统一脱敏为固定 `BENCHMARK_INVALID` 文案，不泄露 Schema 原文/路径/token  
- Schema 失败时不再把该表交给 dense coverage 的数值 OHLC 过滤，避免二次抛底层异常；仍继续收集其他独立 readiness issue  
- 保留 `BENCHMARK_DUPLICATE_KEYS` / symbol / source / 日期覆盖语义；移除手写 `_check_benchmark_invalid` 调用

## 4. P1-B：mapper verified identity 闭包

### 现象—根因—规则（任务单 §5）

`frozen=True` 不能防止 `object.__setattr__` 后的 identity drift；构造时成立 ≠ 消费时仍成立。

### 实现要点

- 四个公开 mapper 在读行前统一调用 `_consume_verified`：用当前 `spec/receipt/receipt_sha256/frame` **重建** exact `VerifiedRawResponse`，只消费重建成功对象  
- 不复制 receipt/content hash 算法，不改 B2A 构造语义  
- 重验失败 → `M3G1MappingError("G1_MAPPER_RESPONSE_INVALID")` + `from None`；四观察面仅暴露稳定 code

### 新增测试（§5.3–5.4）

| `test_p1b_receipt_sha256_drift_rejected` | 单独漂移 `receipt_sha256` |
