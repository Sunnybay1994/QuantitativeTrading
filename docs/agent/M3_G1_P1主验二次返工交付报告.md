## 2. P1-C 根因与修复

### 根因

一次返工虽调用 `BenchmarkBar1dSchema.validate`，但顺序仍是 column gate → `source`/`benchmark` Polars 比较与 group → Schema。exact 八列下，`source`/`benchmark` 为 Schema 不兼容 dtype（如 `List[String]`、`Int32`）时，在 Schema 之前即抛 `ComputeError` / `InvalidOperationError`，调用方拿不到结构化 `ReadinessIssue`。

### 修复

数据流改为任务单规定顺序：

```text
column gate
  -> required projection (_REQUIRED_BENCHMARK_FIELDS)
  -> BenchmarkBar1dSchema.validate(projection)
  -> 只消费 validate 返回的 frame
  -> source selection / duplicate / identity / dense coverage
```

要点：

- `_validate_benchmark_bars` 捕获全部异常，返回脱敏 `BENCHMARK_INVALID`，不向外抛 Polars/Pandera。
- extra 列仍由 column gate 报 `BENCHMARK_INVALID`；投影 Schema 通过后继续收集 `BENCHMARK_DATE_COVERAGE` 等独立 issue。
- 缺必需列仍只走 `BENCHMARK_MISSING_FIELDS`，不访问缺列。
- 未改 `BenchmarkBar1dSchema`，未使用 `strict=False` / 手工 cast / 逐表达式 try 补丁。

### 语义对齐说明

重复 `(benchmark, trade_date, source)` 在 Schema-first 下由生产 Schema 唯一性检查先于 duplicate helper 拦截，稳定报 `BENCHMARK_INVALID`（不再先出现 `BENCHMARK_DUPLICATE_KEYS`）。fail-closed 不变；对应单测已更新。
