## 3. 发现与返工条件

### P1-1：包装后的 I/O/TOML 异常仍通过 cause 链泄露原异常

- 位置：`src/quant/research/m3/config.py:412-426`。
- 现象：`str(M3ConfigError)` 与 `repr(M3ConfigError)` 已脱敏，但 `traceback.format_exception(error)` 仍包含
  原 `FileNotFoundError` 和物理文件名。生产日志常以 `exc_info=True` 记录完整异常链，因此当前实现没有满足
  “I/O/parser 原异常不得直接透传、异常不含物理路径”的契约。
- 根因：两个包装分支都使用 `raise M3ConfigError(...) from exc`；实现测试只检查了外层 `str/repr`，没有检查
  traceback/context/cause。
- 应遵循规则：脱敏必须覆盖异常对象的所有常见呈现面，包括 `str`、`repr`、formatted traceback、
  `__cause__/__context__` 的可见链和结构化日志，不只是外层 message。
- 最小复现：对名为 `C0_PHYSICAL_PATH_SENTINEL.toml` 的不存在文件调用 `load_m3_config`，捕获异常并运行
  `traceback.format_exception`；当前结果包含 sentinel。
- 新增测试：至少分别覆盖 I/O 与 TOML parse 包装，断言 formatted traceback 和模拟 `exc_info` 输出不含
  物理路径、输入片段或 sentinel；不能只断言 `str/repr`。
- 通过条件：抑制或安全替换原异常链（例如显式 `from None`），同时保留稳定
  `CONFIG_IO_ERROR/TOML_PARSE_ERROR`，上述测试及全量回归通过。

### P1-2：敏感键在 percent-decoding 前分类，编码变体绕过 `SECRET_VALUE`

- 位置：`src/quant/research/m3/config.py:727-765`。
- 现象：direct document 中的 quoted key `%74oken` 只产生 `UNKNOWN_KEY`，没有同时产生
  `SECRET_VALUE`。这违反 4.0.4“安全检查先于 unknown-key 丢弃，并对 percent-decoding 后文本再检查”的机械
  规则。
- 根因：值扫描会最多三次 `unquote`，但 `_is_sensitive_key` 只对原 key 做 lowercase 和 hyphen 替换，key 与
  value 使用了两套不同的规范化管线。
- 应遵循规则：安全分类必须按“受控重复 percent-decode → case/hyphen 规范化 → 敏感集合匹配”的唯一顺序
  处理键和值；unknown 不能成为跳过安全分类的理由。
- 最小复现：完整有效 document 增加 `extra = {"%74oken": "plain"}` 后调用公开 canonicalizer；当前 issue
  集只有 `UNKNOWN_KEY extra.%74oken`。
- 新增测试：覆盖单层和双层编码的 `token/api-key/private-key` 变体，断言同时产生 sanitized
  `SECRET_VALUE` 与 `UNKNOWN_KEY`，且 message/traceback 不回显值。
- 通过条件：编码敏感键被 fail-closed 分类，原始 dotted path 仍可用于定位但不包含值；既有合法 dump SHA
  继续不被误杀。

### P1-3：公开 tracking target 与 loader 的 experiment name 安全语义分叉

- 位置：`src/quant/research/m3/config.py:442-459`。
- 现象：完整 loader 会由 `_scan_secrets` 对 `tracking.experiment_name` 运行绝对路径检查，但
  `canonical_tracking_target_key` 只调用 `_scan_secret_value`。因此同一个 `/tmp/m3-experiment` 在 loader 中
  被 `UNSAFE_PATH` 拒绝，直接调用 target key API 却成功产生 identity。
- 根因：公开 helper 手写了一份不完整的 name 验证流程，没有复用 loader 的同一校验原语。
- 应遵循规则：能够被 loader 和 direct caller 同时调用的安全边界必须共享同一 primitive；同一语义值不能
  因入口不同而出现 accept/reject 分叉。
- 最小复现：调用
  `canonical_tracking_target_key(tracking_uri="sqlite:///artifacts/m3.db", experiment_name="/tmp/m3-experiment")`；
  当前不抛异常。
- 新增测试：对 POSIX absolute、Windows drive、UNC、反斜杠和 percent-encoded absolute name 同时比较
  loader/direct helper 的 issue code 与 dotted path。
- 通过条件：direct helper 与 loader 对 tracking URI/name 的可接受域一致，合法 URI alias 仍归一为相同 key。

### P2-1：direct mapping 的非字符串键在校验前被有损转换

- 位置：`src/quant/research/m3/config.py:496-505,953-956`。
- 现象：加入 `{1: "x"}` 后公开 canonicalizer 报 `UNKNOWN_KEY extra.1`，没有报映射键的 `TYPE_ERROR`；
  `_iter_assignment_leaves` 中的 non-string key 分支实际上无法看到该输入。
- 根因：`_thaw` 在验证前无条件执行 `str(key)`，把错误类型转换成了看似正常的字符串键。
- 应遵循规则：严格 validator 不得在类型检查前做有损 coercion；normalize 只能发生在输入已证明属于合法
  类型之后。
- 最小复现：完整 document 增加 `extra = {1: "x"}` 后调用公开 canonicalizer，观察 issue code。
- 新增测试：根层、普通嵌套层和费用 period mapping 的非字符串键均应产生稳定 `TYPE_ERROR`，且不能与真实
  字符串键 `"1"` 合并或碰撞。
- 通过条件：先递归验证 key type，再复制/冻结，不再静默字符串化非法 key；合法 TOML 行为与 hash 不变。

## 6. 反馈闭环与复验要求

实现 Agent 已正确识别“冻结 literal 不能用非法变体做 hash 差分”和 `api-token` hyphen 变体，说明按真实
合法域测试的方向是对的。本轮新增问题暴露了三条需要写回后续任务/测试准则的通用教训：

1. “错误文本脱敏”必须把 traceback 与 exception chaining 纳入契约，不能只测 `str/repr`；
2. 安全匹配的 decode/normalize/classify 顺序必须是共享 primitive，键和值不能分别维护；
3. direct public helper 必须与 loader 使用同一可接受域；任何入口差异都要用成对回归测试锁住；
4. strict validation 在 coercion 之前，尤其不能用 `str(key)` 掩盖非法输入。

返工 Agent 应只修复上述最小范围并新增对应回归，不借机重构 selector/hash 主体。返工后独立复验至少重跑
本报告 12+1 个反例、针对性 87 tests、全量 pytest、Ruff、mypy 和 C0D 源码搜索；在这些条件全部满足前，
C0 不得标记通过。
