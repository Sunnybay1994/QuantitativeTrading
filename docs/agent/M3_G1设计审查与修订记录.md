## 3. 对实现 Agent 的指导

这些问题的共同根因不是少写了几个 `if`，而是把不同层次的事实合并了：raw 与 clean、历史域与资格域、
观察日与可知时点、理论标签与可执行成交、单文件写入与数据集发布。实现时应先保持这些边界，再写最小代码：

1. raw 层只忠实留证，重复、空值和异常不能提前“修好”。
2. 映射层可以标准化，但每次丢行、合并或推导都必须有规则、血缘和计数。
3. 质量门禁默认 fail-closed；缺证据不是正常值。
4. release 身份覆盖所有会改变研究结论的逻辑输入，与物理路径和抓取时间无关。
5. 实现报告若发现真实 SDK 与任务书冲突，先报告最小样例，由主 Agent 修改 SSOT 后再继续；不得迁就错误契约。
6. 配置文件只在 C0 入口解析一次；下游需要“配置内容与身份一致”时，传只读 section 与窄化 hash 并在
   副作用前复算，不传物理配置路径。
7. 状态机术语必须能映射到唯一物理布局；若“多候选”等抽象分支在布局中不可表达，应先冻结文件命名、
   目录白名单和并发语义，不能让实现者自行发明第二套 journal 格式。
8. `Verified`、`Plan`、`Batch` 等名称本身就是信任承诺；不能依赖“正常调用者不会直接构造”，公开对象要么
   自证闭包，要么收窄构造入口并在每个消费边界重新验真。
9. 安全结论不能由单个 happy-path 反例外推。异常与文件系统边界应按调用点枚举直接异常、chained cause、
   cleanup failure、root/祖先 symlink 和目录项类型，并用未公开反例证明全路径闭包。
10. “副作用前检查 root”不等于检查了本次将使用的路径。请求 ID 已确定时，应在联网前把检查延伸到该
    request 的既存 descendant 和全部条目；过滤非法条目后得到空集合，会把异常证据误判成“尚未抓取”。
11. “零网络”不等于“零副作用”。失败关闭测试必须同时比较 connector/clock/sleep 调用和 raw/journal
    普通文件集合；intent 是证据文件，不能在确认既存 raw/candidate 状态合法之前用于“顺手修复”闭包。
12. 事后发现状态变化不等于阻止了错误提交。任何 expected mode/identity 的比较都必须位于首个持久化动作
    之前；外层 post-check 只能做二次断言，不能让内层先写 candidate 再报告 closure changed。
13. `COMPLETE` 是状态，不是身份。提交引用 raw 的证据前必须比较同一 snapshot 的完整物理/逻辑 digest；
    只复查目录仍含两个文件，无法区分 COMPLETE-A 与内容不同的 COMPLETE-B。
14. 两次读取各自校验成功，不代表它们属于同一时刻的证据。需要同时使用物理 snapshot 与逻辑 frame 时，
    必须由一次受控 bytes 读取/验真返回 bundle，不能先返回 snapshot 再按路径二读 frame。
15. required-column subset 只用于避免缺列后的二次异常，不能证明 strict Schema。验收 Schema 时必须覆盖
    missing、extra、dtype 和跨字段约束，并让消费边界调用代码 SSOT，而不是复制局部门禁。
16. 构造时闭合不等于消费时仍闭合。对 `Verified/Plan/Receipt/Snapshot`，既要测非法构造，也要测构造后
    identity drift；消费方必须重建或调用生产 verifier 后再读取载荷。
17. Schema 必须位于它所保护的第一条字段表达式之前；“最终调用了 validate”不能证明消费边界安全。
    Schema 开启 coercion 时，下游必须消费 validator 的返回值，不能验证后继续使用原 dtype 的 frame。

## 4. 后续验收顺序

每个任务包先由实现 Agent 自测，再由另一名 Agent 用未公开反例初验，最后由主 Agent复核跨包不变量、
真实小样本和全量 pytest/Ruff/mypy。只有 B1–B4、L0 证据齐全且真实 G1 release 通过
`verify_g1_release` 与跨源对账后，才能把 G1 标为通过。

本轮把 mapper 拆为 B2B 核心机械映射与 B2C 规则映射。原因是 daily/factor/benchmark/suspension 只需
验证 response scope、单位、Schema 和有限规范化，而 stk_limit/dividend 的正确性依赖合法无限制日规则、
公告版本选择和 factor-ratio 对账。将后二者塞进 B2B 会诱导实现者先写无法证明的 null 默认或
`keep="last"` 占位，破坏 fail-closed。该拆分不减少最终 G1 功能，只调整依赖顺序。

G1-P1 关闭后，原计划直接执行 G1-P2/B3；实施前真实只读探针和跨合同复核又发现五项设计缺口：示例
`2016-01-01` 是休市日；`next_open` 版本名与“下一 session 收盘后可知”矛盾；result-only verifier 无法阻止
整体 session 平移后重算 digest；calendar 未证明尾部严格下一 session；clean digest 接受 datetime 会引入未定义
时区语义。前两项拆为 P2-0 配置前置，后三项写回 P2 严格 verifier、calendar proof tail 和 v1 scalar 闭包。
P2-0 主验前不启动 P2，避免在错误配置身份上生成后续证据。

复核任务书时又发现 data-layer `build_observed_membership` 没有 `LoadedM3Config` 输入，不能被要求硬编码或自行
比较示例 `data.start_date/end_date`。现行规则改为：P2 只证明 caller 日期是 verified SH session；真实 stage/G2
边界把 G1 manifest 日期与同一 loaded config 精确比较。这样保留纯函数/分层边界，也不会为了测试制造十年日历。

P3 实现前扩大真实探针又发现旧 reconciliation 合同会错误阻断主链：12 只匿名 CSI300 样本的 127 个 dividend
factor transitions 中，现金/送转通式有 6 个超过 `0.001`，最大约 `0.00350`；125 个有 daily 行的事件用
`previous actual close / pre_close(除权价)` 全部闭合，最大约 `0.000356`；另 2 个 FULL_DAY event 没有 daily
行但 declared 公式闭合。根因不是应放宽容差，而是接口丢掉了官方除权参考价，同时没给停牌缺行情保留严格
第二证明路径；沪深规则还明确通式含配股并允许批准调整。P3 现改为重建 daily responses：有行时 raw pre-close
做主门禁，无行时只有 declared 自身闭合才能继续，并以三个 MATCHED status 显式区分，版本升级为
`tushare_factor_daily_preclose_v1`。P4 必须从 plan 的 daily verified responses 重建，不能信 caller 自算参考价。

同一探针还发现 `stk_limit` 的完整历史里有 666 个 `pre_close=0` 键且全部伴随 suspension，另有 55 个 null；
旧 mapper 会因一个 sentinel 拒绝整只证券十年响应。现行规则不是放宽成无限制日：mapper 只对 positive valid
row 发布 `has_price_limit=true`，null/zero 留在 raw；coverage 接收 suspensions，FULL_DAY 从 required key
排除，PARTIAL/无 suspension 仍必须有 valid limit。method version 因语义变化冻结为
`tushare_stk_limit_suspension_aware_v1`。G7 同步允许 FULL_DAY 缺 limit，并用 verified reconciliation 的实际
factor ratio 处理无 bar 公司行动日 mark，禁止重算现金公式。

P2-0 关闭后，下一执行包才是 G1-P2/B3，而不把 B2C/B4 一起下放。B3 同时涉及 batch 完整性、
PIT 可知时点、日历 session、instrument 生命周期和 clean 内容身份；这些不变量内部强耦合，但与公司行动
选版/涨跌停和 release 文件系统状态机相互独立。该颗粒度允许高能力外部模型完成一条完整主链，又避免一次
任务跨越三个信任边界后只能靠全量绿测掩盖局部缺口。

P3 继续把“执行事实”从 B4 文件发布状态机中抽离：价格限制的难点不是五列转换，而是持仓延续覆盖；公司行动
的难点不是保留最新行，而是全历史范围、nullable version total order、事件 identity 和 factor 解释。将这些
纯函数及 evidence Schema 先冻结，B4 才能专注 plan/receipt 闭包、质量汇总、跨源对账和原子发布。
