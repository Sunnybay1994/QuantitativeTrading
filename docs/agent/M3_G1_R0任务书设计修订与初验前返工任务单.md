# M3 G1-R0 任务书设计修订与初验前返工任务单

日期：2026-07-15  
状态：**待外部返工**  
执行模型：非 fast `cursor-grok-4.5-high`

## 1. 现象

- 首轮实现进程按当时任务书把 SH clean 日历补到 `2015-01-01..2026-12-31`；
- SZ clean 日历仍为 `2023-01-01..2026-12-31`；
- 进程退出时没有生成约定交付报告，stdout 为空，因此七端点/BaoStock/kernel probe 是否完成没有可验收
  证据；
- 尚未进入独立初验。

## 2. 根因与责任

主 Agent 首版 R0 任务书错误地只要求补 SH。后续内部只读设计 lint 对照
`audit_g1_candidate` 发现：正式 G1 audit 要求 SH/SZ 日期域及 `is_open` 逐日完全一致；只补 SH 会让未来
真实 candidate 必然产生 `CALENDAR_MISMATCH`。这是任务书设计缺口，不归因于实现 Agent。

首轮外部进程没有返回可恢复 session ID 或交付报告，主 Agent 无法按原 session 续接。本返工允许新建一个
Grok High 实现会话，但报告必须保留这一职责偏差及原因；独立初验仍必须使用另一全新会话。

## 3. 应遵循规则

以已修订的
[`M3_G1_R0权威日历补全与真实源烟测外部闭环任务单.md`](M3_G1_R0权威日历补全与真实源烟测外部闭环任务单.md)
全文为唯一执行合同。重点变化：

1. 日历目标是 SH **和** SZ；
2. 写入前分别核对已有交集，并核对新 Tushare SH/SZ 全域一致性；
3. 更新后两份均须覆盖 2015–2026 且逐日 `is_open` 相同；
4. 已完成的 SH 合法结果不回滚、不覆盖 raw；按同一 pipeline 幂等复核/复用；
5. 七端点、BaoStock、kernel probe、测试和凭据扫描必须形成正式交付报告。

## 4. 最小复现

```text
SH clean: 2015-01-01..2026-12-31, 4383 natural dates
SZ clean: 2023-01-01..2026-12-31, 1461 natural dates
```

因此在 2015–2022 日期域，G1 两市场 calendar 表不可能一一对应；即使 SH session 规划可运行，P4A audit 仍
会失败。

## 5. 返工范围

- 先只读抓取/映射完整 SZ 日历，并重新抓取/映射 SH 用于交叉比较；任何交集或沪深差异先停止写入；
- 三类比较均为零后，用现有 pipeline 幂等更新 SZ；SH 不需要为了产生新时间戳重复写 raw，但必须复核当前
  clean 与本轮内存 SH 结果一致；
- 完成原任务书 R0.3/R0.4 的真实烟测；若首轮已经发起过远端请求也不得依赖无报告状态，按每端点最多两次
  的总安全原则谨慎执行一次可证明请求；
- 生成唯一 `docs/M3_G1_R0权威日历补全与真实源烟测交付报告.md`；
- 不修改源码、测试、配置、路线图或 R1A/R1B/R1C。

## 6. 新增验证与通过条件

1. SH/SZ natural dates 都为 4383、范围相同、无缺日、`is_open` mismatch=0；
2. `resolve_history_window(60,10)` 成功并报告固定边界；
3. 七个 Tushare endpoint 与 BaoStock 均有稳定摘要，任何永久失败如实阻塞；
4. kernel probe 如实；WSL1 unsupported 不冒充 publish 通过；
5. 定向 pytest、Ruff、mypy 按主任务书执行；
6. 交付报告和白名单文件凭据/绝对路径扫描 0 命中；
7. 报告状态只能“待独立初验”，不得宣称 R0/G1/Gate 通过。
