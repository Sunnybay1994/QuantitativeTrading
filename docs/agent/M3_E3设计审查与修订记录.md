## 1. 审查结论

旧 E3 不是可在其上继续堆叠 G8/G9 的可信底座。当前实现仍使用 `sha256:<hex>`，receipt parser 会以
`str()/int()` 接受错误类型，未拒绝 duplicate key、未知字段、非规范 JSON、内部 symlink 和 input/output
交叉重复；同时缺少 ACCEPTANCE scope、receipt 版本和 snapshot/provider-validation/reconciliation 身份键。
`DatasetSnapshot.provider_path` 还把内容寻址 snapshot 与派生 provider 的生命周期错误耦合。

因此本轮先冻结 R1–R4，不把 DAG、CLI 或业务算法交给实现 Agent 猜测。旧测试冻结的是旧行为，必须随
权威合同迁移，不能以“保持兼容”为由保留双格式。

## 2. 二次审查新增问题

### 2.1 覆盖式 replace 破坏 immutable receipt

- 现象：旧任务单保留 `temp+fsync+replace`；两个发布者都在 exists 检查后进入时，后者可覆盖前者。
- 根因：把“单进程原子替换”误当成“并发 no-clobber 创建”。
- 应遵循规则：immutable evidence 只能首次创建；并发已存在只允许完整验真后的同内容复用。
- 最小复现：在最终 publish 前让另一进程写入不同规范 receipt，再继续原 `os.replace`。
- 新增测试：monkeypatch/no-clobber race 的相同与冲突两种分支。
- 通过条件：生产路径无覆盖式 replace；冲突字节保持原文件不变。

### 2.2 相同 receipt 字节不代表可复用

- 现象：旧实现只比较 existing receipt bytes，artifact 已被修改仍返回成功对象。
- 根因：把 receipt identity 与其声明事实的有效性混为一谈。
- 应遵循规则：COMPLETE/receipt 是状态证据，不是无需复验的身份缓存。
- 最小复现：发布 receipt，修改 artifact，再以同参数重发。
- 新增测试：相同 receipt 字节、artifact hash 不符必须失败。
- 通过条件：复用前调用严格 verifier 对 receipt 和全部 artifact 重验。

### 2.3 alias 可绕过交叉重复

- 现象：两个 alias 可指向同一物理 root，同一文件遂可分别列作 input/output。
- 根因：只对逻辑 `(alias,path)` 去重，没有验证 root 注册表自身的一致性。
- 应遵循规则：安全边界应验证 root→ancestor→leaf 全链，且逻辑别名不能为同一物理根制造第二身份。
- 最小复现：`{"A": root, "B": root}`，同一 `x.bin` 分别用 A/B 声明。
- 新增测试：duplicate physical root fail-closed。
- 通过条件：任何 digest 前先严格验证完整 root mapping。

### 2.4 非规范 JSON 使 receipt digest 多义

- 现象：语义相同的缩进、字段乱序、尾随换行可被 parser 接受，却产生不同 receipt SHA。
- 根因：只规范写，不规范读。
- 应遵循规则：作为身份闭包输入的 JSON 必须有唯一字节表示。
- 最小复现：对合法 receipt 增加尾随换行或改字段顺序。
- 新增测试：非规范但语义相等文件拒绝。
- 通过条件：原始 bytes 必须精确等于严格对象的规范重编码。

### 2.5 E3 输入合同与 snapshot 生产入口断裂

- 现象：E3 要求裸 64 hex，`snapshot.py::_stable_hash` 仍产生 `sha256:<hex>`。
- 根因：只迁移消费者，遗漏当前生产者。
- 应遵循规则：公共契约迁移必须检查直接 producer/consumer，不得留下项目自身无法消费的值。
- 最小复现：将 `snapshot_id_from_manifest()` 的结果传给严格 `compute_provider_key()`。
- 新增测试：snapshot ID 为裸 64 hex，且 provider key 可直接消费。
- 通过条件：只迁移 snapshot hash 输出编码，不改变 manifest hash 输入。

### 2.6 只在 parser 校验会留下非法内存对象

- 现象：调用方可以直接构造大写 hash、乱序 digest 或交叉重复的 frozen dataclass。
- 根因：验证挂在 IO 路径而非值对象边界。
- 应遵循规则：公开值对象必须自证；Batch/Plan/Verified/Receipt 的嵌套内容均不能信任调用者。
- 最小复现：直接 `ArtifactDigest(..., sha256="BAD")` 或构造乱序 `StageReceipt`。
- 新增测试：直接构造非法对象立即失败。
- 通过条件：publish、verify 与直接构造复用同一校验器，无双套规则。

### 2.7 嵌套 root 与 receipt 路径未闭合

- 现象：只拒绝两个 alias 指向同一 root，仍可用父 root 的 `child/x` 和子 root 的 `x` 指向同一文件；任意
  root 外的 receipt 路径也使 self-reference 与错误脱敏缺少受控基准。
- 根因：只验证逻辑路径，没有把 root registry、物理文件身份和 receipt 发布位置放进同一边界。
- 应遵循规则：嵌套 root 可合法表达层级，但同一物理文件在整个 receipt 内只能出现一次；receipt 必须位于
  显式 root 内且父目录预先存在。
- 最小复现：`A=/root,B=/root/child`，分别声明 `A:child/x`、`B:x`；或把 receipt 写到 roots 外。
- 新增测试：嵌套 alias、hard-link、root 外 receipt、缺失 receipt parent、receipt/output hard-link。
- 通过条件：按物理文件身份拒绝重复/自引用，同时不误拒绝两个嵌套 root 中不同文件。

### 2.8 Provider-validation 传播与不可变路径冲突

- 现象：旧文字称 provider 抽样“仅”改变 provider-validation，但 reconciliation key 绑定 validation receipt；
  required-input 表又让不绑定该 key 的 experiment/features receipt 把它列作内容输入。
- 根因：混淆“执行前置门禁”与“内容身份输入”，且传播矩阵没有沿 receipt 依赖继续推导。
- 应遵循规则：validation 变化必须传播到 reconciliation/acceptance；experiment/features 只要求 PASS 前置，
  不把 validation receipt 纳入不变路径的内容 receipt。
- 最小复现：只改 `validation.provider` 后，experiment key 相同但旧 required inputs 不同，重发必冲突。
- 新增测试：experiment/work 相等，provider-validation/reconciliation 不等；required-input 表静态审查。
- 通过条件：4.0、4.9、任务书与后续 G8 计划使用同一传播关系。

### 2.9 公开身份函数与值对象仍可能部分宽松

- 现象：“四组接口/这些函数”可能遗漏现有 experiment/work；有默认首字段的普通 dataclass 也无法导入。
- 根因：任务书没有逐个冻结全部 public 边界和可执行构造形式。
- 应遵循规则：迁移公共合同必须覆盖全部直接入口；值对象签名本身必须可运行且拒绝错误容器类型。
- 最小复现：旧 `compute_experiment_key(snapshot_id="snap-a",...)` 成功；默认字段置于非默认字段前报 TypeError。
- 新增测试：六函数严格输入；StageReceipt kw-only/default version；list 冒充 tuple 失败。
- 通过条件：六函数统一 validator，StageReceipt 精确签名与 SSOT 相同。

### 2.10 Receipt 自引用不能只检查 outputs

- 现象：旧 helper 名称和行为只检查 outputs，existing receipt 仍可作为 input 或经 hard-link 别名进入。
- 根因：把“完成标记不是业务 artifact”误缩窄为“不能声明为输出”。
- 应遵循规则：receipt 在 inputs/outputs 任一侧均非法；完整 root registry 也必须先于 digest 全量验真。
- 最小复现：先创建 receipt，再以该文件或其 hard-link 作为 input 调用 publish/verify。
- 新增测试：input 自引用、input hard-link、未使用 root 非法三类反例。
- 通过条件：统一上下文校验器覆盖 inputs∪outputs 和全部 roots。

### 2.11 临时 receipt I/O 也属于对外错误边界

- 现象：首轮主验发现 `tempfile.mkstemp`、临时文件写入/`fsync`、`unlink` 与目录 fd `close` 的异常没有全部
  转换为稳定脱敏错误；成功 link 后 `unlink` 失败还会被静默吞掉并返回成功，遗留未声明 `.tmp` 文件。
- 根因：实现与初验只搜索显式 `raise ... from exc`，遗漏标准库调用直接抛出的原始 `OSError`；同时把
  “cleanup 不掩盖主异常”错误理解为“发布成功后可忽略 cleanup 失败”。
- 应遵循规则：公开 publish 的所有本地 I/O 失败都必须用稳定消息 fail-closed；cleanup 有主异常时保留主
  异常，无主异常时自身必须失败，不能静默返回成功。已发布 receipt 保留并在重试时验真复用。
- 最小复现：令 `mkstemp` 抛含绝对路径的 `PermissionError`；或令临时 `Path.unlink` 在 link 成功后失败。
- 新增测试：temp create/write/fsync/cleanup、主异常+cleanup 双失败、目录 fsync+close 双失败，均核对
  `str/__cause__/traceback` 脱敏、receipt/temp 的真实落盘状态。
- 通过条件：无原始 `OSError` 逃出；cleanup 失败不掩盖主异常也不伪装成功；失败后无错误覆盖 fallback。

## 3. 明确不承诺的边界

- receipt 的原子创建不提供多个 artifact 的跨文件事务。
- artifact 由外部进程在最后一次验真后修改仍存在 TOCTOU；后续复用/验真必须 fail-closed，不伪称锁住外部写者。
- 父目录 `fsync` 在部分挂载文件系统可能不可用；必须尝试并披露，不得回退为覆盖式发布。
- E3 不实现 StageRunner 的期望集合比较、DAG、CLI、MLflow 或真实研究 Gate；这些仍由 G8/G9 完成。

## 4. 对实现与验收 Agent 的反馈要求

代替逐项证据。任何返工继续按“现象—根因—规则—最小复现—新增测试—通过条件”记录，并把可复用教训
写回本记录或 4.9 SSOT。
