## 1. 目标、前置与唯一职责

本包只关闭 formal G7F 与现有 G8 `StageRunner.run_static` 之间的发布缝隙：把 freshly verified target、backtest
plan、experiment、G1 release 及其 exact receipt/market-facts 闭包解析为一个 **identity-resolved WORK/backtest
wave**，在 runner 分配的空 temp 中调用 actual G7F builder，以 pre-receipt fresh closure 验真后原子发布目录，
再由 StageRunner 发布 exact 21-input/29-output receipt，最后调用 actual G7F verifier 得到
`VerifiedBacktestArtifact`。

硬前置：

1. G7F R1 实现、全新独立初验与主 Agent 最终验收全部 PASS；
2. G7E、G7F-P0、G7A/G7B、G7D-F0/F1/F2、G7C 的既有主验继续有效；
3. G8A plan-only 与 G8B static runner 的既有阶段主验继续有效。

任一前置未 PASS，本任务只能保持设计冻结。当前 G7F 仍在主验前，因此实现禁止开始。

本包不实现 public CLI、`run-all`、tracking/MLflow、research summary、fresh-process reproducibility、fake 全 DAG、
G9 或正式 G1 数据运行；不改变 G7F 交易、指标、Decimal、七表、21/29 receipt 或 P0 publication 语义。

## 2. 审计发现与必须拆包的原因

当前 `make_work_run_plan` 把全部 stage 放在同一静态 chain。backtest 节点目前收到公共 label/reconciliation/folds/
experiment boundary inputs，以及直接前驱 backtest-plan 的四个 outputs；它既没有 target/plan producer receipt 的
输入引用，也没有 formal G1 manifest、G1 receipt 与八个 market-facts 文件的 exact 输入闭包。

G7F verifier 则明确要求 receipt inputs 精确为：

1. target manifest、target receipt、target weights、target daily；
2. plan manifest、plan receipt、scheduled targets、schedule diagnostics、cost schedule；
3. experiment manifest、experiment receipt；
4. G1 manifest、G1 receipt；
5. 八个 G1 market-facts 文件。

总数精确 21，不能多、不能少。当前 node 若直接交给 StageRunner，会发布与 G7F verifier 不兼容的 receipt。
此外，StageRunner 必须在 final rename/receipt 之前调用完整 closure verifier；现有 G7F 只有 builder 与“要求正式
receipt 已存在”的 final verifier，没有 pre-receipt fresh output verifier。用宽松 manifest reader、handler 自报
`PASS` 或发布 receipt 后才首次做业务验真都不合格。

因此 G8 必须拆成：

1. **本 R1：formal backtest identity-resolved wave + pre-receipt fresh closure + final verified result；**
2. 后续 R2：formal tracking wave；
3. 后续 G8C 增量：public `backtest`/`run-all` loader、失败隔离与 CLI；
4. 后续 G8E/G8F：fresh-process reproducibility 与 fake 全 DAG。

本包不得顺手实现 R2 或 CLI。五种用户可见 continuation 仍是
`SNAPSHOT/PROVIDER/EXPERIMENT/WORK/SUMMARY`；R1 是 `WORK` 内身份完全解析后的新 wave，与已经采用的
provider/experiment 多 wave 原则一致，不新增第六 continuation。

## 3. G7F pre-receipt public closure

在 `src/quant/backtest/a_share_reporting.py` 增加并从 `quant.backtest` 安全导出：

    experiment: VerifiedExperimentIdentity,
    fresh_context: BacktestArtifactFreshVerificationContext,
) -> tuple[Path, ...]: ...


def backtest_artifact_output_relative_paths() -> tuple[str, ...]: ...


def verify_backtest_build_output(
    *,
    root: Path,
    target: VerifiedTargetArtifact,

冻结要求：

- `backtest_artifact_input_paths` 是 21-input 顺序与集合的唯一 public SSOT；现有 builder/verifier receipt 逻辑改为
  调用它，G8 不复制第二份文件清单；返回值必须精确 21、绝对物理路径唯一，并把四个 receipt path 与 outer
  verified bundle 的 receipt SHA/physical path 对齐；
- `backtest_artifact_output_relative_paths` 返回 canonical POSIX、严格排序、精确 29 个 leaf file；G7F P0 expected
  names 与 G8 `StageBuildReport` 均调用它，不复制 29 文件集合；
- `verify_backtest_build_output` 与 final verifier 共用同一私有 fresh/tree/readback 实现：actual public plan
  verifier exact once、F0 loader exact once、actual G7E 三次、固定 Decimal context、29-file whole-tree、Schema、
  metrics 与 manifests 全部重算；唯一区别是 pre-receipt boundary 不读取 receipt，也绝不返回
  `VerifiedBacktestArtifact`；
- pre-receipt 函数成功仅表示 temp/final tree 的业务内容在当前 fresh 输入下成立，不是跨 stage verified bundle；
- 三个函数 exact type fail-closed，普通错误稳定为 `M3_A_SHARE_BACKTEST_ARTIFACT_INVALID`，cause/context 为空，
  不泄露 path/hash/symbol/date/TOKEN/SQL/PID/private marker；不得扩大 rollback 错误语义；
- 不改变既有 `build_backtest_artifact` 与 `verify_backtest_artifact` 签名、返回类型、字节、异常、fresh 次数和
  21/29 合同。

## 4. Formal backtest wave API

新增 `src/quant/research/m3/backtest_stage.py`：

```python
@dataclass(frozen=True)
class FormalBacktestStageResult:
    final_root: Path
    receipt_path: Path
    verified: VerifiedBacktestArtifact
    receipt: StageReceipt
    reused: bool

    def __reduce__(self) -> Any:
        raise TypeError("M3_FORMAL_BACKTEST_STAGE_INVALID")


def make_formal_backtest_run_plan(
    *,
    target: VerifiedTargetArtifact,
    plan: VerifiedBacktestPlanArtifact,
    release: VerifiedG1Release,
    experiment: VerifiedExperimentIdentity,
    config: LoadedM3Config,
    fresh_context: BacktestArtifactFreshVerificationContext,

def run_formal_backtest_stage(
    *,
    stage_root: Path,
    target: VerifiedTargetArtifact,
    plan: VerifiedBacktestPlanArtifact,
    release: VerifiedG1Release,
    experiment: VerifiedExperimentIdentity,
    config: LoadedM3Config,
    fresh_context: BacktestArtifactFreshVerificationContext,
    artifact_roots: Mapping[str, Path],
    resume: bool = True,

```

允许从 `quant.research.m3` 安全导出上述三个名字。`FormalBacktestStageResult` 只是同次 runner/final-verifier 的
组合返回值，不能由 caller 构造后作为其他 fresh verifier 的替代输入。

### 4.1 Plan 精确合同

`make_formal_backtest_run_plan` 必须：

1. exact 校验 target/plan/release/experiment/config/fresh context/roots；调用
   `backtest_artifact_input_paths` 得到唯一 21 paths，并在给定非嵌套真实 `artifact_roots` 中各自选择唯一 alias；
2. 对 21 paths 当场读取单链接普通文件 identity、size、SHA-256，形成 21 个严格排序、无重复
   `ExternalInput(ArtifactDigest(...))`；不接受 caller digest、hash、manifest Mapping 或裸 path list；
3. 复核 target/plan/experiment/G1 的 work/release/config/receipt identity 与 fresh context exact；node
   `scope="WORK"`、`scope_key=target.manifest.work_key=plan.manifest.work_key`；
4. 返回 exact `RunPlan(continuation="WORK", nodes=(node,))`，其中：
   - `node_id="backtest.<fold>.h<horizon>"`；
   - `spec_name="backtest"`；
   - `fold/horizon` 从 target/plan manifest 唯一取得；
   - `dependencies=()`，因为本 wave 的所有上游都已发布并 fresh verified；
   - `publication.final_directory="work/<work_key>/backtest"`；
   - `receipt_path="receipts/backtest/<work_key>.json"`；
   - `output_specs == BACKTEST_STAGE_SPEC.outputs`；
5. plan builder 是纯函数：不调用 builder/G7E/handler，不创建目录，不扫描 artifact tree，不打开 MLflow。

本包同步修正 `make_work_run_plan`：formal WORK 首 wave 只到 `backtest_plan`，不得再生成一个 receipt 输入不闭合的
formal backtest/tracking node；development/example 旧 chain 可以保持原行为，但必须使用显式 development stage
names，不能冒充 formal。后续 formal backtest 使用本函数，tracking 使用后续 R2 wave。既有 G8A 阶段报告保留
历史，不回写；本包报告明确记录该增量修订。

### 4.2 Runner 精确顺序

`run_formal_backtest_stage` 固定执行：

1. 调用 `make_formal_backtest_run_plan` exact once；
2. 用同一 `stage_root/artifact_roots/config` 创建 `StageRunner`；不得从 runner 私有字段反推输入；
3. handler 收到的 `StageContext` 必须与 plan 唯一 node、同一 `LoadedM3Config` 对象及 21 resolved inputs exact；
   不一致时在第一个业务输出字节前失败；
4. handler 只调用 actual `build_backtest_artifact(..., output_root=context.temp_output_root)` once，不自行创建 final
   path/receipt，不接受 caller result、metrics、frames、transition 或 output report；
5. handler 返回 `StageBuildReport(backtest_artifact_output_relative_paths())`，精确 29 leaf files；
6. `closure_verifier(temp_or_orphan_root)` 调用 actual `verify_backtest_build_output`，因此首次发布、orphan 恢复与
   completed resume 都在 receipt 之前/复用时重新做 fresh 业务闭包；
7. `StageRunner.run_static(..., plan=run_plan, resume=resume)` 负责 lock、temp、whole-directory no-clobber、orphan
   byte equality、receipt 发布与恢复；receipt inputs/outputs 必须精确等于 21/29；
8. runner 返回后调用 actual `verify_backtest_artifact` exact once，要求 root/receipt/work identity 与 runner result
   exact，才返回 `FormalBacktestStageResult`；final verifier 失败稳定映射为
   `M3StageRunnerError("STAGE_RECOVERY_CONFLICT")`，不能把已发布 receipt 当作成功；
9. `resume=False` 遇到合法完成 stage 保持 runner 的 `STAGE_ALREADY_COMPLETE`，零写入且不调用 builder；
10. builder、pre-receipt verifier 与 final verifier 的 fresh 重放不得由缓存、manifest 自报或同一内存
    `_FormalBundle` 代替。高成本是本高风险发布边界的显式代价，后续若优化必须另立等价性任务。

普通 stage 失败只使用现有 `M3StageRunnerError` 稳定 code：input、lock、build、output、publish、recovery conflict、
already complete。不得把 G7F hostile exception message/cause/context 暴露到 runner 或 CLI。

## 9. StageRunner closure 调用次数重冻（2026-08-10）

实现核对发现§4.2.6要求每次closure都actual fresh验真、§4.2.10禁止缓存，而原§5.5又写pre-receipt verifier
actual once。现有安全发布primitive首次必经temp closure与atomic rename后的final closure；完整orphan还要先验
existing final。删除final closure或缓存temp bundle都会削弱发布边界，禁止采用。

权威计数改为“每次closure invocation恰一次actual `verify_backtest_build_output`”：

- 首次发布：handler 1，closure 2（temp 1 + final 1），final verifier 1；
- completed resume：handler 0，closure 1（existing final），final verifier 1；
- 完整orphan相同并补receipt：handler 1，closure 3（existing final + temp + final），final verifier 1；
- `resume=False`已完成：handler 0；runner按其既有顺序若在already-complete前验证existing final，则该closure必须
  actual且计入；测试以actual primitive行为冻结，不得为凑零次改publish顺序；
- partial/different/hostile路径按实际到达的每个closure各actual一次，失败后不得继续后续closure/final verifier。

新增测试必须逐路径断言上述顺序和次数，并令每次actual verifier返回独立对象/计数nonce，证明没有缓存、复用
`_FormalBundle`或跳过final root fresh。原任务其他业务、receipt与白名单不变。

## 10. 邻接测试源码内省修正（2026-08-10）

最终 Windows 组合在既有 `tests/unit/test_m3_orchestration_plans.py` 稳定暴露一项测试合同缺陷：该测试对
development feature verifier 使用 `inspect.getsource()`，强制在装饰后的公开函数源码文本中出现

进一步逐项核对确认同一循环内的 alignment/model/prediction/evaluation/target/backtest-plan/backtest 也均已
使用各自 boundary decorator 委托共享 verifier；不存在可以诚实保留旧字面量内省的子集。权威最小修正一般化为：

- 只修改上述测试文件，完整删除八个 verifier 的 `inspect.getsource()` 字面量循环及因此变成未用的 import；该
  orchestration test 只负责验证 development plan 的 exact stage 集合、依赖与 receipt 路径，不再越层检查 artifact
  verifier 的实现形状；

## 11. WSL1 exclusive commit 能力边界（2026-08-10）

最终 WSL base 组合的唯一失败发生在 actual golden 首次 static commit。定向只读/临时探针确认：final 全部父目录
存在，temp 与 final parent 同一 `st_dev`；但本机 WSL1 在 `/tmp` 与 `/mnt/f` 对
`renameat2(RENAME_NOREPLACE)` 均返回 `EINVAL`。因此不是跨设备、父目录或 G8 路径缺陷，而是当前 WSL1 内核
不提供 StageRunner 冻结的 exclusive directory commit primitive。

本包平台验收重冻如下：

- 禁止为使 WSL1 变绿而改 `commit_directory_noreplace`、StageRunner publish primitive，禁止退化为先检查再普通
  rename、覆盖发布或非原子 fallback；
- actual G8 golden 在入口使用现有 public `platform_supports_renameat2_noreplace()` 能力探针；能力为 false 时只跳过
  该 golden，并写明 exclusive commit unsupported。能力为 true 时必须完整执行，失败不得 skip；Windows 当前必须
  继续 actual PASS；
- WSL base §7 其余单元、G7F/P0/编排邻接必须全部 PASS，期望当前主机为 `91 passed, 1 skipped`；Ruff/mypy/cold
  import 仍必须全绿；
- 该 skip 只证明安全 fail-closed 与 WSL interpreter/DrvFS 邻接兼容，不证明 Linux ext4/G8 Gate。未来 ext4 主验必须
  先证明能力探针 true，再运行 actual golden 与最终组合全 PASS，方可关闭平台 Gate。

此条不改变任何 production 白名单或业务合同，只允许在既有 G8 golden 文件中增加窄平台能力标记。

## 13. R3：WSL1 不可达实体窗口的测试证据诚实性返工

### 13.1 现象、根因与应遵循规则

R2 独立初验确认 production 的 current context、21-input 与 Windows 三窗口实体守卫均可实触达；阻断仅在测试
证据语义。WSL1 的 public `platform_supports_renameat2_noreplace()` 为 false，StageRunner 在 exclusive commit
处先以 `G1_RELEASE_PUBLISH_UNSUPPORTED` 短路并映射为 `STAGE_PUBLISH_FAILED`。因此 temp 后 final closure 前、
final 后 receipt 前两个 mutation callback 在该宿主根本没有执行，EntityGuarded 也没有触达。R2 测试把后两窗
允许码放宽为 `{STAGE_RECOVERY_CONFLICT, STAGE_PUBLISH_FAILED}`，错误地把平台前置短路算作实体窗口反例通过。

测试不得把“未到达被测窗口”伪装成该窗口的安全证据。平台能力 false 只允许按§11诚实窄 skip；能力 true 时必须
证明 mutation 与对应守卫实际发生，不能用宽错误码集合掩盖前置失败。

### 13.2 最小返工合同

1. 本轮为 tests-only：不得修改 `src/quant/research/m3/backtest_stage.py`、StageRunner primitive、G7F/G1 或任何
   production；记录并核对 production SHA 与 R2 交付值一致。
2. handler 后 temp closure 前的窗口不依赖 exclusive commit，双平台继续实际执行并按原合同断言。
3. temp 后 final closure 前、final 后 receipt 前两个窗口：
   - capability false 时，在进入构建/发布前以明确理由窄 skip，例如
     `exclusive commit unsupported; inode window unreachable`；不得执行后再把 `STAGE_PUBLISH_FAILED` 当通过；
   - capability true 时必须实际执行 mutation，并以计数或等价不可伪造证据断言 mutation 已发生；temp→final
     只接受 final closure 的实体重验失败，final→receipt 还必须断言 EntityGuarded 已触达且 base receipt publish
     未发生；当前稳定公开码均为 `STAGE_RECOVERY_CONFLICT`，不得再接受 `STAGE_PUBLISH_FAILED`。
4. 所有实际执行的失败仍须断言无 receipt/temp 残留且 cause/context 为空；不得把 skip 计作 PASS 或 ext4 Gate。
5. 保留 current Windows unit/golden/必要邻接；WSL 当前 revision 必须取得明确 unit+golden 终态，预期后两窗及
   actual golden 按各自 public capability 窄 skip，其余全部 PASS。未来 capability true 的 Linux/ext4 必须实际
   运行三窗和 golden，不能沿用 skip。
