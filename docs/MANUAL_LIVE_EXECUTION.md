# 半自动实盘：通知、人工成交与自动记账

设计日期：2026-09-20。状态：已核对现有代码并形成实施设计，尚未部署双向机器人、未开通实盘账户、未发送真实下单指令。日常流程由独立后台程序执行，不依赖 Codex 会话或 LLM；下单、撤单仍由用户在券商端完成，`auto_trade=false`。

## 1. 信号频率不等于下单时点

|情形|可用信息与操作|当前判断|
|---|---|---|
|现有 Q10/R8 日线/月度策略|T 日收盘后计算，T+1 盘前核对；只在冻结策略规定的调仓日操作|优先接入候选；研究报告好看不等于已批准真实资金使用|
|T+1 开盘集合竞价|订单必须事先准备并在适用竞价窗口内提交；限价及未成交处理固定|更接近开盘执行假设，但不保证成交；不能提前使用尚未知的实际开盘价|
|T+1 09:30 后人工操作|使用即时行情，在预先验证的执行窗口内手动限价下单|适合两分钟人工流程；真实成交可能是09:32，不能直接沿用09:30开盘价回测结论|
|T 日尾盘操作|只能用下单前确实已知的信息，例如截止14:50的完整分钟数据或T−1日线|这是另一个执行/信号定义，不能拿T日最终收盘、全天成交量在14:55下单|
|5分钟日内信号|完整bar且数据已实际到达后才计算，再叠加消息和人工延迟|5分钟只是信号频率；无需持有恰好5分钟，也不保证两分钟延迟仍可获利|

当前 `q10_paper.py` 明确月末收盘信号、下一交易日模拟成交，且当日日更等待21:00之后的执行输入。`reference_orders` 是收盘参考价格下的估算，不能把模拟现金、模拟持仓和估算价格当成真实账户。现有开盘±1%价格带仅为演练工具，不是已验证的实盘风控参数，也不能在真实开盘价出现前计算。

上交所股票竞价时段为9:15–9:25、连续竞价9:30–11:30及13:00–14:57、收盘集合竞价14:57–15:00；9:20–9:25及14:57–15:00不接受撤单。临近收盘才发两分钟时效消息很容易跨入不可撤单阶段。这里不能推广为所有ETF/所有市场规则，执行器须按证券类别、市场和交易日历分别验证。[上交所2026交易规则](https://www.sse.com.cn/lawandrules/sselawsrules2025/stocks/exchange/c/c_20260424_10816482.shtml)

建议先验证“前一晚准备、次日固定窗口手动限价”的日线模式。窗口、有效期、价格偏离上限和未成交处理先冻结，再回放0/1/2/3/5分钟延迟与原三档成本；不挑表现最好的时刻事后上线。需要1分钟或更细的可用价格证据时，不用5分钟OHLC伪造09:32成交；成交量、限价未成交、部分成交和先卖后买都进入回放。原路线图日内悲观3分钟及2×成本要求保留，额外查看5分钟异常压力，不能降低原准入门槛。

两分钟应分开计量：数据可用→计算→平台接受→用户确认→券商委托→实际成交。现有实时数据配置1分钟轮询不少于60秒、供应商bar标签至少确认63秒；总延迟还受标签语义、网络和人工影响，不能把“收到后两分钟”视为“bar结束后两分钟”。测量每个时间戳及p50/p95、过期率、漏单率和实现偏差。A股个股T+1继续生效；ETF是否日内回转按品种规则，不能统一当T+0。

## 2. 已有基础与明确缺口

本节为源码检查事实，不是已完成的实盘验证。

|能力|现状|接入方式|
|---|---|---|
|信号及次日参考订单|`execution/q10_paper.py`、`stock_paper.py` 已有|复用冻结信号，以真实账户重新算订单，不拷贝模拟账户数量|
|手工订单风控|`execution/manual_orders.py`、`manual_execution_plan.py` 已有演练入口|抽取已有检查并接到真实账本；原演练命令不冒充生产服务|
|成交与资金事件|`execution/manual_fills.py` 支持外部ID、相同事件去重、冲突拒绝、现金与T+1|作为已验证纯函数复用；补消息到订单/成交事件的映射、持久事务、乱序重建|
|日终真实账本估值|`execution/manual_nav.py` 支持收盘估值及出入金修正|独立真实账本；费用未知和券商未核对要显式标明|
|通知|`notify` 有邮件/企微/飞书webhook/wxauto；当前channels为空|尚无启用的双向实盘通道|
|双向交互|wxauto有读消息函数；企微/飞书现有代码仅发送|新增官方事件订阅和固定格式解析，不能凭微信显示昵称认证|
|投递可靠性|现有webhook只按HTTP状态判断；outbox本地落盘也返回ok|区分已落盘、平台接受、用户确认、已委托、已成交；补平台业务码和消息ID|
|行情|Futu只读行情与本地存储已有，包含新鲜度/可用时间检查|先核验真实交易时段、权限、覆盖和延迟；历史补全不等于实时可用|

不得把 `outbox ok`、机器人发送成功、用户回复“收到”或“已委托”当成成交。现有手工账本把股票买入按T+1处理，首版如纳入T+0 ETF，须先补证券级结算规则，不能直接复用股票规则冒充正确。

## 3. 通信渠道

|渠道|建议|实际接入|
|---|---|---|
|飞书自建应用机器人|用户已选择，作为首版主渠道|官方Python SDK发送消息、订阅接收消息和卡片回调；长连接服务主动连平台|
|企业微信智能机器人|同等可选，不必为了技术强制改用飞书|官方Python SDK已有WebSocket、主动推送、消息接收、卡片事件和重连；账户权限、可见范围与手机接收须实测|
|个人微信wxauto|可做备用提醒，不作为无人值守主回执入口|依赖登录客户端、解锁交互桌面；当前读消息包装无稳定发送者ID/消息ID|

官方SDK能力来源：[飞书Python SDK](https://github.com/larksuite/oapi-sdk-python)、[企业微信Python SDK](https://github.com/WecomTeam/wecom-aibot-python-sdk)。两者不能与项目现有“只填Webhook地址”的发送器混为一谈。采用长连接时服务只需主动联网，不为这个功能开放本机看板端口；平台后台的应用发布、权限和指定会话绑定仍需完成。

只接用户允许的账号ID和会话ID；密钥置环境变量/系统凭据，不进Git、不写普通日志。平台回调按官方SDK验证；服务只收与交易协议有关的结构化消息。正常入账不用LLM、DeepSeek、语音或图片识别猜价格；图片可作附件证据，不自动作为成交事实。只给必要会话发送账户别名、证券和数量，不发送券商密码或完整账户号码。

首版飞书接线：企业自建应用启用机器人，发布到用户可见范围，按需开启 `im:message:send_as_bot`、接收指定会话消息的最小权限，订阅 `im.message.receive_v1`；卡片模式再增加 `card.action.trigger`。选择官方SDK长连接，密钥使用 `FEISHU_APP_ID` / `FEISHU_APP_SECRET` 环境变量。先用指定用户单聊，保存稳定用户ID/会话ID白名单；不申请无关通讯录或全群消息权限。Python服务负责调度和计算，不需要购买LLM服务。官方接口名见[飞书SDK](https://github.com/larksuite/oapi-sdk-python)。

## 4. 最小常驻流程

```mermaid
flowchart LR
    A[冻结信号与真实账户] --> B[时效与执行风险检查]
    B --> C[持久订单建议与消息待发记录]
    C --> D[机器人通知]
    D --> E[用户在券商手动下单或撤单]
    E --> F[结构化委托及成交回报]
    F --> G[验证身份 去重 入账]
    G --> H[自动确认 持仓及现金更新]
    H --> I[收盘估值与券商对账]
    I --> A
```

1. 首次由用户选定冻结策略版本、真实账户别名和允许本金；导入经核对的初始现金、持仓、可卖数量、成本及在途委托。不是把模拟账户余额改名成实盘。首期资金只选10万或100万；选择取决于用户，并须匹配已有执行证据。
2. T日晚间信号完成后持久保存候选计划、数据时点、策略版本、订单建议编号；未调仓也产生“今天无操作”的状态。盘前复核交易日、停牌、涨跌停、账户差异与必要行情；不合格只发原因，不发可执行买入单。
3. 根据冻结窗口释放订单建议：账户、交易日、证券、方向、股数、限价规则、有效截止时间、理由及版本；分开“预告”与“可执行”。参考价不等于成交价。先卖后买的可用资金只依据实际已报成交和券商可用余额，不能预支计划卖出资金。
4. 用户在券商手动下单后回“委托”，后续回“成交”；不需要Codex审读，解析器确定性执行。平台收到先持久化收件箱并及时ACK，后台再校验/记账，避免阻塞回调期限。
5. 每笔真实成交增加现金/持仓事件，更新暂记账本并自动回确认。部分成交只记本次量，剩余量保留；“已委托”只冻结资金/可卖数量，不改变真实持仓。
6. 订单有效期结束只停止继续提示执行，不视为券商已撤单。若用户已经委托但无终态，提示去券商查询/撤余单；确认前保持相应预留，禁止重复下同一订单。
7. 日终生成真实净值和策略理想净值对照、实际滑点及未执行归因；接收券商成交CSV/对账单或结构化余额/持仓核对。无券商只读接口时，系统只能自动同步用户回报，不能独立证明券商真实状态。

程序实现限定在 `notify`（渠道收发）与 `execution`（订单/成交账本）及现有reporting展示；复用现有存储/事务工具，缺的用一个单写入SQLite数据库保存消息、建议、事件和检查点，不再引入新的通用OMS平台或恢复冻结的formal体系。

## 5. 固定格式与语义

以下仅协议示例，不是当前交易建议。机器人生成带订单编号、版本的可复制模板；证券/买卖方向默认从订单带入，减少人工输入。

```text
委托 O20260921-001 v1 券商单号=B123 数量=1000 限价=10.52 时间=09:31:05
成交 O20260921-001 v1 成交号=F456 本次数量=400 成交价=10.50 时间=09:31:18 费用=待核
成交 O20260921-001 v1 成交号=F457 本次数量=600 成交价=10.51 时间=09:31:36 费用=待核
撤单确认 O20260921-002 v1 券商单号=B124 已撤剩余=500 时间=09:34:10
跳过 O20260921-003 v1 原因=错过窗口
```

- 券商委托号与成交号分开；日期从绑定订单确定，全部存储完整Asia/Shanghai时间。`本次数量`是增量，不是累计数。多笔成交可用卡片表格一次填报，卡片动作只提交记录，不能替用户发券商指令。
- 幂等键包含渠道消息ID，以及账户/交易日/券商成交号；同号同内容不重复入账，同号异内容挂起核对。无逐笔成交号时以订单+人工分笔号替代并标“用户回报待对账”，不能把重复新消息当新成交。
- 订单号、版本、证券、方向、数量上限、价格格式/最小变动价位、真实时间与账户绑定都校验；显示昵称不能替代稳定用户ID。格式缺字段自动提示模板，不猜值。
- 用户实际成交可能超过建议限价或发生在过期后：保存原始回报并标执行偏差，不能为了漂亮账本丢弃真实成交。异常数量/账户矛盾在核对后修订账本，未核对前暂停相关新增买入建议。
- 漏报可补录；新回报按实际成交时间进入追加事件，再从此前检查点重建。不能绕过当前 `manual_fills` 的乱序保护。更正新增一条有引用的更正事件，原事件不可覆盖；重新核算受影响日期及之后净值。
- 费用未知记录为待核，不默认0并宣称净收益准确；先预留保守费用，券商对账后替换估计并版本化重算。最低佣金按券商实际计费归属核对，不每条部分成交都重复收最低费。
- 无入金/出金/分红/费用记录的“持仓一致”不是完整对账。把这些事件与交易成交一起同步，外部现金流不能算成策略利润。

## 6. 延迟、断点与人工可操作性

订单建议、发送尝试和收件事件先持久保存；入账与处理标记在同一事务完成。重启恢复未处理收件记录，重新校验未发建议；过期提醒不补发为可执行订单。平台超时不等于没发送，优先利用平台去重/查询能力，不能盲目重发让用户下第二单。不同备份渠道使用同一订单编号。

离线期间是否重投递消息不能假设：按官方事件语义与权限补拉缺口；无法证明完整接收时标记回执缺口，要求用户/券商成交记录补齐，不宣称已自动同步。

主进程与研究挖掘分开，由Windows启动任务/服务启动、单实例和失败重启；开盘前健康检查。没有电脑电源和网络就没有本地服务，不能承诺关机仍在线。用户允许电脑休眠/关机时，选择常开小主机或服务器；另一个在线节点才能报告本机彻底离线。本轮不购买或开通云服务。

提醒没确认与实际没成交分开；超时只提醒查询，不能自动生成“补买”。未知的在途订单预留资金与可卖股数。紧急停用只阻止新建议，不能替用户撤掉券商中的订单。

两分钟应按整批订单而不是单笔估计：Q10 Top50月末可能有多笔调仓，不能假设50笔手动操作都在两分钟内完成。纸面联调测用户处理整批的延迟，若超限，先研究预注册的执行窗口/数量方案或更低操作量策略；不能擅自砍成Top5或分三天而沿用原收益结论。

## 7. 实施顺序及验收

|顺序|交付|完成证据（待实现）|
|---|---|---|
|1|选一个官方双向渠道；演练消息协议与持久收件箱|指定用户手机收到、回复被识别；业务码/消息ID可靠；重复、伪身份和坏格式不改账；重启能恢复|
|2|把现有manual_fills/manual_nav接到回报处理|全成/部分成/撤单未成/补录/更正/费用待核/重复和乱序场景逐项正确，账本可重建|
|3|冻结一种日线人工执行窗口，影子跟单|记录全链路时延、整批操作量、漏单与实际成本；分钟回放包括延迟及未成交，不伪造开盘成交|
|4|真实账本、资金预留、盘前复核、日终对账和看板|初始券商状态一致，真实与模拟分列；未核对费用/持仓明确显示；停机恢复不重复建议或入账|
|5|用户明确启用一个账户和冻结策略的小规模人工实盘|只有前述链路通过后才发真实可执行建议；用户逐笔手动决定下单，auto_trade=false；不据此自动换模型或加仓|
|6|按证据决定5分钟策略|真实延迟分布和分钟覆盖满足既有研究要求；日内回转仅限适用证券；高操作量或对延迟敏感则继续研究，不强行上线|

已确认主渠道：飞书自建应用机器人。待用户确认的设计参数：可绑定账号、券商、首期资金、现有持仓、开盘/尾盘可操作时间、常开主机条件、是否能导出券商成交和持仓CSV。先完成设计不需要这些凭据；连接真实渠道及启用资金账户前再落实具体对象。

本文件是工程设计，不是实验结果或收益保证。当前只完成设计与代码审查，没有把以上待实现项目登记为完成。
