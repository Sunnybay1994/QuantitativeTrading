五环节还需一条研究反馈链：预注册候选→统一评估→逐年模型→模拟盘/人工执行→成交成本和预测误差→下一批研究。现有研究入口已能串联统计、成本、筛选、模型和报告，但日常数据与人工成交反馈尚需衔接。不能将独立模块数量当成运行链已完成。

## Rust：先看可替换耗时，后谈语言

Polars的核心已经是Rust，并内置多线程；Python中的列式过滤、聚合和连接并非纯Python循环。换一个调用语言不自然产生同等量级加速。参考[Polars官方介绍](https://docs.pola.rs/)、[多进程说明](https://docs.pola.rs/user-guide/misc/multiprocessing/)。

本地已有证据：

- 32项因子的年度成本汇总，通过日期检查列式化从152.04秒降到63.48秒，约2.4倍；年度选择一致。产物：`artifacts/models/p4_training_costs_20260911_09_fast/timing.json`。
- 20个交易日、264只股票的剖析总耗时1.225秒。`quant.backtest`中Python函数的排他耗时0.206秒，占16.84%；`iter_rows`自身耗时0.175秒，原生Polars `collect`耗时0.286秒。还有重复schema校验、构造表和字典等开销。排他耗时与调用链累计耗时不可相加。
- 如果仅把上述0.206秒加速10倍，其他耗时不变，整体为1.18倍；该部分耗时降至零的上限约1.20倍。这不是完整Rust账户内核的上限，因为改造数据表示也可能减少其他开销。

敏感性计算采用`整体加速 = 1 / (1 - 可替换占比 + 可替换占比 / 内核加速)`，暂不增加跨语言传输成本：

|假设可替换部分占整批耗时|假设Rust内核快10倍|整体加速|
|---:|---:|---:|
|20%|10倍|1.22倍|
|50%|10倍|1.82倍|
|80%|10倍|3.57倍|

上表为条件推演，不是本机Rust实测。样本也不覆盖整库、多进程争用和全部公司行动。剖析原件：`artifacts/data_quality/cost_profile_20260911_02/profile.prof`；估算：`artifacts/data_quality/rust_assessment_20260911_01/summary.json`。

### 值得试验的边界

第一候选是账户逐日推进与成交撮合：把标的编码、价格、目标、费用及公司行动按窗口批量送入，在内核保留状态，再批量返回净值/成交/拒单。Python继续负责数据供应商、配置、研究编排、Polars列计算和报告。PIT、T+1、整手、拒单原因和公司行动时序必须与现有账户一致。

先在当前实现减少重复表校验和行对象转换，输入边界的必要校验保留；再测常规月度、高换手、停牌/涨跌停及公司行动窗口。若仍有占比足够大的CPU循环，再用同一组数据比较Rust内核和当前最优Python实现，计入读取、转换、传输、输出时间及峰值内存。不要以一个排序/收益求和微基准代表完整投研。

Rust/Python接口宜粗粒度；PyO3官方说明跨边界和解释器附着有成本，长时间纯Rust工作可解除解释器附着，见[性能说明](https://pyo3.rs/main/performance.html)。现有批处理已多进程、Polars各自多线程，新增Rust并行还要控制总线程数。

建议试验时间盒1–2天，是否进入正式实现看代表性端到端速度、输出一致和维护投入；暂以至少2倍端到端提升作为值得继续投入的目标，而非宣称可达到的结果。成本包括Python 3.13/Windows扩展构建、依赖维护、浮点与整手边界及全部公司行动回归。收益是缩短研究等待和提高复验吞吐，不直接增加策略收益。

若每次原耗时为H小时、整体加速S倍，则每次节省`H×(1−1/S)`；开发验证投入C小时，对应计算等待回本次数`C / [H×(1−1/S)]`。例如假设投入24小时、每批6小时、加速2倍，需8批节省24小时机器等待；机器等待价值与开发工时价值仍应分别看待。
