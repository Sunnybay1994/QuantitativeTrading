## 1. 方法与结论

主 Agent 对当前代码/文档做全链审计，再由未参与实现的下级 Agent 只读复核。独立 Agent 未修改文件、
未读取 `_old/` 或凭据。结论是：原 E1/E2 虽已描述 Qlib/LightGBM 薄适配器，但日期域、test 推理、模型

人工记忆。

## 2. 已确认的 P0 与修订

### P0-1：全收益基准无法通过领域 Schema

- 现象：配置和标签 SSOT 固定 `H00300.CSI`，实际 `ForwardReturnLabelSchema` 却复用只接受 SH/SZ/HK
  可交易证券的正则；`BenchmarkBar1dSchema` 只存在文档、尚未落地。
- 根因：把不可交易 benchmark identity 当作 instrument symbol。
- 规则：benchmark 使用独立 pattern；实际 Benchmark Schema 含 `source_snapshot_id`；首版配置只接受
  `H00300.CSI`，但不得放宽证券正则。label return 与 prediction score 均 finite。
- 反例：合法 `H00300.CSI` 标签必须通过；`H00300.CSI` 不得通过 Instrument/Bar Schema。
- 状态：设计已冻结，代码由 G1/H0 前置机械实现。

### P0-2：旧标签实现不再代表 v2 契约

- 现象：当前 `labels.py` 无 eligible_keys、adj_factor、diagnostics，默认价格指数并静默跳过缺失。
- 根因：旧 D3 是 v1 骨架，后续 G1 独立审查已经改变标签权威语义。
- 规则：每个 `(eligible key,horizon)` 恰好落入成功标签或一个固定优先级 reason；只遍历 PIT 资格域；
  两端 raw price×factor；显式 benchmark；diagnostics 计数守恒。
- 反例：未来成员 B 有完整行情仍不能在生效前产生标签；2:1 除权样本必须按 factor 得到正确收益。
- 状态：G1 前置，旧绿测不得作为 G3 证据。

### P0-3：fold 把 warmup/tail 当成信号日期

- 现象：旧函数直接从完整 calendar 第一日切分，而 snapshot 同时含 signal 前 60 日和后 10 日。
- 根因：provider history domain 与 signal domain 未分离。
- 规则：FoldPlan 显式 signal start/end，完整日期列表、embargo、cutoff 和 calendar hash；固定 rolling；test
  不重叠。warmup/tail 永不进入 segment。
- 反例：输入 60 warmup + signal + 10 tail，第一 train 日必须等于 signal start，最后 test 不超过 signal end。

### P0-4：label cutoff 错设为 segment end

- 现象：原设计 train/validation 只保留 `available_as_of <= segment.end`，会丢掉每段末尾约 h 个样本，
  同时让 embargo 失去“等待标签成熟”的用途。
- 根因：只记录 segment 边界，没有记录模型真正可用信息的时点。
- 规则：train cutoff 是 train→validation embargo 最后一日；validation cutoff 是 validation→test embargo
  最后一日。test 标签只事后评估。
- 反例：train 末日信号的 h=10 标签在 embargo 第十日成熟，应进入 train；晚一天才成熟则拒绝。

### P0-5：Alpha158 加载域、默认 label 与 canonical schema 不明确

- 现象：若 handler 从 train.start 加载，首批 rolling 特征缺历史；Qlib Alpha158 默认 learn processors 和
  LABEL0 可能重新引入框架标签；默认 instruments 是 csi500。
- 根因：把 Dataset segment 当作 handler raw loading domain，且只说“丢弃 Qlib label”。
- 规则：handler 从 provider history start 加载到 test.end；instruments 来自 provider manifest；显式空
  processors 和 `label=([],[])`；运行时 feature config 必须是 158 个唯一 name/expression 并发布 manifest。
- 反例：训练首日有 60 日回看；fake 若收到默认 csi500、非空 processor 或 label expression立即失败。

### P0-6：test 先 join label 造成选择偏差

- 现象：旧单一 `align_features_and_labels` 让 test prediction 只覆盖未来恰好有标签的行。
- 根因：把监督训练矩阵与实时推理矩阵抽象成同一对象。
- 规则：train/validation 使用 `SupervisedSegment`；test 使用不接受 label 参数的 `InferenceSegment`。
  prediction keys 精确等于全部 eligible+scorable test keys，标签只在预测发布后连接。
- 反例：B 未来 exit 缺价但信号日可评分，仍必须预测/进入 G7，只有 evaluation 不匹配 B。

给实现 Agent 的指导：任何“未来结果是否存在”都不能决定当时是否产生信号。若同一个函数同时服务
fit 与 inference，先检查其参数是否让未来 label 渗入推理路径。

### P0-7：train 全 NaN projection 没有唯一执行点

- 现象：旧任务要求 fit 时删全 NaN 列，predict 又要求列 hash 完全一致，调用者只能自行猜何时切列。
- 根因：input schema、selected schema 与 projection lineage 未分开。
- 规则：FeatureBundle 是唯一 projection 执行点；先验真 158 input，再用 train eligible rows 选 selected，
  validation/test 复用。manifest 同时记录 input/selected hash 和 dropped names，model 只接受 selected。
- 反例：A 列 train 全 NaN、test 有值仍永久删除；缺列/额外列/换序均失败。

### P0-8：early stopping 指标与接口不一致

- 现象：配置写 validation RankIC，旧 fit 接口却没有日期 metadata，无法按日计算；实现很可能悄悄使用
  LightGBM 默认 l2。
- 根因：研究报告指标和 booster iteration 选择指标混为一谈。
- 决策：M3 固定参数、无搜索；native LightGBM regression 只用 validation l2 early stopping，RankIC 在
  模型锁定后报告；不使用 test、不合并 train+validation 重训。
- 反例：fake 证明 valid_sets 只有 validation、metric=l2、test 对象无法传入、best iteration 来自 callback。

### P0-9：模型多文件发布与 StageRunner 重复负责

- 现象：model/metadata 两次 replace 不能形成集合原子提交，且 G8 已指定 receipt 是唯一完成标记。
- 根因：模型函数和编排器都试图当 publisher。
- 规则：fit 只写 StageRunner 分配的空临时目录；runner 发布并最后写 receipt。新增 `load_fitted_model`，
  供新进程复算 hash、identity、projection 和版本后恢复。
- 反例：model 后/metadata 前崩溃不得被下游视为完成；篡改任一文件或跨 work 加载失败。

### P0-10：prediction 可混合两个真实模型

- 现象：静态 model_version/snapshot/fold/horizon 不足以区分不同参数、代码或 model 文件。
- 根因：PredictionScore 是跨层轻契约，缺少批次 artifact lineage。
- 规则：不把所有研究字段塞进全局 Schema；同目录 prediction manifest 绑定 experiment/work、model hash、
  feature schema和 parquet hash。evaluate/targets 必须同时验真 manifest。Schema 的 key/rank 分组补入 model。
- 反例：两个 model 文件、相同 model_version 的部分证券预测拼表，manifest hash/identity 必须拒绝。

### P0-11：评估把所有不可计算日叫“零方差”

- 现象：无 label、无 prediction、样本过少、score/label 零方差都落入同一布尔值；NaN 指标又不是严格 JSON。
- 根因：缺少 coverage ladder 与稳定状态机。
- 规则：五层样本计数、四个 coverage、八种 `ic_status`；ICIR 用可计算日 mean/sample std、不年化；计数
  为 int，未定义值为 JSON null，`allow_nan=false`。
- 反例：每个 status 单独 fixture；prediction 完整但 label 缺失不得被叫 prediction coverage 下降。

### P0-12：同 fold 两个 horizon 重算相同大特征

- 现象：原 G8 将 features 放在 work scope，h=5/h=10 会重复 Qlib 计算和存储。
- 根因：把 horizon-dependent label alignment 与 horizon-independent Alpha158 混成一个 stage。
- 规则：每 fold 一个 experiment-scoped FeatureBundle，两个 work 共享；alignment 才按 horizon 分开。
- 反例：2 folds×2 horizons 只调用 Qlib handler 两次，不是四次；同 fold 两 work 的 feature hash 相同。

## 3. 聚合与 Gate 口径

- fold daily IC 可按 horizon 拼接，但日期必须不重叠；aggregate 从 daily 重算，不平均 fold ICIR。
- test metrics 永不用于调参、iteration、feature projection或选择“最好 fold”。
- G6 research aggregate 不复合 G7 各折独立账户 NAV；成本后收益由 G7 单独报告。
- acceptance threshold 与科学 metric 分离：threshold 改变不改历史结果 identity；`minimum_ic_symbols` 会
  改变 daily computability，因此属于 `evaluation` scientific config。
