## 4. P1-A：readiness 未执行严格 Benchmark Schema

### 4.1 现象

当前 readiness 只检查必需列是输入列的子集，再做部分 OHLC/key 检查。给合法 benchmark 表额外加入
`symbol,volume,amount,adj_factor` 后，结果没有 `BENCHMARK_INVALID`，旧股票形状因此可以通过结构门禁；
主验样例只另因夹具日期不足出现 `BENCHMARK_DATE_COVERAGE`。

### 4.2 根因与应遵循规则

根因是把“具备所需列”当成“符合严格 Schema”。L0A 的系统不变量是：基准不是可交易股票，readiness
消费的 `benchmark_bars` 必须精确符合代码 SSOT `BenchmarkBar1dSchema`，而不是它的任意超集。

- 缺少必需列仍使用 `BENCHMARK_MISSING_FIELDS`；
- 额外列、列类型、Schema 跨字段约束、OHLC/null/non-finite/非正问题统一形成 `BENCHMARK_INVALID`；
- 结构错误不得向外泄露 Polars/Pandera 异常，也不得阻止其他独立 readiness issue 的确定性收集；
- 不得把股票列加进 `BenchmarkBar1dSchema`，也不得恢复股票 helper。

实现应在依赖性 Polars 操作前检查 exact column set，并调用生产 `BenchmarkBar1dSchema.validate`（或
一个唯一、等价且由该 Schema 驱动的公共 validator）。不得再手写一份可能漂移的宽松字段合同。

### 4.3 最小复现

在 `tests/unit/test_m3_readiness.py` 的合法 `_benchmark_bars()` 上增加：

```python
symbol="000300.SH", volume=1.0, amount=1.0, adj_factor=1.0
```

调用 `_audit(benchmark_bars=...)`。修复前没有 `BENCHMARK_INVALID`；修复后必须稳定包含该 code，且不抛
底层异常。

### 4.4 新增测试与通过条件

至少增加：

1. 股票专属四列作为 superset 时拒绝；任意一个未知额外列也拒绝；
2. 精确列但 dtype 无法按 Schema 合法转换时拒绝，验证真实 Schema 被执行，而非只验列名；
3. 精确合法 `BenchmarkBar1dSchema` 仍保持原有合法路径；
4. 缺列只报既定缺字段语义，不因随后访问缺列抛二次异常；
5. 注入含绝对路径/疑似 token 的 Schema 异常时，公开 issue 不泄露原消息、cause 或 traceback。

通过条件：上述反例均绿，原 readiness 日期覆盖、symbol/source、重复键语义不退化。

## 5. P1-B：mapper 未重验 VerifiedRawResponse identity 闭包

### 5.1 现象

先用正常构造器生成合法 `VerifiedRawResponse`，保存 receipt 的 `response_content_sha256`，再通过
`object.__setattr__` 把 frozen 对象的 `frame` 替换为同列、同行数、同 scope、数值仍合法但 close/high 已改变
的 frame。四个 mapper 的公共 `_prepare` 当前只复查类型、endpoint、列和 scope，daily mapper 会成功输出
改变后的 `close=99.0`，而 receipt 仍声明旧内容摘要。

### 5.2 根因与应遵循规则

根因是把 dataclass 的一次 `__post_init__` 和 `frozen=True` 当成持续可信身份。frozen 只是普通 API 的防误改
机制，不是跨进程、反序列化或对抗调用边界的证据闭包。`Verified` 名称是信任承诺；每个公开 mapper 在读取
frame 行值前必须重新证明以下对象仍属于同一闭包：

- exact `VerifiedRawResponse` 类型；
- spec 的规范 request identity；
- receipt 与 spec 的 endpoint/request/parameters/fields/columns/row count 闭包；
- `receipt_sha256` 与规范 receipt bytes；
- frame 的 columns/row count/规范内容 digest 与 receipt 一致。

最小实现优先复用 `VerifiedRawResponse` 的生产验证边界：以当前 `spec/receipt/receipt_sha256/frame` 重建一个
新的 exact verified 值对象，并只消费重建成功的对象。不要在 mapper 再复制一套部分 hash 算法，也不要改
B2A 已通过的构造语义。重验失败统一转换为脱敏的 `M3G1MappingError("G1_MAPPER_RESPONSE_INVALID")`
并 `from None`；不得泄露底层异常、绝对路径、token、原始行或 receipt repr。

### 5.3 最小复现

```python
response = _make_verified("daily", _daily_frame())
changed = response.frame.with_columns(...)  # 保持列、行数、scope 和合法 OHLC，只改变内容
object.__setattr__(response, "frame", changed)
map_g1_daily_response(response=response)
```

修复前映射成功且输出改变值；修复后必须在任何行映射前以 `G1_MAPPER_RESPONSE_INVALID` 拒绝。

### 5.4 新增测试与通过条件

至少增加：

1. daily 的 frame 内容漂移但 shape/scope/值仍合法；
2. benchmark 或 suspension 至少一个 mapper 的同类 frame 漂移，证明四函数共用的消费边界有效；
3. 单独漂移 `receipt_sha256`；
4. 单独漂移 spec 或 receipt 中 request/parameters/content identity，且对象表面 endpoint/columns 仍可匹配；
5. 重验底层异常四观察面脱敏：`str/repr/__cause__/traceback`；
6. 合法对象仍只验一次生产闭包后正常映射，输出与现有测试一致。

通过条件：四个 mapper 都经同一生产重验路径；不得仅在各 mapper 的值校验后补 hash 比较，不得接受
duck type，不得新增网络、配置或 research 依赖。

## 6. 对首次实现与初验的反馈

首次实现构造的测试对象均是内部自洽的合法 `VerifiedRawResponse`，首次独立初验也只变换 frame 的业务值、
顺序与 scope，没有在构造成功后制造 identity drift；因此两者都把“构造时成立”误当成“消费时仍成立”。
readiness 初验则把手工列合同与 `_check_benchmark_invalid` 视为等价于 Schema，却没有测试 strict Schema 的
superset 反例。

以后验收 `Verified/Plan/Receipt/Snapshot` 一类对象，至少同时测试：正常构造失败、构造后身份漂移、以及
消费边界重验。验收严格 Schema 时，至少同时测试 missing、extra、dtype 和跨字段约束；required-column
subset 只能用于避免二次异常，不能代替 strict Schema。这两条规则已同步写回 G1 设计记录与实施 SSOT。

## 7. 独立复验最低要求

独立验收 Agent 不复用实现者新增的精确样例，至少新增以下变体：

1. readiness 只加一个非股票未知列，并把列放在中间而非末尾；
2. readiness 输入同时存在 extra column 与日期覆盖错误，确认两个独立问题可确定性报告；
3. mapper 漂移 frame 的物理 row order 但保持规范内容不变，确认不得把无关物理顺序误报为内容漂移；
4. mapper 漂移 frame 的一个值但保持输出 Schema 合法，必须因 receipt/content 不闭合拒绝；
5. mapper 漂移 receipt 的非 endpoint identity 字段，不能被现有 endpoint/columns 检查漏过；
6. 任一底层重验异常含路径和 secret marker，四观察面均无泄露。

独立报告逐项给出代码位置、测试名和运行结果。若发现新问题，只把影响基准正确性、raw/receipt 身份、单位、
前视、安全泄露或主链路可复现性的缺陷作为本轮阻断；无关格式和微小内部实现问题记录为 P2/P3 后延。
