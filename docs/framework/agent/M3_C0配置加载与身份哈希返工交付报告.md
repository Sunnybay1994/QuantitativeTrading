## 2. P1-1：异常链与 traceback 脱敏

- 现象：初版用 `raise M3ConfigError(...) from exc` 包装 I/O/TOML parser 异常，外层 `str/repr` 虽脱敏，
  但 formatted traceback 仍包含物理配置路径或输入片段。
- 根因：测试只覆盖外层错误文本，没有把 `__cause__/__context__` 和结构化日志常见的 formatted traceback
  纳入安全边界。
- 应遵循规则：公开配置边界不得保留含敏感路径/原值的底层异常对象；脱敏必须覆盖错误的全部常见呈现面。
- 最小复现：加载不存在的 `C0_PHYSICAL_PATH_SENTINEL.toml`，再调用
  `traceback.format_exception(error)`。
- 代码改动：`load_m3_config` 改为通过 `_read_config_bytes` 与 `_parse_toml` 私有边界把失败转换为 sentinel；
  私有边界内部吞掉原始 `OSError/UnicodeDecodeError/TOMLDecodeError`，公开函数在异常处理栈之外新建
  `M3ConfigError`，因此不保留含路径的 cause/context。
- 新增测试：分别对 I/O 与包含输入 sentinel 的 parse 失败断言 formatted traceback、`__cause__`、
  `__context__` 均不泄露。
- 通过条件：稳定保留 `CONFIG_IO_ERROR/TOML_PARSE_ERROR`，同时 traceback 不含物理路径、输入片段或
  底层异常链。

## 3. P1-2：percent-encoded quoted secret key

- 现象：初版 `%74oken` 只产生 `UNKNOWN_KEY`，没有同时产生 `SECRET_VALUE`。
- 根因：值扫描使用重复 percent-decode，键分类却只做 lowercase/hyphen normalization，两条安全管线分叉。
- 应遵循规则：安全分类顺序统一为“最多三层受控 percent-decode → case/hyphen normalization → 精确敏感
  集合匹配”；unknown key 必须先完成安全扫描。
- 最小复现：在完整 document 加入 `extra = {"%74oken": "plain"}` 后调用公开 canonicalizer。
- 代码改动：新增唯一 `_controlled_percent_decode`，键、值和路径扫描复用；`_is_sensitive_key` 在精确集合
  匹配前调用该 primitive，没有增加“长字符串/长 hex 即 secret”等宽泛启发式。
- 新增测试：`%74oken`、`%2574oken`、`api%2dkey`、`private%252dkey` 均同时产生 sanitized
  `SECRET_VALUE + UNKNOWN_KEY`；合法固定 dump SHA 仍可加载。
- 通过条件：单层/双层编码敏感键 fail-closed，错误只包含定位 path，不回显配置值且不误杀供应链 SHA。

## 4. P1-3：tracking direct helper 与 loader 同源安全域

- 现象：loader 会拒绝绝对路径形式的 `tracking.experiment_name`，但
  `canonical_tracking_target_key` 初版可直接接受并生成 key。
- 根因：公开 helper 手写了只覆盖 secret 的 name validator，没有复用 loader 的 path/control 安全检查。
- 应遵循规则：同一语义值经 loader 或 direct public helper 进入时，必须共享同一安全 primitive 和
  accept/reject 域。
- 最小复现：用合法相对 SQLite URI 和 `experiment_name="/tmp/m3-experiment"` 调用 direct helper。
- 代码改动：新增 `_validate_safe_string`，统一组合 secret/control/path 检查；loader 的递归扫描和 direct
  tracking helper 都调用它。
- 新增测试：POSIX absolute、Windows drive、UNC、普通反斜杠、percent-encoded absolute 和控制字符均成对
  比较 loader/direct 的 issue code 与 `tracking.experiment_name` path；合法 HTTP default-port alias 回归保留。
- 通过条件：两个入口的安全域一致，路径类变体为 `UNSAFE_PATH`，控制字符为 `SECRET_VALUE`，合法 URI
  规范化行为不变。

## 5. P2-1：严格校验先于 mapping key coercion

- 现象：direct document 的整数 key 被 `_thaw` 静默转换成字符串，错误从应有的 `TYPE_ERROR` 变成
  `UNKNOWN_KEY`，并可能与真实字符串 key 碰撞。
- 根因：递归复制函数在 validator 看到原始输入前执行 `str(key)`。
- 应遵循规则：strict validation 必须先于 normalize/coercion；只有已经证明为原生 `str` 的 key 才能进入
  规范化、冻结和 JSON 投影。
- 最小复现：完整 document 同时加入 key `1` 与 key `"1"` 后调用公开 canonicalizer。
- 代码改动：`_thaw` 原样保留 mapping key；`_iter_assignment_leaves` 在根层、嵌套 table 和费用 period
  先产生稳定 `TYPE_ERROR`；安全扫描对非法 key 使用固定占位 path 继续检查 child，不调用其 `repr/str`；
  `_normalize_scalars/_freeze/_json_value` 只在验证成功后使用类型 cast，不再执行字符串 coercion。
- 新增测试：根层、`data` 嵌套层和 `costs.a_share_periods[0]` 的非字符串 key 分别产生 `TYPE_ERROR`；整数
  `1` 与字符串 `"1"` 同时存在时，保留 `TYPE_ERROR config + UNKNOWN_KEY 1`，证明没有合并。
- 通过条件：所有 direct mapping key 必须原生 `str`，非法 key 在任何有损复制前失败，合法 TOML/hash 不变。
