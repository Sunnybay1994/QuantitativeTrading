## 2. P1-C：Schema 之前的依赖表达式可直接抛异常

### 2.1 现象

对合法 `_benchmark_bars()` 保持精确八列，只替换一个字段 dtype：

| 变体 | 当前结果 |
|---|---|
| `source=Int32` | `ComputeError: cannot compare string with numeric type` |
| `source=List[String]` | `InvalidOperationError: cannot cast List type ... to String` |
| `benchmark=Int32` | `ComputeError: cannot compare string with numeric type` |
| `benchmark=List[String]` | `InvalidOperationError: cannot cast List type ... to String` |

异常分别发生在 `benchmark_bars.filter(pl.col("source") == source)` 或
`pl.col("benchmark") != configured_benchmark`，调用方没有得到结构化 `ReadinessIssue`。

### 2.2 根因

一次返工虽然新增 `_check_benchmark_schema`，但调用顺序仍是：column gate → source filter/duplicate 等
Polars 操作 → Schema validate。也就是说，Schema 只验证了“已经能被依赖表达式处理”的输入，无法保护
真实消费边界。新增测试只把错误 dtype 放在 OHLC 列，未覆盖被前置表达式直接使用的 `source/benchmark`。

### 2.3 必须遵循的系统规则

1. required columns 齐全后，任何依赖字段值或 dtype 的 Polars filter/comparison/group/duplicate 操作之前，
   必须先经过生产 `BenchmarkBar1dSchema`。
2. 因 `BenchmarkBar1dSchema.Config.coerce=True`，后续只能消费 `validate(...)` **返回的已验证 DataFrame**；
   不能验证原表后继续操作原表，否则合法 coercion 后仍可能在旧 dtype 上崩溃。
3. extra columns 仍必须产生 `BENCHMARK_INVALID`。若需要继续收集日期覆盖，可先投影唯一
   `_REQUIRED_BENCHMARK_FIELDS`，对该投影执行同一生产 Schema，再只消费验证返回值；不能直接信任投影。
4. Schema 无法验证时返回稳定、脱敏的 `BENCHMARK_INVALID`，不得向外抛 Polars/Pandera 异常；缺必需列
   仍只走 `BENCHMARK_MISSING_FIELDS`，不得访问缺失列。
5. Schema 允许的 coercion 由代码 SSOT 决定，不另写 dtype 白名单。可 coercion 的输入使用返回的规范 frame
   继续 source/identity/coverage 检查；不可 coercion 的输入 fail-closed。

## 3. 最小实现边界

允许修改：

```text
src/quant/research/m3/readiness.py
tests/unit/test_m3_readiness.py
docs/M3_G1_P1主验二次返工交付报告.md
docs/M3_G1_P1主验二次返工独立复验报告.md
```

建议保持最小数据流：

```text
column gate
  -> required projection
  -> BenchmarkBar1dSchema.validate(projection)
  -> validated/coerced frame
  -> source selection / duplicate / identity / dense coverage
```

exact/extra 是结构诊断状态，不得与“投影已通过 Schema”混为一个布尔量。extra 表即使投影合法也仍保留
`BENCHMARK_INVALID`；投影通过只表示可以安全继续收集独立 issue。不要复制 Pandera 规则，不要用
`strict=False`/手工 cast/try-every-expression 方式逐点打补丁。

禁止修改 `m3_mappers.py`、`m3_backfill.py`、领域 Schema、B2A/B2C/B3/B4、路线图与无关测试。若发现必须
改变 `BenchmarkBar1dSchema` 才能完成，停止实现并提交证据，由主 Agent 重新审核 SSOT。

## 4. 实现 Agent 必测矩阵

至少新增以下生产回归：

1. exact columns，`source=List[String]`：不抛异常，包含 `BENCHMARK_INVALID`；
2. exact columns，`benchmark=List[String]`：不抛异常，包含 `BENCHMARK_INVALID`；
3. exact columns，`source=Int32`：不论 Schema 按当前 Config coercion 还是拒绝，都不得抛底层异常；若
   coercion 成字符串后与配置不匹配，应按既有 source 语义报告；
4. exact columns，`benchmark=Int32`：不抛异常，并按生产 Schema/identity 语义 fail-closed；
5. extra unknown column + `source` 不可 coercion：仍不抛异常，且至少包含 `BENCHMARK_INVALID`；
6. extra unknown column + 合法 required projection + 缺交易日：继续同时报告
   `BENCHMARK_INVALID` 与 `BENCHMARK_DATE_COVERAGE`；
7. 可 coercion 的精确输入必须证明下游消费的是 Schema 返回 frame，而不是原 frame；
8. Schema 异常包含绝对路径/疑似 token 时，issue message、异常 cause、repr/traceback 不泄露；
9. 精确合法基准、foreign source、重复键、错误 benchmark、空表与原 55 项全部不退化。

## 5. 独立验收 Agent 要求

独立验收 Agent 必须未参与本轮编码，并使用不同于实现者的 dtype/值组合。至少新增：

1. `source=List[Int64]` 与 `benchmark=Struct` 两种 exact-column 变体；
2. extra 列位于中间，同时 required `source` dtype 非法；
3. monkeypatch `BenchmarkBar1dSchema.validate` 返回一份 source 已规范化、与输入 dtype 不同的 frame，证明
   后续确实使用返回值；
4. Schema validator 抛含 secret/path 的 Polars 或普通异常，四观察面无泄露；
5. extra+coverage 双码与 mapper identity 原主验反例继续通过，防止修 readiness 时误伤已关闭合同。

发现失败时回到实现 Agent 迭代，直到独立复验通过。报告必须逐项写明测试、源码证据和结果；不得只引用
全量绿测。独立通过时只声明“G1-P1 主验二次返工外部闭环通过，可交主 Agent 终验”。
