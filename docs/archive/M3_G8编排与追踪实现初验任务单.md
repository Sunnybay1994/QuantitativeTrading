## 1. 边界

本任务只实现显式 DAG、CLI、恢复、MLflow 幂等登记和冷启动复现编排，不在编排器内重写标签、Qlib、
LightGBM、策略或账户算法。实现 Agent 遇到缺失 stage handler 时应保留明确接口并报告前置未完成，不能
放假产物、跳 stage 或写空 complete receipt。

采用主任务书 → 实现自测 → 独立初验 → 主终验。不得读取 `_old/`，不得调用真实券商；默认单测不联网，
不得输出 token 或本机绝对路径。

## 2. O1：内容寻址身份与五段 continuation RunPlan

新增：

- `src/quant/research/m3/orchestration.py`

实现 SSOT 的 `StageSpec`、`StageNode`、`RunPlan`、`StageFailure`、`RunSummary`、
`build_snapshot_plan/build_provider_plan/build_experiment_plan/build_work_plan/build_summary_plan`。身份函数复用 E3
`compute_experiment_key/compute_work_key`，不得复制 hash 逻辑。E3 在实现前须按 SSOT 新接口改为
`receipt_path + artifact_roots/root_alias`；不得先实现旧的单 `artifact_root` 接口再由 G8 打补丁。
provider identity 必须复用 E3 同包新增的 `compute_provider_key`。
现有 E3 首次交付还没有 receipt version、严格字段/duplicate-key、`ACCEPTANCE` scope 和 root 内 symlink
拒绝，必须先按 [`M3_E3严格Receipt增量返工任务单.md`](../framework/agent/M3_E3严格Receipt增量返工任务单.md) 关闭；G8
不得在 StageRunner 中维护另一套宽松 parser。

要求：

- snapshot、provider、experiment、work 目录严格分离；snapshot 未验真前不得计算 provider/experiment key。
- 第一段使用 `snapshot_request_key` 在 build 目录产出 staging，只有 manifest 验真后才得到内容寻址
  `snapshot_id`；原子发布 snapshot 和不可变 request→snapshot 映射。不得用配置 hash 冒充 snapshot ID。
- 第二段只接收已验真的 snapshot 并发布 provider，再以独立 validation key 发布 provider validation；第三段
  先验证 provider-validation PASS，再只以 snapshot/provider receipts 与科学身份发布 experiment identity，
  随后发布 labels、显式绑定 validation receipt 的 G3 reconciliation 和 folds shared evidence；第四段只有在
  folds receipt 验真后才能读取 `folds.json` 并枚举 work。
  第四段每 fold 先生成一个 experiment-scoped FeatureBundle，再让 h=5/h=10 work 分别从 alignment 开始；
  第五段只在所需 evaluation receipts 完整后构造 horizon research summary。各段自身静态，边界值只能
  来自明确 receipt/manifest，禁止扫描目录猜测或在 plan builder 中调用 handler。
- 静态 stage registry 与 SSOT 产物矩阵逐项一致；`StageNode.node_id` 唯一、依赖图无环、输出
  `(root_alias,path)` 无冲突。stage 类型名可复用，执行实例不能靠模糊 stage 名寻址。
- 目录型 output 只允许写入 plan 指定的 stage 临时目录；发布时展开为 receipt 中的逐文件 digest，拒绝
  符号链接和目录外文件。不得把 `provider.complete.json` 列为 provider 自身输出形成自引用。
- folds 按 name、horizon 按数值稳定排序；重复 fold/horizon、未知 stage、缺依赖或空 horizons 失败。
- scientific config hash 严格使用 SSOT 4.9 的唯一 allowlist；任务书不维护第二份键清单。配置解析器必须
  拒绝 allowlist 子树内的未知键、缺失必需键和错误类型。
- snapshot config hash 使用更窄 allowlist；provider 另有 `provider_key`。改变 tracking URI 不改变任何
  identity，改变成本只改变 experiment/work，改变 provider 字段、Qlib 版本或 dump tool hash 只改变
  provider/experiment，不改变 snapshot；改变 staging 字段/映射才改变 snapshot request/content。
- readiness 同时发布 provider runtime subset 与完整 dependency fingerprint。Python、NumPy、pandas、
  PyArrow、Qlib、Fire、tqdm、Loguru 任一变化必须改变 provider 和 experiment；Polars/SciPy/scikit-learn/
  LightGBM 等只参与完整指纹，改变 experiment/work 而不改变 provider；两类都不伪造 snapshot。
- validation config 不进入 snapshot/provider/experiment。`validation.provider` 和 `validation.labels` 分别通过
  provider-validation 与 label-reconciliation key 失效各自旧证据；二者不得使用一个总 hash 制造无关
  失效。experiment/features 的计划执行以 provider-validation PASS 为前置，但其内容 receipt 不列该 validation
  receipt；label-reconciliation 必须绑定它，避免 validation 变化在不变路径制造 receipt 冲突。
- provider plan 显式接收 E3 计算的 provider-validation key；Stage registry 按 SSOT required-input 矩阵注入
  `CONFIG/G1_RELEASE/EXTERNAL_QLIB` 等只读 roots，handler 不扫描或隐藏读取。

至少覆盖此前矛盾反例：同一 snapshot 有 3 folds×2 horizons 时只有一个 experiment key、六个不同 work
key；不能让 fold/horizon 同时进入 experiment key 又在其下枚举。另覆盖 snapshot 尚未生成时不能要求
真实 snapshot ID，以及重复 stage 类型的六组 node 仍有唯一 node_id/receipt path。

## 3. O2：可恢复 StageRunner 与 CLI

新增/修改：

- `src/quant/research/m3/orchestration.py`
- `src/quant/research/run_m3.py`
- `tests/unit/test_m3_stage_runner.py`
- `tests/unit/test_run_m3_cli.py`

`execute_m3_plan` 通过显式注入的 stage handler registry 执行。handler 只能收到声明的 root alias、
input/output path 和本 stage 临时目录；
不得让 handler 自行扫描 artifact tree。每步流程固定为：验证依赖 receipt → 验证/复用本 stage receipt →
临时目录计算 → Schema/业务验真 → 原子发布产物 → 最后发布 receipt。

恢复规则：

- receipt 完整且 hash 全对：标记 reused，不再调用 handler。
- receipt 不存在：允许清理本 stage 自己的临时文件后计算；不得清理其他 stage。
- receipt 不存在但正式输出已存在：重算到临时目录，逐字节相同才允许认领 orphan 并补发 receipt；内容
  不同立即失败。此规则覆盖“产物 rename 成功、receipt 写入前进程崩溃”的窗口。
- receipt 存在但非法、产物缺失/hash 不符：失败，不自动覆盖。
- folds/provider 等全局 shared stage 失败：不启动依赖 work；某 `labels[h]` 失败只阻止该 horizon；某
  `features[fold]` 失败只阻止该 fold 的两个 horizon；单个
  work 失败跳过该 work 下游，继续其他 work。
- `resume=true` 为默认；`--no-resume` 遇到已完成 stage 也不得删除，只能明确失败或写全新 identity。

本任务实现 SSOT 4.9 命令表中 acceptance-audit 之前的七个执行子命令；第八个最终验收命令属于 G9。
identity 参数、依赖闭包、停止 stage、stdout/stderr 和退出码不在实现中维护第二份映射。第三方库
warning 不得污染 stdout；参数/配置错误不得产生 stage 产物。

错误 JSON 只含稳定 code、scope、stage、fold/horizon 和脱敏 message，不含 traceback、token、客户端 repr
或绝对路径。debug traceback 只能写本地脱敏日志且不得作为 MLflow artifact 自动上传。

## 4. O3：MLflow tracking journal 与幂等恢复

修改/新增：

- `src/quant/research/m3/tracking.py`
- `tests/unit/test_m3_tracking_recovery.py`

保留 `log_m3_run` 作为低层一次登记函数，新增：

```python
@dataclass(frozen=True)
class TrackingMarker:
    tracking_target_key: str
    tracking_key: str
    request_sha256: str
    mlflow_run_id: str
    artifact_digest_sha256: str

def compute_tracking_key(*, work_key: str, request_sha256: str) -> str: ...

def register_m3_work(
    *, work_dir: Path, tracking_uri: str, experiment_name: str,
    work_key: str, params: Mapping[str, object], metrics: Mapping[str, float],
    artifacts: Sequence[Path], tags: Mapping[str, str],
) -> TrackingMarker: ...
```

`request.json` 明确列出过滤后的 params/tags/metrics 和全部上游本地 artifact digest；request 与
marker 自身不进入该列表，避免自引用。先原子发布
request。文件位于 `tracking/target=<tracking_target_key>/`，target key 是规范 tracking URI 与 experiment
name 的 hash，request/marker 只保存 hash，不保存 URI 或凭据；切换 server 产生新登记目录但不改变科学
identity。其 request hash 与 work key 形成 tracking key；随后查询 MLflow 中同 experiment
且 `tags.quant_tracking_key` 精确匹配的 run：0 个则创建，1 个且 request/artifact hash 完全一致则复用，
但只有 `FINISHED` run 可恢复；单个 `RUNNING/FAILED/KILLED`、多于 1 个或不一致均失败，且不得以同一
tracking key 新建第二个 run。最后原子发布 marker。模拟“MLflow 成功、marker 前崩溃”时重跑必须恢复同一
run ID，不创建第二个 run。fake MLflow 覆盖 0/1/2 匹配、FAILED/RUNNING/FINISHED 状态、artifact 缺失、
marker 冲突和 secret/绝对路径递归拒绝。

target key 必须直接调用 C0 `canonical_tracking_target_key`；tracking key 必须调用上面的具名函数并使用
规范 JSON 数组，禁止字符串拼接。加入 `("ab","c")` 与 `("a","bc")` 不碰撞、HTTP host 大小写/默认端口
得到相同 target key 的回归。

新建 remote run 的首个 API 调用必须携带 `quant_tracking_key` 初始 tag；禁止先 start 再 set tag。登记期间
以 WSL `flock` 对 target+tracking key 做单机互斥；测试双进程并发最终只有一个 remote run。上传 artifact
必须保留相对目录层级，不能把同名 `metrics.json` 扁平化覆盖。跨主机并发不属于 M3 保证范围，报告披露。

## 5. O4：冷启动可复现编排

新增：

- `src/quant/research/m3/reproducibility.py`
- `tests/unit/test_m3_reproducibility.py`

`verify-reproducibility` 生成稳定 comparison key，由父进程顺序启动两个全新的 WSL Miniforge base Python
子进程，在隔离 attempt 目录运行两次 train→predictions→evaluation。comparison key 包含 work key、
feature/label receipts、模型参数、code/dependency fingerprints 和两个 tolerance。
允许只读复用已验真的 snapshot/provider/features/labels，禁止读取正常 work 或另一 attempt 的 model、metadata、
predictions、metrics、receipt。两个 attempt 使用独立 cache/temp 目录和确定性环境；父控制器实时验证子进程
与父进程不同且两个 attempt 分别启动，但 PID 不写入稳定产物；通过 worker protocol、独立 receipt 与子进程
读路径审计证明隔离。

REPRO required outputs 严格使用 SSOT 稳定矩阵：两个 attempt 均保留 model/metadata、predictions/manifest、
daily IC、metrics 和 `read_audit.json`，根发布 `reproducibility.json`。模型或 Parquet 字节可以不同；行键、
score 与 metrics 按容差比较。任一 output 缺失都不得发布 comparison receipt。

比较要求：prediction 行键完全一致；score 最大绝对差不超过配置 `reproducibility_score_atol`；metrics
键集合一致且逐值不超过 `reproducibility_metric_atol`。NaN 只允许在双方同一已声明不可计算指标位置；
一侧 NaN 或新增/缺失指标失败。成功后发布 `reproducibility.json` 与 comparison receipt；缓存复用、同一
model 文件复制两份或只比较 hash 都不能作为冷启动证据。

## 6. O5：fake DAG 集成验收

新增 `tests/integration/test_m3_orchestration.py`，不要求安装 Qlib/LightGBM/MLflow。使用严格 fake handlers
跑 2 folds×2 horizons，验证：

1. shared stages 各执行一次，四个 work 各自独立；
2. fold_001/h=5 在 predictions 失败，其他三个 work 完成，失败 work 不出现下游 receipt；
3. 二次 resume 只重跑失败 work 的未完成 stage，已完成 handler 调用次数不增加；
4. 任一已完成 artifact 被篡改后 fail-closed，不重算覆盖；
5. 修改 tracking URI identity 不变；修改成本或 LightGBM 只产生新 experiment；修改 NumPy/pandas/Qlib
   runtime、provider 字段或 dump tool 产生新 provider 与 experiment、snapshot 不变；修改 provider 抽样
   产生新 provider-validation、reconciliation 与 acceptance，但 experiment/work 不变；修改 label 容差只
   产生新 reconciliation/acceptance；修改 staging 字段/映射才产生新 snapshot；
6. JSON summary 排序稳定且不泄露工作区路径或 secret。
7. 只有 snapshot receipt 后才能建 provider plan，只有 provider receipt 后才能建 experiment plan，只有
   folds receipt 后才能建 work plan；plan builder 本身不调用 handler。
8. receipt 即使自报 hash 合法，只要漏 required output、scope/scope_key 不符或多读未声明路径也失败。
9. 2 folds×2 horizons 只执行两个 Alpha158 feature nodes；同 fold 两 work 共享 feature receipt，alignment
   各自独立；summary 只在相应 horizon 的 evaluation receipts 完整且日期不重叠时运行。
10. receipt JSON duplicate key/未知字段/未知版本失败；任何 symlink 即使指向同 root 内普通文件也失败。
11. provider validation 未发布或 receipt 与 provider key 不匹配时不得建立 experiment plan；Qlib worker
    必须是 fresh 子进程，父进程不得因连续 provider 运行复用 `qlib.init` 全局状态。
