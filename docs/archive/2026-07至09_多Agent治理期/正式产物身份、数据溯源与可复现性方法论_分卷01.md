# 正式产物身份、数据溯源与可复现性方法论

> 文档目的：解释本项目为什么把配置、数据、代码语义、阶段产物、`manifest`、`receipt` 和验证器绑定为一条可复核的身份链；说明其理论来源、在项目中的实际应用、能力边界和成本。
>
> 本文是方法论说明，不替代 [`AGENTS.md`](../../../AGENTS.md)、[`项目实施路线图.md`](../../../项目实施路线图.md)、[`A股港股通个人量化投研交易系统调研.md`]（历史路径 `A股港股通个人量化投研交易系统调研.md`，当前仓库未收录） 以及 `configs/`、Schema 和源码中的权威业务契约。

## 1. 结论先行

本项目采用的方法并非某一篇论文规定的固定实现，而是四类成熟思想的工程化组合：

1. **数据与计算溯源（provenance）**：一个结果应能说明由哪些输入、通过什么活动、在什么条件下生成。
2. **内容寻址与供应链完整性**：产物摘要必须绑定实际内容及其生成链，消费前应把产物与其溯源声明一起验证。
3. **机器学习可复现性**：代码、数据、配置、随机性和运行环境变化都可能改变研究结论，必须被记录和区分。
4. **金融模型风险治理**：模型不仅要开发正确，还要有验证、变更管理、使用边界、持续监控和审计证据。

本项目据此形成如下核心原则：

> **结果不是一个孤立文件，而是“结果内容 + 科学配置 + 上游数据和产物 + 生成规则 + 验证证据”的整体。下游使用前，必须确认自己拿到的仍是这个整体。**

它解决的主要不是“文件能否打开”，而是更危险的问题：

- 数据更新了，但旧模型仍被标成新数据训练；
- CPU 与 GPU 训练配置发生变化，却继续沿用同一个模型身份；
- target 文件内容没变，但它引用的预测或股票池已经漂移；
- 手工修改一个 JSON 后重新计算局部 hash，试图冒充完整合法发布；
- 下游把另一次实验、另一个账户或另一个回测窗口的文件混入当前结果；
- 文件在验证后被替换，后续逻辑仍把它当成刚才验证过的对象。

## 2. 理论来源

### 2.1 W3C PROV：结果、活动和派生关系

W3C 的 PROV-DM 把溯源描述为与数据或事物的生产有关的实体、活动和责任主体信息，并指出这些信息可用于判断质量、可靠性和可信度。其核心关系包括：活动使用实体、活动生成实体，以及一个实体由另一个实体派生。

映射到本项目：

- raw/clean 数据、配置、模型、预测、target、回测结果是 **Entity（实体）**；
- 清洗、特征计算、训练、预测、组合构建、回测是 **Activity（活动）**；
- `manifest` 和 `receipt` 记录 `used / wasGeneratedBy / wasDerivedFrom` 一类关系；
- 一组阶段性 `receipt` 构成“溯源本身的溯源”，对应 PROV 的 bundle 思想。

因此，本项目的产物链本质上是一个领域化的**溯源有向无环图**。它在结构上类似内容寻址的 Merkle DAG，但我们没有宣称实现了一套通用 Merkle 数据库或完整 W3C PROV 序列化格式。

### 2.2 SLSA 与 in-toto：产物必须连同生成链一起验证

SLSA 把 provenance 定义为可以把产物沿复杂供应链追溯到来源的可验证信息，即说明产物在何处、何时、如何生成。其验证建议包括：

- 产物摘要与 provenance 中的 subject 相符；
- 生成类型和外部参数符合预期；
- 不认识的外部参数应默认拒绝；
- 必要时递归验证依赖；
- provenance 只有被实际检查才有价值。

in-toto 的论文把软件供应链描述为多个独立步骤和参与者组成的过程，并通过每一步的材料、产品和验证规则，检查从源头到最终交付的完整链条。

映射到本项目：

| 供应链概念 | 本项目对应物 |
|---|---|
| materials / inputs | G1 数据发布、配置、fold、feature、label、model、prediction、target 等上游 |
| products / subjects | 当前阶段实际生成的 Parquet、JSON、SQLite 或目录树 |
| attestation / provenance | `manifest`、阶段 `receipt`、输入输出摘要集合 |
| expected parameters | Schema 版本、科学配置、窗口、市场规则、费用版本、账户和运行环境身份 |
| verifier | `verify_*`、fresh verifier、StageRunner 的发布前后 closure |
| trusted consumption | 只把验证成功后签发的 `Verified*` 对象交给正式下游 |

这说明“使用前验真”并不是本项目独有的偏好，而是供应链完整性领域的基本原则。

### 2.3 机器学习可复现性：相同名称不等于相同实验

Pineau 等人在 JMLR 的机器学习可复现性报告中，把使用相同代码和数据获得相近结果视为可复现性的重要形式，并讨论了代码、数据、实验细节和工作流透明度对可靠性的作用。

量化研究比普通 ML 更容易出现隐性漂移，因为结果还依赖：

- Point-in-Time 数据可知性；
- 当时有效的成分股、停牌、涨跌停和公司行动；
- 信号日与最早成交日；
- 训练 fold、标签窗口和预测窗口；
- 交易费用、整手、T+1 和撮合规则；
- 随机种子、LightGBM 参数、CPU/GPU backend 和线程策略。

因此，“配置只改一行”可能确实形成另一个实验。合理做法不是禁止修改，而是：

1. 为新配置生成新的版本化身份；
2. 保留旧配置和旧产物的合法历史；
3. 禁止新旧链条互相冒充；
4. 用对照实验决定新版本能否晋升为正式 profile。

### 2.4 金融模型风险治理：验证、变更管理和使用边界

美国联邦储备系统、OCC 和 FDIC 的模型风险管理指导强调，模型可能因根本错误或不当使用造成损失，需要与风险相称的模型开发、实施、验证、治理和控制。2026 年发布的 SR 26-2 更新并取代了历史上的 SR 11-7，同时继续强调风险导向和适合机构规模、复杂度的治理方式。

本项目不是受该美国银行监管文件直接约束的机构，也不声称符合某项监管认证。但这些原则对量化系统仍具有方法论价值：

- 明确模型目的和适用边界；
- 区分开发结果与正式可消费结果；
- 对数据、假设、配置和实现变化做版本管理；
- 由独立证据验证关键模型与运行链；
- 失败时 fail closed，而不是带着未知状态继续生成订单。

## 3. 本项目中的整体模型

### 3.1 三层对象

本项目把一个阶段的结果拆成三层：

1. **业务内容**：Parquet、JSON、模型文件、数据库状态等。
2. **声明与溯源**：`manifest` 描述内容、Schema、参数和上游身份；`receipt` 描述一次阶段执行精确使用了什么、产生了什么。
3. **经验证的消费权限**：`Verified*` 对象表示“当前进程已经按正式规则验证过这组内容”，正式下游只接受这种窄类型。

可以概括为：

```text
数据/配置/代码语义
        │
        ▼
  阶段构建活动 ──────► 业务文件
        │                 │
        ├──────────────► manifest
        └──────────────► receipt
                          │
                          ▼
                fresh verifier 验证
                          │
                          ▼
                    Verified* 对象
                          │
                          ▼
                       下游阶段
```

### 3.2 典型 M3 研究与回测链

当前 M3 的主要身份链可以抽象为：

```text
科学配置 + 正式 G1 数据发布
            ↓
snapshot / provider / fold
            ↓
feature + label + alignment
            ↓
model
            ↓
prediction
            ↓
target weights
            ↓
backtest plan
            ↓
0.5x / 1.0x / 2.0x 三场景回测 bundle
```

任何会改变下游科学结论的上游输入，都应进入相应阶段的 identity。例如：

- LightGBM 从 CPU profile 改为 GPU profile：模型及其下游身份变化；
- 只更新 broker 运行配置：不应让无关的 G1 数据身份变化；
- 修订某日公司行动：受影响的 market facts、账户回放和回测结果变化；
- 只修改不参与计算的说明文字：不应为了“看起来严格”而污染科学身份。

这也是“身份覆盖范围”必须精确而不能无限扩张的原因。

### 3.3 典型 M4 纸面交易链

M4 侧采用相同思想，但关注点从研究可复现性转向运行授权和账户一致性：

```text
formal runtime environment
        ↓
execution policy
        ↓
broker-policy binding
        ↓
formal paper account
        ↓
durable broker store / snapshot / gateway
```

这里的 identity 用于防止：

- development policy 被替换字段后冒充 formal policy；
- 一个账户的 store 被另一个账户或 session 消费；
- runtime 配置已经物化变化，却继续使用旧的 cold capability；
- caller 自报路径、账号、scope 或 hash 来越过正式 loader。

## 4. `manifest`、`receipt`、hash 和 fresh verifier 各自负责什么

### 4.1 `manifest`：这一包东西“是什么”

典型 `manifest` 应说明：

- Schema 和产物版本；
- 业务窗口、证券域、折次或场景；
- 精确文件集合、行数、列或内容摘要；
- 会影响结论的配置摘要；
- 直接上游产物身份；
- 本阶段关键语义版本。

它相当于产物的结构化说明书和物料清单。

### 4.2 `receipt`：这一次活动“用了什么、产生了什么”

`receipt` 绑定：

- 阶段类型和 scope；
- 精确输入路径及字节摘要；
- 精确输出路径及字节摘要；
- 执行和发布闭包所需的身份。

它不是普通日志。日志主要用于观察过程；receipt 是可机器验证的阶段证据。

### 4.3 SHA-256：检测内容变化，而不是证明作者身份

规范化后的内容摘要提供：

- 同样内容得到同样摘要；
- 任一受绑定字节变化会导致摘要变化；
- 下游可以不依赖文件名判断内容是否仍相同；
- 多阶段摘要可组成可递归核对的身份链。

但必须明确：

- hash 本身不是数字签名；
- 攻击者若能同时改文件和声明并重新计算 hash，单纯 hash 无法证明是谁发布的；
- 真正对抗恶意发布者还需要签名、可信密钥、可信构建平台或外部透明日志等信任根。

因此，本项目目前更准确的表述是：具有较强的**内容一致性、来源闭包和本地发布安全**，但不能据此宣称达到某个 SLSA 等级或具备完整 PKI 供应链认证。

### 4.4 fresh verifier：防止“曾经验证过”被误当成“现在仍有效”

只在构建完成时验一次不够。下游消费前还需要：

1. 检查输入是精确正式类型，而不是 dict、subclass 或 development 对象；
2. 重新读取实际文件并计算摘要；
3. 重新验证直接上游，必要时递归到更上游；
4. 从当前实际内容重建预期 `manifest`；
5. 将预期值与声明值逐字段比较；
6. 验证 `receipt` 的精确输入输出集合；
7. 检查 root、文件身份和 no-clobber 条件，防止验证期间被替换；
8. 成功后才签发当前进程可消费的 `Verified*` 对象。

这对应 SLSA 所说的“provenance 若无人检查就不起作用”，也是本项目“fresh”一词的含义。

## 5. 为什么改一行配置会导致部分身份变化

假设 CPU 正式 profile 包含：

```toml
device_type = "cpu"
num_threads = 4
```

现在新增 GPU profile：

```toml
device_type = "gpu"
```

如果 `device_type` 会影响训练，则它属于科学配置。配置规范化摘要变化后，依赖它的模型身份应变化，并向下传播到 prediction、target、plan 和回测 bundle。

这里应精确理解为：

- **不是整个仓库所有正式产物都失效**；与该配置无关的 raw/G1 数据等通常不变。
- **旧 CPU 产物也不是被删除或判定错误**；它仍是 CPU v1 链下的合法历史产物。
- **不能把旧产物当作新 GPU 链的结果**；两套实验必须有不同身份。
- 如果证明 CPU/GPU 在冻结容差和业务指标上等价，也应通过明确的版本晋升或兼容规则表达，而不是偷偷复用旧 identity。

这与源代码版本管理相似：一次新提交不会否定旧提交存在，但新旧提交不能共用同一个 commit identity。

## 6. 哪些做法来自通用标准，哪些是本项目加严

| 做法 | 性质 | 说明 |
|---|---|---|
| 显式记录输入、输出、活动和派生关系 | 通用溯源原则 | W3C PROV |
| 产物摘要与 provenance/attestation 绑定 | 通用供应链原则 | SLSA、in-toto |
| 固定代码、数据、配置和环境以复现结果 | 通用 ML 研究原则 | 可复现性研究与工程实践 |
| 模型验证、变更管理和使用限制 | 通用金融模型治理原则 | 监管指导与行业实践 |
| 每阶段精确文件集合和严格 receipt | 项目领域化实现 | 比一般实验日志更严格 |
| 正式与 development 使用不同 exact type | 项目加严 | 防止松散对象越过正式边界 |
| process-local `Verified*` capability | 项目加严 | 把“已验证”变成窄消费权限，而非可自报布尔值 |
| 消费时递归 fresh 验真 | 项目加严 | 提高防漂移能力，但计算成本较高 |
| no-follow、文件/root物理身份、no-clobber 发布 | 项目加严 | 处理本地文件替换、链接和并发发布风险 |
| 所有异常稳定码、脱敏且 fail closed | 交易安全加严 | 避免未知状态继续进入订单路径 |

这些项目加严措施是合理的，但不应被视为永远不可优化。优化的正确方向是：

- 在同一次可信调用内安全复用已验证结果；
- 并行执行互相独立的场景；
- 避免重复扫描相同不可变字节；
- 使用有生命周期和身份约束的缓存；
- 保持串行与优化路径的输出、manifest 和 receipt 等价。

错误方向则是删除上游身份、跳过 fresh 验真，或让 caller 自报 hash 来换取速度。

## 7. 方法的能力边界

### 7.1 能较好解决

- 无意配置漂移；
- 文件损坏、漏文件、多文件或路径混配；
- 新旧实验、账户、窗口或场景串包；
- 构建和消费之间的本地文件替换；
- 无法复述“这个结果怎么来的”；
- 旧产物在新配置下被误用；
- 开发对象冒充正式能力。

### 7.2 不能单独解决

- 数据源本身提供了逻辑错误但格式完全合法的数据；
- 模型假设本身不合理；
- 同时控制代码、产物和声明的恶意内部人员；
- 没有可信签名时的发布者真实性；
- 训练算法的全部非确定性；
- 未来市场制度变化导致旧模型不再适用；
- “验证通过”但策略经济价值很差。

因此还需要数据质量门禁、PIT 审计、独立模型验证、经济指标、压力测试、纸面交易和持续监控。身份链证明的是“它确实是所声明的那一次计算”，不证明“这次计算一定赚钱”。

## 8. 成本与风险比例原则

严格溯源会增加：

- 计算与 I/O；
- Schema、manifest 和 receipt 的维护成本；
- 变更时的身份迁移工作；
- 长链 fresh verification 的运行时间；
- 测试矩阵和跨平台复杂度。

所以不应把所有临时探索都升级为正式产物。合理分层是：

1. **探索层**：快速试验，允许较轻记录，但不得进入交易或正式结论。
2. **development artifact**：可重复、可检查，适合工程联调，但不宣称正式 Gate。
3. **formal artifact**：输入闭包、不可变发布、fresh verification、稳定失败语义均满足后才签发。
4. **交易运行能力**：除 formal 数据与策略外，还需账户、风控、Gateway、对账和人工开关。

控制强度应与错误代价相称。研究草稿不需要银行级流程；会影响资金和自动下单的链路则值得加严。

## 9. 对本项目后续工作的直接指导

### 9.1 CPU/GPU 优化

- 保留 `alpha158_lgb_cpu_v1` 作为审计基线；
- 把 GPU 建成新的版本化候选 profile，而非原地修改旧配置；
- 在同一 fold 比较耗时、显存、CPU、验证损失、RankIC、排序和重复训练稳定性；
- 只有证据满足约定后，才把 GPU profile 晋升为正式路径；
- GPU 只加速适合它的训练部分，不虚构 Decimal 账户回放、公司行动和 hash 验真可由 GPU 普遍加速。

### 9.2 性能优化

- 先剖析真实热点；
- 优先消除同一可信调用内的重复验真和重复读盘；
- 对三个成本场景做资源受限并行，同时为其他工作保留 CPU 和内存；
- 发布、receipt 和最终提交保持串行；
- 用串行/并行输出 identity 等价证明优化没有改变科学结果。

### 9.3 正式数据与纸面交易

- 数据 source、发布日期、请求参数和修订必须进入来源闭包；
- 账户、策略、runtime、broker policy、store 不能只靠同名字符串关联；
- 开仓、成交、公司行动和对账分别保留经济事件身份；
- 缺少权威数据或账户语义时停止，而不是猜一个默认值完成“形式闭环”。

## 10. 推荐阅读顺序

1. 先读 W3C PROV-DM 摘要和第 2 节，理解 Entity、Activity、Derivation。
2. 再读 SLSA Provenance 与 Verifying Artifacts，理解产物摘要、参数预期和消费前验证。
3. 阅读 in-toto 论文摘要和体系结构，理解多阶段材料—产品链。
4. 阅读 JMLR 可复现性报告，理解 ML 实验为何不能只保存最终模型。
5. 最后阅读金融模型风险指导，把技术溯源放入验证、治理和使用边界中理解。

## 12. 一句话总结

本项目的方法论可以归结为：

> **用溯源图说明结果从哪里来，用内容摘要识别实际字节，用 manifest 表达产物含义，用 receipt 证明阶段输入输出，用 fresh verifier 在消费时重新核对整条链，再用版本化身份让不同实验可以共存但不能互相冒充。**

这套方法不能保证策略盈利，却能显著降低“结果看起来一样、实际来源已经变了”以及“系统不知道自己正在使用什么”的风险。

## 13. 轻量级量化系统的实施取舍建议

### 13.1 结论

对于个人、日频、单账户的量化投研和交易框架，本方法论不应被理解为“每一次研究都必须走完整 formal artifact 链”。严格身份链对策略 Alpha、收益或夏普没有直接增益；它主要提升的是结果可信度、变更可解释性和错误产物进入交易链的防护能力。

因此，项目可以并且应当先采用轻量路径快速验证策略经济价值；但不应以“轻量化”为理由绕开时间语义、数据质量、真实撮合约束和交易安全控制。身份链只能证明“它确实是所声明的那次计算”，不能修复错误数据、后视偏差、过拟合或没有经济价值的策略。
