# M4 P8 R1：稳定性与故障演练独立复验报告

日期：2026-08-09  
角色：未参与实现的独立初验 Agent  
结论：**FAIL**

## 结论摘要

P8 R1 的 development/formal 类型隔离、append-only 目录检查、故障经济闭包计算、稳定错误码及现有回归均可复现；
但是 formal `PAPER_REAL_TIME` Gate 没有建立“真实自然时间”和 P5/P7 原始证据的可信闭包。独立反例在一个
进程内用调用方提供的历史/未来时间与 fixture 完成 2 个 session、10 个强制 drill，随后通过公开
`build -> append -> verify -> decide` 路径直接得到正式 `PASS`。这与冻结任务单“fake clock、回放、
development example 和一次长测均不得冒充”直接冲突，因此不得进入主验或启动正式 28 日 soak。

## 阻断问题 1：调用方自报时间可在单进程内伪造 formal 28 日证据

### 现象

`build_soak_run(..., started_at=...)`、`append_soak_session(...,
invocation_started_at=..., invocation_completed_at=...)`、`append_fault_drill(...,
started_at=..., completed_at=...)` 与 `decide_soak_gate(..., as_of=...)` 的所有时间均来自调用方。
`decide_soak_gate` 只检查 receipt 时间彼此单调、`last <= as_of` 及 `last - first >= 28 days`，没有可信时钟、
真实调度 receipt、跨自然日写入证明或 formal 专用不可注入时间源。

独立最小复现使用系统临时目录、零网络与项目 fixture：

- formal manifest：`PAPER_REAL_TIME`，`started_at=2026-08-01`；
- 调用方自选 expected sessions：`2026-08-03`、`2026-09-01`；
- 同一进程立即 append 两个 session 和 exact 10 个强制 fault drill；
- `as_of=2026-09-02` 后调用 `verify_soak_evidence` 与 `decide_soak_gate`。

实际输出：

```text
FORMAL_SAME_PROCESS_STATUS=PASS
SESSIONS=2 FAULTS=10
SPAN_DAYS=29
```

### 根因

formal 与 development 仅由枚举/类型和目录后缀区分；`PAPER_REAL_TIME` 名称没有附带任何不可伪造的
实时观察能力。`expected_schedule_identity` 也只是对调用方自报日期 tuple 做自哈希，不是已验真的交易日历
schedule capability，因此同一进程可同时伪造“完整 schedule”和“跨 28 日时间”。

### 应遵循规则

冻结任务单要求正式 PASS 来自至少 28 个自然日内全部预期交易 session 的真实调度产物；fake clock、回放、
fixture 和一次长测只可验证 development 合同，不得构造 formal PASS。

### 新增测试与通过条件

返工必须新增独立于 development fake-clock 测试的 formal 对抗测试：单进程传入历史 `started_at`、跨 28 日
invocation/fault 时间、未来或当前 `as_of`，即使 sessions/drills 完整也必须稳定拒绝或保持
`WAITING_FOR_SOAK_EVIDENCE`。formal expected schedule 必须由已验真的 schedule capability 提供，而不是
调用方 tuple 的自哈希。真实 runner 的每次观察还必须绑定不可回放的调度/落盘事实；formal 路径不得接收
可任意注入的 clock 作为真实性依据。

## 阻断问题 2：receipt 全量重哈希后 verifier 仍接受，P5/P7 没有 fresh 证据闭包

### 现象

独立反例在已复制的临时 formal evidence 中把首个 session 的：

- `recovery_id` 改成 `ff...ff`；
- `command_ids_sha256` 改成 `aa...aa`；
- 同步重算 `invocation_identity` 与 `receipt_id`。

`verify_soak_evidence` 无上游 canonical bytes 可供重验，仍返回 verified，Gate 仍为：

```text
WHOLE_REHASH_STATUS=PASS
FORGED_RECOVERY=ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff
FORGED_COMMAND_HASH=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

### 根因

append 时 `_prove_recovery`、`_prove_reconciliation`、`_prove_report` 只验证当次内存对象；session receipt 只保留
若干 id/摘要。verify 阶段只重算 receipt 自身 identity，既不持有 P5 recovery/reconciliation、P7 report 的
canonical retained bytes，也没有可 fresh 调用的 store/report capability，因而“修改字段后整体重哈希”就是
一份新的自洽 receipt。现有测试只修改 `invocation_identity` 而没有同步重算它，未覆盖 whole-result rehash。

### 应遵循规则

正式 verifier 必须从 retained canonical 上游证据或显式窄 capability fresh 重建 P5/P7 闭包，再与 receipt
逐字段比较；不能把调用方可重算的哈希当作来源证明。

### 新增测试与通过条件

返工测试至少分别替换 recovery/reconciliation/report id、command/event/ledger 摘要和整个 receipt，并同步重算
所有下游 identity；`verify_soak_evidence` 必须 fail closed。正式 evidence 必须保留或引用 exact canonical P5/P7
输入，且 verifier fresh 验证其 identity、经济闭包和 report canonical bytes，无仅凭 receipt 摘要的生产旁路。

## 阻断问题 3：同一 canonical run 可复制到不同物理根并继续 formal PASS

### 现象

将完整临时 formal run 的 manifest/sessions/faults 复制到另一个物理 root，在目标 root 幂等重建相同 manifest
后，`verify_soak_evidence` 与 `decide_soak_gate` 仍返回：

```text
RELOCATED_STATUS=PASS
EVIDENCE_ID=2b95746557fa419e1ebf07f8329d31acec041b78a6c57049555ca54bd099ab98
```

### 根因

manifest/run/evidence identity 不绑定 formal root 的不可逆物理 store identity；`root` 只是每次调用时的路径参数，
且 `_require_persisted_manifest` 只比较目标路径下的 manifest bytes。复制 canonical bytes 即复制了全部证明。

### 应遵循规则与通过条件

formal run 必须绑定不会泄露绝对路径的物理存储 capability/volume+file identity 或等价不可逆身份，并在每次
append/verify fresh 核对。新增“相同 bytes、不同物理 root”对抗测试，目标 root 必须稳定拒绝；development
可迁移性不得放宽 formal Gate。

## 已通过的合同项

- 完整 29 日、2 sessions、10 drills 的 development evidence 返回
  `WAITING_FOR_SOAK_EVIDENCE`，稳定码为 `SOAK_DEVELOPMENT_NOT_GATE_ELIGIBLE`，没有 PASS。
- session 顺序按 expected prefix、时间严格递增；漏中间 session 无法作为完整证据，缺 session 的 Gate 保持等待。
- unknown root entry 和 symlink 检查为 fail closed；现有 unknown-entry 测试通过，代码逐项拒绝 root/session/fault
  下的未知项与 symlink。
- `append_fault_drill` 不接收调用方自报 outcome/stable code/经济摘要；实现从 before/after recovery 的
  command、cancel、event、ledger、checkpoint 闭包重算。独立完整矩阵中 10 个 drill 均由该路径产生 PASS。
- development/formal verified 类型 exact 检查存在，development 类型不会被包装成 formal PASS。
- 稳定错误使用 `raise ... from None`；现有 hostile identity/路径测试通过。上游 code 经 `_redacted_code` 过滤，
  不符合稳定码格式的文本只输出 `SOAK_UPSTREAM_ISSUE_REDACTED`。本项不抵消上述 formal 真实性缺口。

## 最终判定

**FAIL**。静态检查与既有测试绿色，但 formal Gate 可由单进程时间回放直接构造 PASS，且 receipt 全量重哈希、
物理 root 复制均没有被 verifier 拒绝。状态应回到“实现返工 -> 全新独立复验”；当前只能保留
`WAITING_FOR_SOAK_EVIDENCE` 的开发合同表述，不得启动或累计正式 28 日证据。
