# M4-P2B-0 取消命令合同实现报告

## 结论

已完成开发态 `CancelCommand` 与取消网关传输合同。该交付只建立内容寻址、可持久化重放的 PAPER 取消命令边界，不实现具体 Gateway、持久化迁移、自动重试或 LIVE；不代表 M4 正式 Gate 关闭。

## 冻结合同的实现

- `CancelCommand.cancel_id` 由原始 `command_id`、已绑定的 `broker_order_id`、`PAPER` mode、首次取消时的 OMS 状态、累计成交量、完整已应用事件 ID 顺序、最后事件 UTC 时刻和取消 `as_of` 共同计算。
- 首次取消只接受经重建复验的 `OrderAggregate`，状态必须为 `SUBMITTED` 或 `PARTIAL_FILLED`，且 broker order id 已绑定；`OrderCommand` 及其 intent 身份均再次验证。
- `CANCELLING` 不生成第二个经济命令。调用者必须提供既有 `CancelCommand`；实现验证同一 command/broker/mode、原事件闭包仍是当前闭包前缀、成交量与事件时刻单调后，原样返回同一个 `cancel_id`。因此 `CANCELLING` 中的晚到 fill 不破坏已有取消命令重放。
- `GatewayCancelTransport` 与 `GatewayCancelResult` 复用既有 `DispatchCertainty` 和 `ExecutionEvent`。结果严格绑定 `cancel_id`、attempt、原订单及 broker id；`UNKNOWN` 禁止携带 callbacks，其稳定 `cancel_id` 只供上层人工查询，合同不提供自动重试入口。
- 既有 `GatewayTransport.submit`、SQLite v2 schema 和 OMS reducer 均未修改；既有晚到 fill 语义保持不变。

## 依赖边界说明

`quant.execution.oms` 顶层依赖 `quant.execution.contracts`，因此 `contracts.py` 不能顶层反向 import `OrderAggregate`。`build_cancel_command` 使用函数内局部 import，并立即以 `OrderAggregate` 全字段重建来重新执行其不变量；模块导入图仍保持无循环，只有显式构造取消命令时才跨到 OMS 快照验证。未新增第三方依赖或 IO。

## 独立初验返工闭环

### P1-1：identity verifier 未重跑结构合同

- 现象：只重算 digest 时，冻结对象被原地改成 `enum -> str` 或 `tuple -> list` 后，结构等价载荷存在绕过字段类型约束的空间。
- 根因：`build_cancel_command_identity` 没有重新执行 `CancelCommand.__post_init__` 的全部类型、UTC 和交叉约束。
- 应遵循规则：身份验证必须先从全部字段严格重建值对象，再认可内容摘要；摘要相同不代表 Python 结构合法。
- 最小复现：构造合法取消命令后用 `object.__setattr__` 把 `mode`、`aggregate_status` 或 `observed_event_ids` 改成对应字符串/列表。
- 新增测试：`test_cancel_identity_reconstructs_types_before_digest`、hostile timezone 与 TOKEN event-id 脱敏反例。
- 通过条件：所有结构篡改统一以无 cause/context 的 `CANCEL_COMMAND_INVALID` 失败，错误文本不含输入 sentinel。

### P1-2：取消回调未证明 OMS 可消费

- 现象：逐事件 hash/source 检查仍可能接受非法 ACK、累计成交回退/跳跃或 OMS 不可达的回调序列。
- 根因：verifier 未绑定原 `OrderCommand` 和首次取消时的完整 `OrderAggregate` 快照，也未按 callback 原顺序执行 reducer。
- 应遵循规则：取消结果必须从与 `CancelCommand` 字段完全一致的合法快照起步；每个回调先验证内容身份和同 id 载荷一致性，再限制为取消竞态可达类型、精确 broker、时间窗口，最后调用 `reduce_order`。
- 最小复现：`CANCEL_ACCEPTED -> PARTIAL_FILL(cumulative=40,last=20)`、累计量回退、`ACCEPTED` 冒充取消 ACK、broker 为 `None`。
- 新增测试：合法 `cancel -> late partial -> cancelled`、`cancel -> full fill`，以及非法类型、broker、累计量跳跃/回退、快照漂移和 TOKEN 篡改反例。
- 通过条件：合法竞态序列通过；任何一步 OMS 不可消费均以稳定脱敏的 gateway error 失败。

### P1-3：终态后无法重放既有取消命令

- 现象：取消命令已持久化后，订单可能在恢复前进入 `CANCELLED` 或因竞态进入 `FILLED`；旧实现只允许 `CANCELLING` 重放。
- 根因：replay 分支按单一中间状态分派，没有按订单状态的合法单调后继验证。
- 应遵循规则：提供 replay 时只接受 `CANCELLING`、`CANCELLED`、`FILLED`；command/broker 必须一致，旧事件闭包必须是当前闭包前缀，filled/last time 必须单调，始终返回原对象和原 `cancel_id`。
- 最小复现：首次取消后应用 `CANCEL_ACCEPTED -> CANCELLED` 或 `CANCEL_ACCEPTED -> FILL`，随后恢复并重放。
- 新增测试：`test_cancel_replay_survives_cancelled_and_filled_monotonic_successors`，同时验证 `SUBMITTED` 携 replay 被拒绝。
- 通过条件：三个允许状态返回同一对象；其他状态、闭包漂移或数值倒退均失败。

### P1-4：校验顺序与异常脱敏不足

- 现象：先做唯一性或直接传播底层异常，可能回显恶意 event id/tzinfo 文本，或保留异常 context。
- 根因：缺少“无回显身份/形状验证优先”的统一边界，部分路径在 `except` 内直接抛新异常。
- 应遵循规则：先验证 event 内容身份/hex 形状，再检查同 id 载荷一致性；捕获状态只写布尔标记，在 `except` 外抛稳定错误。
- 最小复现：重复的 `TOKEN_SECRET_EVENT_ID`、hostile tzinfo、篡改 callback broker 后保留旧 event id。
- 新增测试：CancelCommand 与 gateway 两层均断言 sentinel 不出现，且 `__cause__`、`__context__` 均为空。
- 通过条件：对抗输入失败且不泄露输入载荷或内部异常链。

### 复验追加：精确重复 event id 必须保留 OMS 幂等语义

- 现象：返工版 blanket reject 任何重复 event id，误伤 Gateway 重复投递的同 payload 回调。
- 根因：verifier 自行实现了比 OMS 更严格的去重策略，没有把精确重复事件继续交给 reducer。
- 应遵循规则：维护 `event_id -> 已严格验证事件`；同 id 同 payload 保持原顺序并继续调用 `reduce_order`，由 OMS 做幂等 no-op；同 id 异 payload fail closed。
- 最小复现：回调序列包含两次相同 `CANCEL_ACCEPTED`，或两次相同 `PARTIAL_FILL`。
- 新增测试：ACK exact duplicate 与 partial-fill exact duplicate 正例；保留同 event id 篡改 payload 的 TOKEN 脱敏反例。
- 通过条件：精确重复序列通过且返回原 result；异 payload 以稳定无回显错误失败；P2A 行为不变。

## 边界与剩余工作

- 当前证据是 Windows 与 WSL/DrvFS 的开发合同验证，不是 WSL/ext4 平台 Gate，也不替代正式 M4 端到端验收。
- 后续 P2B 实现需要为取消命令增加独立 durable outbox/store 生命周期，并明确 `UNKNOWN` 后的人工 query/resolution 流程；本任务刻意保持 SQLite v2 不变。
- 具体 PAPER Gateway 仍需把取消回报标准化为既有 `ExecutionEvent`，再由 OMS 按现有状态机处理，包括 `CANCELLING` 阶段晚到 fill。
