# M4-P5-P0 恢复与账本持久化前置设计

状态：冻结前置设计；不代表 P5、M4 或 Linux Gate 通过。本文件只拆解 P5 实现前必须关闭的接口缺口，
不修改 [`M4轻量交易闭环分包任务书.md`](M4轻量交易闭环分包任务书.md) 的 P5 业务合同。

## 1. 为什么 P5 暂停

P5 的公开入口是 `recover_local_state(store) -> RecoveryResult`，调用者不会提供 command、event、aggregate、
delivery 或 ledger key。当前 `ExecutionRepository` 只有按已知 key 的读取接口，没有安全列举接口；P4 的
command/event/aggregate canonical codecs 是 `service.py` 私有函数；B5 的 `LedgerEntry/LedgerState` 也没有
公开 canonical bytes codec，且 P4 尚未把 B5 ledger checkpoint 与 entries 纳入 callback 事务。

因此 P5 当前若继续，只能选择私有 SQL、import 私有 codec 或复制 wire 格式，都会破坏 P0 窄仓储接口、
SSOT 或持久化闭包。前置按 P0A → P0B → P0C 三包顺序关闭，随后才实现 P5。

## 2. P5-P0A：typed atomic recovery snapshot

### 2.1 目标与接口

在 `quant.execution.store` 增加不可变、严格类型化的 `RecoveryRows`，至少包含：

- `commands: tuple[StoredRecord, ...]`
- `events: tuple[StoredEventRecord, ...]`，保留 `event_id -> command_id` 关联键；
- `order_aggregates: tuple[StoredRecord, ...]`
- `outbox_deliveries: tuple[OutboxDelivery, ...]`
- `ledger_entries: tuple[StoredRecord, ...]`
- P0C 引入后追加 `ledger_contexts` 与 `ledger_checkpoints`，不得另建第二个快照入口。

唯一读取入口冻结为：

```python
ExecutionRepository.read_recovery_rows() -> RecoveryRows
```

P5 必须在一次 `with store.transaction() as repo:` 中调用该入口。所有表在同一 SQLite transaction snapshot
内读取，结果按各自主键字节序升序返回；禁止分页跨事务拼接、调用者传表名、任意 SQL、任意 where/order
表达式或暴露 connection/cursor。

### 2.2 严格性与失败语义

- 每一行必须复用现有 `_row_to_stored`、event 关联键验证和 `_row_to_outbox_delivery`；不得返回未验证 tuple。
- duplicate key、非法类型、非法枚举、缺 outbox join、delivery 闭包矛盾统一 fail closed。
- SQLite 异常映射为稳定 `RECOVERY_SNAPSHOT_READ_FAILED`，异常不得包含 SQL、绝对路径或数据库文本，且
  `__cause__`/`__context__` 断链遵循 P0 已冻结规则。
- 空库返回各字段均为空的合法 `RecoveryRows`；它不等价于“broker 也是空”，结论留给 P5。
- 此接口只读，不 claim delivery、不续 lease、不修复行、不写 reconciliation run。

### 2.3 文件白名单与验证

- `src/quant/execution/store.py`
- `tests/unit/test_execution_store.py`
- P0A 独立任务单、实现报告、独立初验报告

反例至少覆盖：跨表写入在 snapshot 前/后发生时不出现撕裂视图；两次读取稳定排序；损坏 delivery join、
event 关联键或 row 类型时整体失败；空库；SQLite hostile error 脱敏。不得借此增加通用 list/table API。

## 3. P5-P0B：shared public canonical wire 与 verifier

### 3.1 目标与模块边界

把当前 P4 私有 wire 实现提升为共享公开 SSOT，P4 与 P5 必须调用同一实现，不允许复制 JSON 字段清单。
建议模块：

- `quant.execution.wire`：`OrderCommand`、`ExecutionEvent`、`OrderAggregate`；
- `quant.backtest.ledger_wire`：B5 `LedgerEntry`、`LedgerState`。

P5 对 B5 的依赖仅限上述 immutable domain objects 与公开 codec；不得调用 simulator、数据源或扫描数据目录。
若后续决定把共享账本合同下沉到更低层，应另立架构任务，不在本前置中搬迁整个 B5。

公开接口冻结为成对的严格函数：

```python
encode_order_command(value: OrderCommand) -> bytes
decode_order_command(payload: bytes) -> OrderCommand
encode_execution_event(value: ExecutionEvent) -> bytes
decode_execution_event(payload: bytes, *, command: OrderCommand) -> ExecutionEvent
encode_order_aggregate(value: OrderAggregate) -> bytes
decode_order_aggregate(payload: bytes, *, command: OrderCommand) -> OrderAggregate

encode_ledger_entry(value: LedgerEntry) -> bytes
decode_ledger_entry(payload: bytes) -> LedgerEntry
encode_ledger_state(value: LedgerState) -> bytes
decode_ledger_state(payload: bytes) -> LedgerState
```

decode 必须要求 UTF-8、无 BOM、无空白、排序键、严格字段全集、有限 Decimal 的唯一文本、UTC/date 唯一文本、
合法 enum 和 schema version，并重新构造 domain object 以复验 content identity。调用者自报 identity 不参与
信任；repository row identity/key 与 decoded domain identity 的闭包由 P5/P0C 显式检查。

### 3.2 兼容与迁移

- command/event/aggregate 保持现有 `m4-*-v1` 字节完全相同；这是代码抽取，不是 wire 升版。
- P4 `service.py` 改用公开 codec 后，既有 golden bytes、command/event id、aggregate digest 必须不变。
- Ledger wire 首次冻结为 `m4-ledger-entry-v1` 与 `m4-ledger-state-v1`；schema 名写入 canonical root。
- decoder 只接受显式已支持版本。未知版本稳定报 `WIRE_VERSION_UNSUPPORTED`，不得 best-effort 猜测。
- 旧库中任意非 canonical/无 schema ledger opaque bytes 不自动升级、不删除、不解释；P0C/P5 将其分类为
  `LEGACY_LEDGER_WIRE_UNVERIFIED`，Gate fail，等待人工迁移。

### 3.3 文件白名单与验证

- 新建 `src/quant/execution/wire.py`、`src/quant/backtest/ledger_wire.py`
- 最小修改 `src/quant/execution/service.py` 以复用公开 codec
- 对应新测试及 `tests/unit/test_execution_service.py` 的 byte-compat 回归
- P0B 独立任务单、实现报告、独立初验报告

反例至少覆盖：extra/missing key、重复 JSON key、NaN/Infinity、Decimal 非唯一文本、非 UTC、未知 enum/schema、
command-event 错绑、aggregate quantity 错绑、ledger entry/state identity 篡改、 hostile bytes/异常脱敏；另用
既有 P4 fixture 证明重构前后 bytes 与 hashes 完全一致。

## 4. P5-P0C：P4 + B5 ledger 持久化事务闭包

### 4.1 持久化模型

现有 `ledger_entries` 保持 append-only。schema v4 新增两类窄记录：

- `ledger_contexts(command_id PRIMARY KEY, identity, payload)`：每个 sendable command 的不可变账本上下文；
- `ledger_checkpoints(checkpoint_key PRIMARY KEY, identity, payload, last_entry_id)`：当前单账户/单 store 的
  canonical `LedgerState` checkpoint 与 entry 链尾。

`checkpoint_key` 为版本化固定常量，不接受调用者任意账户路径/表名。当前 M4 一个 execution store 只承载一个
PAPER/SHADOW 账户；未来多账户必须另立迁移，不在 key 中暗藏未验证 account id。

`ledger_context` 至少闭包：command id、`SettlementRule` canonical identity/bytes、交易与结算日历来源身份、
适用 session，以及 B5 实际需要的 FX snapshot identity/bytes。A 股 CNY=CNY 也必须使用显式、可验证的 identity
context，不以 `None` 表示隐式汇率。context identity 由 canonical bytes 计算，不能由调用者自报 hash。

### 4.2 P4 事务边界

P4 的 API 通过窄 typed dependency 显式取得已验证 ledger context；不得在 dispatch 时访问网络或按当前配置
重新猜历史 rule/FX：

1. `plan_and_stage` 的 command/outbox/delivery 事务同时写入对应 immutable `ledger_context`。缺 settlement
   calendar、rule 或 FX 时整个 stage 回滚，不能形成 sendable delivery。
2. 首次建立 store 时，从已验证 `AccountSnapshot` 构造 genesis `LedgerState` checkpoint；已有 checkpoint 时
   必须验证 origin/scope 闭包，禁止用新 account snapshot 覆盖本地状态。
3. gateway `SENT` callback 事务内按 event 顺序调用 B5 纯函数，写 canonical events、OMS aggregate、每个
   append-only `LedgerEntry`、CAS 替换 checkpoint，最后标记 delivery `SENT`。任一步失败全部回滚。
4. exact duplicate event/entry 是同 bytes no-op，不能产生第二次经济影响；同 id 异 payload fail closed。
5. `NOT_SENT` 不写 ledger；durable `UNKNOWN` 不猜成交、不写经济账，只留 P5 `QUERY_REQUIRED`。

为避免 execution service 自行复制 B5 逻辑，账本转换应是一个同步、无 IO 的 typed adapter/protocol；输入必须是
verified checkpoint、command、callbacks 与 immutable context，输出必须是 verified next state 与 entries。
具体 adapter 可以位于 B5 模块，P4 仅负责编排及同一 SQLite transaction 提交。

### 4.3 migration 与旧数据

- v3 → v4 只建新表，不回填、不修改既有 command/event/aggregate/outbox/delivery/ledger row。
- migration 不为旧 PENDING/LEASED delivery 伪造 ledger context；缺 context 的旧 sendable row 在 adapter 前
  fail closed，状态由 P5 报 `LEGACY_LEDGER_CONTEXT_MISSING`，不得静默发送。
- 旧 SENT/UNKNOWN row 缺 checkpoint 或 context 时不从 broker snapshot 倒灌本地；P5 至少产生
  `MANUAL_REQUIRED` 或 `QUERY_REQUIRED`，Gate fail。
- legacy opaque ledger bytes 不自动解释。迁移工具、如需要，必须是后续独立人工任务并保留原 bytes。
- schema migration 失败继续遵循 P0 `migrating` fail-closed 语义。

### 4.4 恢复闭包与失败语义

P0C 完成后，P0A 的 `RecoveryRows` 原子包含 context/checkpoint。P5 恢复时必须验证：

- command、event、aggregate、delivery、context 的 key/identity/payload 互相闭包；
- checkpoint identity、origin、entry chain tail、applied event ids 与 persisted entries 一致；
- duplicate economic event 只出现一次；未知或断裂 entry、缺 context/checkpoint、未来 schema 均稳定 fail closed；
- 恢复只构造不可变本地视图，不 claim、重放、改写或修复任何 row。

错误只返回稳定 code/subject，不包含 payload、broker 文本、SQL、绝对路径、token 或 traceback context。

### 4.5 文件白名单与验证

- `src/quant/execution/store.py` 与新 migration（仅新增窄表/API）
- `src/quant/execution/service.py`
- B5 的最小 ledger adapter/codec 文件
- 对应 store/service/ledger 定向测试
- P0C 独立任务单、实现报告、独立初验报告

反例至少覆盖：stage 缺 settlement/FX 全回滚；callback 第二个 entry 失败导致 event/aggregate/entries/checkpoint/
SENT 全回滚；重复 callback 零重复经济影响；同 entry id 异 payload；checkpoint CAS 冲突；v3 旧 pending 不被
发送；UNKNOWN 不写账；重启后用 persisted context 得到相同 checkpoint identity；hostile context/checkpoint
失败且脱敏。

## 5. 分包顺序与完成条件

```text
P5-P0A atomic recovery rows
        ↓
P5-P0B shared canonical wire/verifiers
        ↓
P5-P0C ledger context + checkpoint + P4 transaction closure
        ↓
M4-P5 recover_local_state + reconciliation
```

三个前置包各自采用“任务书 → 实现/自测 → 独立初验 → 主验”的职责分离，不以一次大改合并。P0B 可先写
纯 codec，但 P0C 不得在 P0A/P0B 主验前宣称恢复闭包成立。每包均执行 Windows 定向反馈与 WSL Miniforge
base 定向 Ruff/mypy/pytest；DrvFS/Windows 绿色不替代 ext4/Linux Gate。

只有以下事实同时成立，P5 才解除暂停：

1. `recover_local_state(store)` 能通过公开 typed atomic snapshot 发现全部本地相关行；
2. 所有 opaque bytes 都由唯一公开 codec 严格解码并复验 domain identity；
3. P4 callback 的 OMS、ledger entries/checkpoint 与 delivery SENT 在同一事务提交；
4. settlement/calendar/FX 是持久、显式且 identity-bound 的输入；
5. 旧 v3/legacy 数据有明确 fail-closed 分类，没有伪造回填或 broker 覆盖本地。

即使以上开发合同全部通过，P5 仍不得把开发 reconciliation 表述为正式 PAPER soak、M4 Gate 或 Linux Gate。
