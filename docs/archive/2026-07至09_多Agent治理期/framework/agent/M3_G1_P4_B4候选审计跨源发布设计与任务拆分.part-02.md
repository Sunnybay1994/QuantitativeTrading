### 6.2 发布输入与纯准备阶段

```python
@dataclass(frozen=True)
class G1ReleaseInputs:
    build_inputs: G1BuildInputs
    cross_source_policy: G1CrossSourcePolicy
    reference_responses: tuple[VerifiedReferenceResponse, ...]

@dataclass(frozen=True)
class G1PreparedRelease:
    candidate: G1Candidate
    primary_audit: G1PrimaryAuditResult
    reconciliation: CrossSourceReconciliationBundle
    release_id: str
    quality: G1QualityReportV1

@dataclass(frozen=True)
class VerifiedG1Release:
    release: G1Release
    manifest: G1ManifestV1
    manifest_sha256: str
    quality: G1QualityReportV1
    quality_sha256: str
    artifact_paths: tuple[tuple[str, Path], ...]  # 17 项，按 manifest path 排序

def prepare_g1_release(*, inputs: G1ReleaseInputs) -> G1PreparedRelease: ...

def publish_g1_release(
    *, output_root: Path, inputs: G1ReleaseInputs,
) -> G1Release: ...

def verify_g1_release(*, release: G1Release) -> VerifiedG1Release: ...
```

`prepare_g1_release` 是无 IO 纯函数，顺序固定：重建 P4A candidate → verify → primary audit → 重算 sample plan →
重算 reference request closure/verified responses → reconciliation → release identity → quality。任何 ERROR 时抛稳定
`G1_RELEASE_QUALITY_FAILED`，正式 root 零文件增量。

### 6.3 release identity 与严格对象

release identity 是下列对象经同一 strict canonical JSON 编码后的 SHA-256：

```json
{
  "schema_version": "m3-g1-release-identity-v1",
  "primary_candidate_key": "...",
  "sample_plan_sha256": "...",
  "reference_receipts": ["按 (source,endpoint,request_id) 排序的完整 BaoStock G1ReceiptProjectionV1 对象"],
  "cross_source_detail_sha256": "...",
  "cross_source_summary_sha256": "..."
}
```

`G1QualityReportV1` 使用 `primary_candidate_key`，不再有 `candidate_sha256`。`G1ManifestV1` 也移除
`candidate_sha256`，补齐 `price_limit_required_keys_sha256`，并补齐：

```text
signal_start
signal_end
history_start
history_end
price_limit_method_version
corporate_action_selection_version
corporate_action_reconciliation_version
```

四个日期只能从已重建的 `G1BuildInputs` 投影：`signal_start <= signal_end`、
`history_start <= signal_start <= signal_end <= history_end`，并必须与 request plan 的 warmup/history/tail
闭包一致。它们不作为 caller 可覆盖的发布参数。G2 snapshot 的日期域只能从这四个 manifest 字段取得并与
自身 narrow config/spec 交叉验证，不能用 staging min/max 或调用方裸日期替代。

manifest `input_receipts` 必须精确包含 candidate 全部 Tushare projections 和 reconciliation 全部 BaoStock
projections，按 `(source,endpoint,request_id)` 排序。

严格 reader 必须拒绝：非 UTF-8、duplicate JSON key、未知/缺字段、错误 exact type、字符串数字、bool 冒充
数字、NaN/Infinity、未知 schema/issue code、未排序或重复 tuple、绝对/逃逸路径、错误统计/hash。reader 解析后
重建 dataclass 并重算业务不变量，不得只做 JSON Schema 形状检查。

### 6.4 固定目录与 artifact 表

发布目录精确为：

```text
data/clean/m3_g1/releases/<release_id>/
  manifest.json
  quality.json
  universe_membership.parquet
  eligible_keys.parquet
  bar_1d.parquet
  adjustment_factor.parquet
  adjustment_factor_match.parquet
  benchmark_bar_1d.parquet
  suspension_1d.parquet
  trade_calendar.parquet
  instrument.parquet
  index_constituent_observation.parquet
  price_limit_1d.parquet
  corporate_action_ledger.parquet
  corporate_action_selection_evidence.parquet
  corporate_action_reconciliation.parquet
  cross_source_reconciliation.parquet
  cross_source_reconciliation.json
```

manifest `files` 精确列出除 manifest 自身外的 17 个普通文件。不得分区、增加 `_SUCCESS`、日志、临时文件或
隐藏普通文件。每个 artifact entry 重算相对 path、bytes SHA-256、逻辑 content digest、size、row count、
Schema/version、key columns、min/max。JSON artifact 固定 row_count=1、空 keys、null min/max；其 content digest
对严格解析对象做规范 JSON hash。

Parquet writer 的 column order 由各 Schema/本文固定表定义冻结；写参数精确为
`compression="zstd"`、`compression_level=3`、`statistics=True`、`row_group_size=65536`、
`use_pyarrow=False`，并由模块常量集中定义。不得依赖 Polars 默认值。release identity 依赖逻辑 digest而不是
Parquet bytes；dependency fingerprint 已进入 primary identity，避免升级 writer 后静默复用。

### 6.5 原子发布状态机

1. 完整执行 `prepare_g1_release`，失败时不创建 staging/final。
2. 校验 output root 全祖先无 symlink，release ID 只能是裸小写 64 位 hex。
3. 若 final 已存在，先严格 `verify_g1_release`，再与本次 prepared identity/summary/quality 比较；相同则复用，
   不同或损坏则失败，绝不补写/覆盖/删除。
4. 在 output root 的受控 staging 子目录创建唯一临时目录；每个文件 exclusive create、flush、file fsync；
   在 staging 中完成全部 reader/Schema/hash/key-range 复验。
5. manifest 最后写入；fsync staging directory。
6. WSL/Linux 必须以 `renameat2(RENAME_NOREPLACE)` 或经测试证明语义等价的目录级 primitive 原子发布
   `staging → final`。若运行时不支持 no-clobber 则 fail-closed；禁止回退到 `os.rename`、`os.replace`、
   逐文件 merge 或“先检查不存在再 rename”。并发 writer 先发布 final 时，当前 writer 只能严格验证并复用
   同一 release，不能覆盖即使对方目录暂为空。
7. rename 成功后 fsync output root，立即再次 `verify_g1_release`。
8. 临时 cleanup 失败不得静默；主异常优先。发布成功后的 fsync/close/verify 失败必须报告，不得伪成功。

verifier 对 final 目录要求真实 directory、每个 entry 为真实 regular file、`st_nlink == 1`、无 symlink、无额外
entry、路径物理身份不互相别名。成功后返回 `VerifiedG1Release`，供 G2 snapshot 在消费边界取得 manifest、
quality 和受控 artifact path；下游不得重新拼 `root / "bar_1d.parquet"` 或接受裸 DataFrame 加自报 hash。
失败时不擅自删除或 quarantine 用户数据。

### 6.6 P4C 必测反例

至少覆盖：

1. 自报 candidate/audit/quality wholesale 替换无法作为 publisher 输入；原始 response 改一格会重建出不同 ID；
2. quality fail、reference fail、prepare 异常时 release root 零增量；
3. 输入行序变化 release ID 不变；calendar/list-date/factor/receipt/tolerance/四个日期域任一变化 ID 改变；
4. quality hash 不进入 release ID 的无循环证明；修改 quality 后 manifest/verify 失败；
5. 17 项 file table 少/多/重复、错误 bytes/content digest、row count、Schema、key min/max；
6. duplicate JSON key、字符串数、bool 数、NaN/Infinity、未知 issue、绝对/`..` path；
7. staging 每个写入点、file fsync、dir fsync、`renameat2(RENAME_NOREPLACE)`、post-publish verify、
   cleanup/close 故障注入；显式反例是“并发方先创建空 final 目录”，不得被覆盖；
8. 两个 writer 同 ID；已有有效 release 零写复用；已有损坏/不同 release 不覆盖；
9. final/staging/root symlink，artifact hardlink、FIFO/socket/device、祖先替换和路径逃逸；
10. 静态证明生产路径无 `os.rename/os.replace` fallback、无 research 反向 import、无 connector/network 调用。

## 7. P0/P1 与“抓大放小”边界

deprecation warning、非关键 helper 命名。不得把安全、证据闭包、PIT、因子/公司行动、跨源或不可变发布问题
降级为“小问题”。
