## 2. 冻结合同映射

### 2.1 B6

- `ScheduledOrderPlan.session_date` 同时约束 plan intents、close 和 fills；现有 Friday plan + Monday fill/close 反例通过。
- 正常模拟固定执行 advance → recognize/settle → trade → capture；PAPER event、ledger transition/checkpoint 和最终状态均进入结果 identity。
- hostile corporate-action validator 和嵌套 plan identity 篡改被映射为稳定 `EventSimulationError`；已有断言确认消息不回显 sentinel，且 `__cause__`、`__context__` 均为 `None`。
- 但公共 self-consistency verifier 只重建每个 `RuleDecision` 的值对象并把整个 tuple 放入 scenario hash；它没有证明 decision 集合非空、唯一、与计划目标/command 对应，也没有重跑该对应关系。因此调用者可删除或替换 decision，再重算 scenario/root identity 获得“验证通过”的不同语义结果。

### 2.2 B7

- 计算入口先调用公开 `verify_simulation_result_identity`，没有复制 B6 私有 hash 公式。
- 账面曲线严格按币种分别计算 `settled + receivable - payable + position avg_cost * quantity`；未发现跨币种求和或把该曲线命名为 NAV/Sharpe/Calmar。
- opening book value 非正时 `book_return=None`；return observation 不足时 annualized volatility 为 `None`；NaN/Inf 和非法 annualization fail closed。
- 由于 B6 verifier 的语义闭包缺失，B7 对伪造结果仍会生成 identity-bound metrics，故 fresh verified 前置不成立。

### 2.3 B8

- `AdmissionContext` 构造和比较均固定 `segment == "test"`；validation-only 无法产生 ADMIT。
- context 精确冻结 candidate/scenario 集合及 snapshot/window/rules/costs identity；候选必须提交全部场景和全部阈值指标。
- 每个场景逐项过阈值后才有排名资格；ranking 使用 MINIMUM 指标的场景最小值或 MAXIMUM 指标的场景最大值。
- 唯一最优过线候选才 ADMIT；无人过线及最坏场景值并列均显式 REJECT。
- 候选输入顺序不改变 evidence 顺序、decision 或 identity；同 id 嵌套 payload 篡改、重复/缺失候选或场景、NaN/Inf 均被拒绝。

## 3. 阻断问题：B6/B7 接受 whole-result 自洽语义伪造

### 现象

以现有 partial-fill fixture 产生合法 B6 结果后：

1. 将场景的 `rule_decisions` 整体删除；或把首个 `ACCEPTED` decision 替换为合法构造但语义相反的 `FORGED_DECISION`；
2. 使用模块现有 canonical identity 规则重新计算 `scenario_result_id` 和 root `result_id`；
3. `verify_simulation_result_identity(forged)` 返回 forged 自身；
4. `build_trading_metrics(forged, 252)` 继续成功，且绑定新的 forged result id。

实际独立复现输出：

```text
DELETED_DECISIONS_ACCEPTED True
WHOLE_RESULT_FORGERY_ACCEPTED True True
DECISION True ACCEPTED -> False FORGED_DECISION
```

### 根因

`_prove_scenario_result` 对 `rule_decisions` 仅做类型/字段构造检查，未验证：

- decision 集合的完整性、唯一性和稳定顺序；
- decision 与 scenario 输入计划目标、生成 command 或 rejection 的一一对应；
- decision 所陈述的 accepted/code/normalized quantity 与实际 command/event/ledger 路径一致。

随后 `_result_payload` 把该 tuple 当作普通可重哈希内容；SHA-256 只能证明调用者提供的内容自洽，不能替代缺失的语义关系。B7 严格调用该 verifier，因此继承同一缺口。

### 应遵循规则

B6 任务书要求公共 verifier 对嵌套 contract、decision、command/event/ledger transition/checkpoint 链路做完整 self-consistency 重验。允许调用者任意重写 decision 后自行重哈希，会使“verified”退化为“well-hashed”，破坏 B6→B7 的可信输入边界。

### 最小复现

使用 `tests/unit/test_event_simulator.py::_fixture(partial=True)`：

- `simulate_order_plans` 得到原结果；
- `dataclasses.replace(scenario, rule_decisions=())`；
- 按现有 `_result_payload` 重算 scenario identity，再按 root payload 重算 result identity；
- 调用公共 verifier，当前错误地通过。

替换首个 decision 为 accepted 取反、code=`FORGED_DECISION` 的合法 `RuleDecision` 也同样通过；B7 随后正常出指标。

### 必须新增的测试

1. 删除一个或全部 rule decision，即使重算 scenario/root identity，公共 verifier 仍须稳定拒绝。
2. 同一目标/command 对应 decision 的 accepted、code、normalized quantity 或 rule version 被替换并重算所有 identity，仍须拒绝。
3. 重复、乱序 decision，或将另一个 target/scenario 的合法 decision 移入当前场景，仍须拒绝。
4. B7 对上述每类 forged B6 结果均须在计算任何 metrics 前抛 `TRADING_METRICS_INPUT_INVALID`。
5. 若公共 self-consistency 结果形态缺少证明对应关系所需的信息，应先扩展 B6 结果闭包或加入 identity-bound 映射，而不是在 B7 复制 planner/rule 私有公式。

### 通过条件

- B6 能以公开、确定、无 IO 的方式证明 decision 集合及其与 command/event/ledger 的完整对应；
- 上述删除、替换、重复、跨场景移植并全量重哈希的反例全部 fail closed；
- B7 对同组反例在指标构建前拒绝；
- 原正常、partial-fill、suspended、HK T+2 和异常脱敏回归保持绿色；
- 修复后由未参与返工的全新 Agent 重新初验 B6/B7。
