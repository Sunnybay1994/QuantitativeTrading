## 2. 主 Agent 首轮发现与修订

### P0-1 snapshot identity 前置循环

- 现象：旧接口要求在 snapshot stage 执行前传入 `snapshot_id`，但该 ID 只能由 staging manifest 得出。
- 根因：把内容寻址产物的最终 ID 当成构建请求 ID。
- 规则：先用 G1 release、snapshot config 和 code 计算 `snapshot_request_key`；staging/manifest 验真后才
  计算并发布 `snapshot_id`，同时写不可变 request→snapshot 映射。
- 回归：snapshot 尚未生成时不得要求或伪造 snapshot ID；损坏映射不得重指向其他 snapshot。

### P0-2 experiment 与 work identity 混层

- 现象：旧 `run_key` 同时包含 fold/horizon，又声称其目录下包含多个 fold×horizon。
- 根因：实验共享身份和执行单元身份未分开。
- 规则：`experiment_key` 只描述共享 snapshot/provider/scientific config/code/dependency；`work_key` 再加入
  fold/horizon。同一 3 folds×2 horizons 只有一个 experiment、六个 work。
- 回归：fold/horizon 变化不得改变 experiment key，必须改变 work key。

### P0-3 单一 StageSpec 无法表示多个执行实例

- 现象：stage 名要求唯一，却又需要六个 features/train/predict 实例。
- 根因：stage 类型与 DAG node 混为一个对象。
- 规则：`StageSpec` 是静态类型 registry，`StageNode` 是带唯一 node ID、scope key、fold/horizon、声明输入
  和输出的实例；依赖只引用 node ID。
- 回归：重复 stage 类型合法，但 node ID/receipt path 必须唯一；输出冲突和 DAG 环必须失败。

### P0-4 receipt 跨 scope 与自引用

- 现象：work receipt 只能记录 work 根内路径，无法审计 snapshot/provider 输入；provider 又把
  `provider.complete.json` 列入自身输出，形成 hash 自引用。
- 根因：digest 没有逻辑 root，且把完成标记误当业务产物。
- 规则：digest 使用 `root_alias + relative_path`，执行器显式注入 alias→root；receipt 自身永不列入
  outputs。未知 alias、绝对路径、`..`、符号链接逃逸、重复路径全部失败。
- 回归：跨 root 合法引用可验真；自引用、漏 required output 或 scope/scope_key 不符均失败。

### P0-5 多文件发布崩溃窗口

- 现象：产物 rename 后、receipt 写入前崩溃会留下 orphan；简单重跑可能覆盖正式文件。
- 根因：单文件原子 rename 不能让多个输出和 receipt 形成一个原子事务。
- 规则：重算到 stage 临时目录；orphan 与重算结果逐字节一致时才可认领并补 receipt，任何冲突 fail-closed。
- 回归：在每个 publish 故障点注入中断；相同 orphan 恢复，不同 orphan 不覆盖。

## 3. 独立 Agent 初验反馈与主 Agent 吸收

### P0-6 plan 分段仍断链

- 现象：首轮修订只有 snapshot/experiment 两段，provider 无所属 plan；experiment plan 同时把未验真的
  folds 当 work 枚举前置。
- 根因：只解决 snapshot ID 的延迟绑定，未把 provider receipt 和 folds receipt 也视为发布边界。
- 规则：固定 continuation：snapshot → provider → experiment shared(labels/folds) → fold-shared features +
  work → research summary。每个 plan builder 都是纯函数，不执行 handler 或扫描目录；下一段只读取上一段
  已验真的 receipt/manifest。G4–G6 后续审查进一步把 Alpha158 从 horizon work 提升为 fold-shared stage，
  并增加只依赖已完成 evaluation 的 summary continuation。
- 回归：缺 snapshot receipt 不能建 provider plan；缺 provider receipt 不能建 experiment plan；缺 folds
  receipt 不能建 work plan。

给实现 Agent 的指导：遇到“输出决定下一层身份或扇出”的情况，应增加显式发布边界，不要在 DAG 外偷跑
函数、用目录存在性猜状态，或把占位 ID 填进最终路径。

### P0-7 StageRunner 接口无法落实文字约束

- 现象：文字要求显式 handler/root 注入，旧函数签名却没有这两个参数。
- 根因：接口设计只表达调度结果，没有表达能力边界。
- 规则：`execute_m3_plan` 显式接收 `handlers` 和 `artifact_roots`；runner 将 receipt 的完整契约与 StageNode
期望集合比较，而不只验证 receipt 自报内容。
- 回归：fake handler 记录所有 open/read；未声明读取、少输出、错 root/scope 均失败。

给实现 Agent 的指导：安全约束必须能由函数参数和类型表达；若测试无法注入严格 fake，说明所谓隔离只是
注释，不是可验证契约。

### P0-8 科学 identity 缺实际依赖指纹

- 现象：相同配置和代码、不同 LightGBM/NumPy 版本可能错误复用同一 experiment。
- 根因：配置中的期望版本不等于实际运行环境。
- 规则：readiness 发布 provider runtime subset 和完整 dependency fingerprint。Python、NumPy、pandas、
  PyArrow、Qlib、Fire、tqdm、Loguru 影响 provider 与 experiment；LightGBM 等仅研究依赖只影响 experiment。
  `NOT_INSTALLED` 必须显式；固定 `unavailable` 禁止。
- 回归：只改变 LightGBM 时 snapshot/provider 不变、experiment/work 变化；改变 NumPy/pandas/Qlib 时
  provider 与 experiment 都变化。

给实现 Agent 的指导：缓存身份应跟随“哪个字节由哪个运行时生成”，不能把所有依赖粗暴放进 provider，
也不能漏掉会改变 dump 结果的 NumPy/pandas/Qlib。

### P0-8A validation 证据与科学 identity 混层

- 现象：抽样算法或容差改变时，旧 provider validation/reconciliation 可能被误复用；若把它们放进
  provider/experiment，又会无必要重建大产物。
- 根因：计算产物身份和验收证据身份未分开。
- 规则：`validation.provider` 与 `validation.labels` 使用两个独立 hash；前者进入 provider-validation，且其
  receipt 再进入 label-reconciliation，后者直接进入 label-reconciliation，最终都传播到 acceptance。
  provider-validation PASS 是 experiment/features 编排前置，但不是其内容 receipt input。
- 回归：只改抽样算法时 provider-validation/reconciliation 改，experiment/work 不改；只改标签容差时仅
  reconciliation/acceptance 改；两者都不改变 snapshot/provider/experiment/features identity。

### P0-9 MLflow target 与创建崩溃窗

- 现象：切换 tracking URI 会误复用旧 marker；先创建 run 再 set tracking tag 时，tag 前崩溃留下不可查询
的孤儿 run；两个进程可同时观察到零匹配。
- 根因：科学 identity、登记目标和登记幂等键没有分层；关键 tag 不是首个服务端写入的一部分。
- 规则：以脱敏 `tracking_target_key` 分目录保存 request/marker，不改变科学 identity；首个 create/start API
原子携带 `quant_tracking_key`；个人单机版用 WSL `flock` 互斥。只恢复唯一、完全匹配的 FINISHED run。
- 回归：切换 URI 不复用 marker；create 后立即崩溃可恢复；双进程只有一个 remote run；RUNNING/FAILED/
KILLED 或多匹配不得创建同 key 第二条。

给实现 Agent 的指导：幂等恢复必须逐个枚举崩溃点，尤其检查“远端已变更、本地 marker 未落盘”的窗口；
不要把普通重试等同于 exactly-once。

### P0-10 冷启动只是目录隔离

- 现象：同一 Python 进程中的两次 handler 调用可共享模块缓存、线程池或模型对象。
- 根因：把“不同输出目录”误当“独立运行环境”。
- 规则：父进程顺序启动两个全新 WSL Miniforge base Python 子进程；attempt 使用独立 cache/temp，父控制器
运行时观察进程确实不同但 PID 不持久化，只允许读取已验真的共享输入。comparison key 覆盖输入 receipt、
模型参数、code/dependency 和 tolerance。
- 回归：注入进程级全局缓存仍必须训练两次；attempt 2 不能读 attempt 1/正常 work model；一侧 NaN、键或
行序差异均失败。

## 4. P1 契约补齐

- CLI 已冻结七个命令的必需 identity、依赖闭包、停止 stage和多失败退出码优先级。
- 配置 hash 使用实际键名 `walk_forward`，不再使用文案式 `walk-forward`；allowlist 是已解析的明确子树，
  未知键、缺失键和类型错误在执行前以 code 2 失败。
- provider 使用独立 `PROVIDER` scope，不再借用 `SNAPSHOT`。
- backtest 三个场景目录和文件名已固定，receipt 必须逐文件列出。
- tracking artifact 上传保留相对目录，避免多场景同名 `metrics.json` 覆盖。
- 文档旧 `runs/<run_id>` 已统一为 `runs/<experiment_key>`。
- `RunSummary` 增加 snapshot/provider/experiment identity 和 node outcome，支持非 work 命令审计。
- stdout 只允许一份规范 JSON；第三方 warning、日志和脱敏 traceback 进入 stderr/本地日志。

### P0-11 plan 内未知 digest 与多文件 stage 原子性

- 现象：旧 `StageNode.inputs` 要求 plan 构造时提供全部 digest，但 alignment→train 等同一 plan 内的上游
  尚未执行；旧 work 根又让 train/predictions/evaluation 文件散落，目录级原子发布无法成立。
- 根因：没有区分 continuation 边界外已验真输入与 plan 内 producer 输出，也没有让 stage 拥有唯一目录。
- 规则：输入拆成 `ExternalInput(ArtifactDigest)` 与 `StageOutputInput(producer_node_id,path)`；runner 只从
  producer 的已验真 receipt 解析后者。每个多文件 stage 独占最终目录，以 WSL 目录级 no-clobber primitive
  原子发布；不支持时 fail-closed，不逐文件 merge 或回退覆盖。
- 回归：builder 不得要求调用者预填 train 输出 hash；篡改 producer receipt、引用未声明 output、并发 writer、
  orphan 同/异内容和缺少 `renameat2(RENAME_NOREPLACE)` 能力均须得到稳定结果。

给实现 Agent 的指导：类型中出现“未来才知道的值”通常意味着边界建模错误。用 producer 引用表达依赖，
把 hash 解析留在 receipt 已发布之后；多文件事务要缩成一个目录发布单元，不能靠执行顺序假装原子。
