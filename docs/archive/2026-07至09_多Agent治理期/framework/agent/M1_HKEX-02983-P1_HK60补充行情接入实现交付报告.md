## 实现结果

- `finalize_hk_history` 新增显式 `hkex_retained_raw: bytes | None` 输入，仅当
  `unresolved` 精确等于 `02983.HK@2026-07-10` 时允许消费。
- retained bytes 在任何 journal/clean 写入前重新经过
  `verify_hkex_daily_quotation`；缺 raw、额外缺口、无缺口却传 raw、非原始 bytes
  均以稳定错误码失败。
- verified quotation 映射为唯一一条 `Bar1dSchema` 行：成交量单位为股、成交额取
  完整 sales turnover、`adj_factor=1.0`、`source="hkex"`。
- 补充路径按 `effective_expected_dates ∪ supplement unresolved keys` 校验完整 key
  闭包与无重复；权威 no-trade evidence 已排除的 key 不会被重新要求为 bar。
- 补充路径的 `finalize.json` 升级为 `hk-history-finalize-v2`，绑定 evidence ID、
  retained raw SHA-256、source record ID 与补充行内容摘要；无补充路径仍写原 v1
  receipt。相同输入重跑字节幂等，证据或 clean 漂移拒绝。
- CLI 新增 `--hkex-retained-raw`，仅 `--finalize` 模式读取；普通执行与离线恢复在
  读取前拒绝，文件错误不泄露物理路径。
- 修复 v2 request receipt 的内存对象比较：canonical JSON 读取后数组为 list，而
  `_receipt_dict` 内部保留 tuple，原实现会把字节完全一致的 v2 receipt 误判为漂移；
  现在比较 canonical wire value 与原始字节，v1 wire 格式不变。

## 冻结合同勘误

- 现象：若 literal 使用原始 `expected_dates`，v2 中已有权威 no-trade evidence 的
  `01065.HK@2026-05-05` 仍会被要求生成 bar，正式 finalize 必然失败。
- 根因：`build_hk_history_plan_v2` 将 evidence key 保留在原始 expected 集合，并只从
  `effective_expected_dates` 中扣除；原任务单第 4 条混淆了原始审计集合与可发布集合。
- 规则：最终可发布 key 固定为 `effective_expected_dates ∪ supplement unresolved keys`；
  supplement 还只允许 v2 plan，v1 即便具有精确 02983 unresolved 也 fail closed。
- 反例：测试同时覆盖 v2 中存在 no-trade evidence 时只发布 seed/request/02983 三类
  key，以及 v1 精确 02983 unresolved 携带 retained raw 时返回 plan conflict 且零写入。
