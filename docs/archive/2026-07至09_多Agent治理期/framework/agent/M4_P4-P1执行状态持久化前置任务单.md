# M4-P4-P1 执行状态持久化前置任务单

日期：2026-08-02  
状态：实现、外部独立初验与主 Agent 最终验收均已通过；本包只关闭执行状态持久化前置，不关闭 P4/M4 Gate

## 1. 目标与依据

P4 需要把 callback event、最新 OMS aggregate 与 outbox `SENT` 在同一事务中提交，并在重复 plan 时复用首次
stage 决策、跨重启保存 `DailyRiskCounters`。现有 v2 store 的 aggregate 只有 immutable insert，且没有 stage
receipt 或 counter CAS，因此不能形成真实恢复闭环。

本包只补齐三个 typed storage primitive：

- immutable `execution_stages`；
- `daily_risk_counters` 的 insert/read/identity-fenced CAS；
- `order_aggregates` 的 identity-fenced CAS replace。

不解释任何 opaque payload，不定义 service wire format，不改变 outbox delivery、lease、attempt、`SENT/UNKNOWN`
语义。

## 2. 冻结 schema 与 API

schema v3 新增：

```text
execution_stages(plan_id PRIMARY KEY, identity, payload)
daily_risk_counters(counter_key PRIMARY KEY, identity, payload)
```

公开 typed repository 增量：

```python
put_execution_stage(*, plan_id, identity, payload) -> bool
get_execution_stage(plan_id) -> StoredRecord | None

put_daily_risk_counters(*, counter_key, identity, payload) -> bool
get_daily_risk_counters(counter_key) -> StoredRecord | None
compare_and_set_daily_risk_counters(
    *, counter_key, expected_identity, identity, payload
) -> bool

replace_order_aggregate(
    *, command_id, expected_identity, identity, payload
) -> bool
```

`put_*` 延续 P0 规则：同 key、identity、payload 返回 `False`，同 key 异内容抛 `IdempotencyConflict`。
CAS 规则：

- 目标 identity/payload 已是当前内容时返回 `False`，不产生写入；
- 目标 identity 与当前相同但 payload 不同，按 identity/payload 漂移 fail closed；
- 其余更新要求当前 identity 精确等于 `expected_identity`，否则 `*_CAS_MISMATCH`；
- 缺行 `*_NOT_FOUND`；成功后回读必须与目标字节完全一致；
- UPDATE 与回读位于方法级 SAVEPOINT，调用方在外层事务内捕获异常也不能提交半更新。

identity 仍是严格 64 位小写 hex；payload 仍是精确 bytes。canonical JSON 的构造与领域 identity 重算属于未来
P4 service，store 只保证 Windows/WSL 字节原样往返。

## 3. 不变量与反例

- v1/v2 数据和 delivery 状态迁移后保持不变；旧 outbox 不变为 sendable。
- stage 永不更新；同 plan id 异 payload 必须冲突。
- aggregate/counter CAS 失败后原 identity/payload 保持不变。
- 外层事务中 aggregate、counter、stage 任一步异常时整体回滚。
- SQLite/OS 错误映射为稳定脱敏 code，不能泄露路径、payload、底层异常或 cause/context。
- migration `migrating` 与未来更高 schema 继续 fail closed。

关键反例：aggregate UPDATE 成功后，post-update SELECT 抛带绝对路径的 SQLite 错误；调用方在同一外层事务
捕获异常并继续查询时，必须仍看到旧 aggregate，异常链为空且路径不出现。

## 6. R1 初验返工冻结

- **现象**：`_put_row` 的首次 SELECT 在异常映射外，INSERT 只映射 `IntegrityError`；stage SELECT 或 counter
  INSERT 的 `sqlite3.OperationalError` 会把底层 sentinel 原样抛给调用方。
- **根因**：新增 API 复用了 P0 helper，但原 helper 只冻结了幂等冲突与约束错误，没有闭合普通 SQLite 查询/
  写入失败的稳定错误边界。
- **应遵循规则**：所有 SQLite 异常在离开底层 `except` 后映射为稳定、脱敏 `StoreError`，cause/context 为空；
  真实 FK/约束冲突仍保持 `REFERENTIAL_INTEGRITY`。
- **最小复现**：连接 wrapper 分别在 `SELECT ... execution_stages` 和
  `INSERT INTO daily_risk_counters` 抛含绝对路径 sentinel 的 `OperationalError`。
- **新增测试**：stage SELECT、counter INSERT 均断言稳定 code、无 sentinel、空异常链、无残留 row；另保留
  event 缺 command 外键回归，必须仍为 `REFERENTIAL_INTEGRITY`。
- **通过条件**：R1 反例与完整 store suite 在 Windows/WSL base 均通过，Ruff/mypy/diff check 通过，再进入复验。
