## 1. 为什么必须先做这个微包

主 Agent 在 P2 实现前发现两个会让真实链路发生时点错误的配置矛盾：

1. 示例 `data.start_date=2016-01-01`，但 Tushare calendar 真实只读探针确认该日 SH 闭市；已验收的
   `resolve_history_window` 和 P2 都明确要求 signal start/end 是 SH session，不自动对齐；
2. 配置方法版本名为 `tushare_monthly_observed_next_open_v1`，而现行业务语义是“observation 后下一 SH
   session 收盘形成可用 `as_of`，再下一 session open 才能成交”。旧名字会诱导实现把成员状态提前一个时点。

本包只纠正配置 SSOT 和 strict literal，不实现 PIT membership。修正必须先完成外部实现、独立复验与主 Agent
终验，P2 才能开始；不能让 P2 通过内部特判迁就错误配置。

## 3. 冻结修改

### 3.1 示例 signal window

`configs/research/m3_qlib_example.toml`：

```toml
start_date = 2016-01-04
end_date = 2026-06-26
```

在相邻注释明确：两端是首版 signal session 边界，必须由 G1 verified SH calendar 证明为开市日；loader 只做
静态类型/跨字段校验，不硬编码交易日表，也不自动把任意闭市日滚到附近 session。费用首段
`effective_from=2016-01-01` 是自然日生效区间，保持不变，不能随 signal start 一起改。

### 3.2 PIT 方法版本

示例 TOML 与 `src/quant/research/m3/config.py` 的唯一允许 literal 同时改为：

```text
tushare_monthly_observed_next_session_close_v1
```

旧 `tushare_monthly_observed_next_open_v1` 必须被 strict loader 作为 `VALUE_ERROR` 拒绝。不得兼容两个 alias、
静默迁移或仅改文档不改 `_FIELD_SPECS`。

### 3.3 hash 传播

字段归属不变，不新增/删除 assignment 或 dotted-key shape：仍为 151 个 assignment、138 种 shape。

- 对新配置单独做一个**合法** `data.start_date` mutation：`full/snapshot/scientific` 改变；
  `g1/provider/provider-validation/label-reconciliation/acceptance/tracking target` 不变；
- `g1_backfill.membership_method_version` 是冻结 literal，不能在同一版 strict loader 中把旧值和新值都当作合法
  mutation。其 `_FIELD_SPECS` selector 归属必须精确为 `{"g1"}`；因此版本切换跨改动基线只允许
  `full/g1` 改变，其余 narrow hash 与 tracking target 不变；
- 新示例同时包含两项变化，因此不能在报告中拿旧 hash 当固定预期；测试只验证传播关系和重算一致性。

实现 Agent 在修改前先只读加载一次当前示例，记录九个 identity；修改后再加载并在交付报告中以
“changed/unchanged”矩阵比较，不必抄写 64-hex 全值。预期：`full/g1/snapshot/scientific` changed，其余五个
identity unchanged。这个一次性前后比较用于证明本次迁移；可重复单测则证明新 literal、selector 归属以及合法
start-date mutation。禁止为了让旧/新 literal 同时可加载而暴露 trusted hash helper、增加 alias 或绕过验证。

这里不把 membership method 塞进 snapshot selector：snapshot 已通过 verified G1 release 继承其结果身份；重复
加入会制造第二套配置归属。

## 5. 必测矩阵

1. 真实示例 strict load 成功，`document.data.start_date` 精确为 `date(2016,1,4)`，end 不变；
2. 示例 method 精确为新 literal，旧 literal、近似拼写、bool/null 均失败；
3. `_FIELD_SPECS` 与真实示例仍为 138 shape 闭包，assignment 数仍为 151；
4. 对合法 start-date mutation 验证 §3.3 的正向和负向 hash 传播；另断言
   `_FIELD_SPECS["g1_backfill.membership_method_version"].selectors == {"g1"}`，不得把旧 literal 当合法 mutation；
5. 注释/键顺序变化不改 hash；将日期改成另一合法 `date` 可以加载并按 selector 传播，证明 loader 没硬编码
   2016-01-04；
6. `costs.a_share_periods[0].effective_from` 仍为 2016-01-01，费用 schedule 连续性测试仍通过；
7. 异常 message/repr 不含配置全文、路径或 secret；本包不读取 token；
8. 全量 pytest、Ruff、mypy 通过，核心 import 不加载 Qlib/LightGBM/MLflow。

独立初验至少补：旧 literal 即使与其他合法字段 mutation 同时出现仍被 loader 拒绝；start-date mutation 不应
改变 g1 hash；方法字段 selector 不得包含 snapshot/scientific；费用生效日未被“顺手对齐”。复验还须核对
实现报告的改动前后 identity 矩阵与本节预期一致，不能只看单测绿色。
