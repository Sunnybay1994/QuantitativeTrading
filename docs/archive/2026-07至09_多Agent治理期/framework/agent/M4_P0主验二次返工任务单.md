## 1. 现象—根因—规则

- 现象：PARENT/OPEN/TX_COMMIT 等映射后的 `StoreError` 虽然 `__cause__ is None` 且格式化 traceback 不展示原
  路径，但 `exc.__context__` 仍挂载含绝对路径的 `OSError/sqlite3.Error`。
- 根因：在活跃 `except` 内 `raise StoreError(...) from None` 只设置 `__suppress_context__`，不擦除自动附着的
  `__context__`。
- 规则：稳定错误必须在离开捕获原异常的 `except` 作用域后再抛出；主错误优先，cleanup 失败不得覆盖。异常
  对象、cause、context、message/repr 和 formatted traceback 均不得携带原路径或原异常文本。

## 3. F1 — 所有映射边界彻底断链

定向审计并修复：parent mkdir、sqlite connect、PRAGMA、migration BEGIN/apply/COMMIT、referential integrity、
transaction BEGIN/COMMIT、close，以及任何同类 OS/sqlite → StoreError 映射。

- 在 `except` 内只记录固定错误 code/构造待抛对象；离开 `except` 后再 `raise ... from None`，确保
  `__cause__ is None` 且 `__context__ is None`。
- 不通过直接赋值异常私有字段伪装清理；使用清晰控制流。
- `_safe_rollback/_safe_close` 失败不得覆盖更早主错误；业务代码在 transaction body 主动抛出的异常保持原样，
  不被改写为 StoreError。
- 不捕获 `BaseException`，不回显 uri/path/sqlite 原错误/SQL 参数。

## 4. 必须新增的测试

1. PARENT_CREATE_FAILED、OPEN_FAILED、PRAGMA_FAILED、MIGRATION_FAILED、TX_BEGIN_FAILED、TX_COMMIT_FAILED、
   CLOSE_FAILED、REFERENTIAL_INTEGRITY：逐项注入带唯一绝对路径 token 的底层异常；
2. 每项同时断言稳定 code、`__cause__ is None`、`__context__ is None`，并检查 `str/repr/traceback` 无 token；
3. COMMIT 失败且 ROLLBACK 再失败：仍以 TX_COMMIT_FAILED 为主且完全断链；
4. transaction body 业务异常且 rollback 失败：仍抛原业务异常；
5. 保留第一轮 **103 passed** 的 URI、identity、FK、损坏 row 与既有幂等语义。
