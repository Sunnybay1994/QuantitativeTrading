# AI 软件工程哲学

## 从写代码到控制代码行动

高能力 Coding Agent 使工程师能够用自然语言发起跨文件、跨模块和跨工具的“大粒度代码行动”。人的工作
重心因此从逐行生成代码，逐渐移向选择问题、定义目标、冻结边界、判断取舍和验收结果。代码生成变得便宜，
判断、理解、验证、维护和删除代码变得更稀缺。

模型能力可能暂时领先于工具集成、项目知识、权限、组织流程和质量治理；工程系统必须补齐这些控制面。自然
语言只是更高层的控制接口，不意味着人退出过程，也不会自动消除错误假设、模糊需求、架构约束和现实风险。

## 新的错误模型

Agent 的主要风险不再只是语法错误，而是在未经验证的前提下，高速完成一套概念上错误但表面完整的实现。
它可能隐藏困惑、不主动澄清、不呈现权衡、该反对时不反对，或用过度抽象掩盖简单问题。因此：

- 不确定性、矛盾、假设和实质性权衡必须显式暴露；
- 对明显复杂、低效或与现有系统冲突的方案，应主动提出更简单的替代方案；
- 测试绿色、Agent 自报完成和代码量增长都不能单独证明任务正确。

## 杠杆来自反馈闭环和耐力

Agent 的独特价值不仅是生成速度，还包括持续搜索、试验、运行工具、分析失败并重新尝试的耐力。耐力只有
放入受控反馈闭环才形成杠杆：

```text
理解现状 -> 提出假设 -> 小步修改 -> 运行验证 -> 分析证据 -> 修正或停止
```

自主性的前提是可验证性。测试、编译器、类型系统、日志、浏览器、数据库、基准、真实依赖探针、权限和回滚
共同构成 Agent 的控制系统；静态提示词只是其中一层。

## 人机分工

- 人类负责问题价值、系统方向、风险偏好、不可逆决定和最终接受。
- 主 Agent 负责理解系统、冻结目标与高风险设计、组织执行和核验证据。
- 执行 Agent 负责搜索、实现、测试、调试和重复迭代。
- 独立审查者负责挑战假设、检查 diff、运行新反例并发现概念偏差。

IDE、代码导航、diff、调试器和人工精修仍是重要的观察与接管界面。Agent 可以成为主要执行者，但不能成为
唯一证据来源。未来编程可能更像实时战略、自动化工厂或演奏：人设置目标、分配执行单元、观察反馈并在关键
节点介入。具体多 Agent 角色与边界见 [`workflows/multi_agent_delivery.md`](workflows/multi_agent_delivery.md)。

## 生产力是加速，也是扩张

Agent 的价值不只体现在把原有任务做得更快，还体现在扩大可执行任务空间：过去不值得自动化的小工具、陌生
技术栈、昂贵的测试与迁移、以及多个候选方案，现在可能变得可行。评估收益时同时考察“节省了什么”和
“新增了哪些原本不会做的高价值工作”，并扣除生成内容带来的维护、验证与治理成本。

Agent 也可能减少样板劳动和卡住感，让构建更有趣、更有勇气；但团队应允许不同的人机分工偏好。LLM 扩大
通才的执行范围，同时提高专家判断的杠杆，并不会消除深层领域知识。善于定义问题、构造验证闭环和控制
复杂度的人会获得更大杠杆，因此顶尖与平均工程师的产出差距可能扩大。随着更多数字知识工作变得可执行，
影响也可能超出软件开发本身。

## 生成泛滥后的治理

生成成本下降会带来更多低价值代码、重复实现、依赖、安全风险和无人真正理解的模块。可靠团队需要代码
所有权、质量门禁、架构约束、来源追踪、依赖治理、可观测性和删除机制。代码量、PR 数、Agent 数和演示
速度都可能沦为生产力表演，不能替代真实结果。目标不是让 Agent 写得更多，而是让系统中的每一份新增
复杂度都有当前价值、明确责任和可验证依据。

## 人的能力不能退出闭环

阅读代码和从零生成代码是不同能力。长期使用 Agent 可能使语法、API、调试和独立实现能力退化，最终也会
削弱判断。人的能力维护见 [`human_capability.md`](human_capability.md)。

本操作系统的核心原则是：人定义正确的问题、边界和裁判；Agent 在可观测、可回滚的环境中持续执行；结果
经过独立证据与人的判断后才被接受。
