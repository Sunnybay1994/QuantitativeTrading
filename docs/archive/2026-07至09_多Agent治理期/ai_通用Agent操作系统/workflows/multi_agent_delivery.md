# 多 Agent 交付工作流

多 Agent 会同时放大吞吐量、错误假设、重复劳动、文件冲突和整合成本。默认先建立可靠的单 Agent 闭环；
只有任务能够真正解耦时才增加并行度。

## 适用条件

适合多 Agent：

- 子任务输入、输出、文件范围和验收标准清晰；
- 接口已经稳定，子任务不依赖彼此未完成的中间结果；
- 文件写入范围互斥，或者角色是只读审查；
- 独立方案探索、测试、文档、性能分析或不同平台适配。

不适合多 Agent：

- 需求、架构或公共接口尚未冻结；
- 多个 Agent 需要同时修改同一核心文件；
- 缺少统一验收标准；
- 子任务高度耦合，整合成本可能超过并行收益。

## 角色

- **主 Agent（例如 Codex）**：理解项目、冻结目标与高风险设计、拆分任务、管理冲突、核验证据并最终验收。
- **执行 Agent（例如 Cursor 或其他 Coding Agent）**：只在允许范围内实现、自测并提交交付报告。
- **独立审查 Agent**：使用与执行者分离的新上下文，只读核对合同、diff 和测试，并增加执行者未使用的反例。
- **人类负责人**：决定产品价值、风险偏好、不可逆事项和最终是否接受；必要时随时接管。

角色可以由不同工具承担，名称不是关键；独立性、范围和证据才是关键。执行者的自测不能替代独立审查，
主 Agent 的汇总也不能替代人的高风险决定。

## 交付闭环

1. 主 Agent 使用任务模板冻结目标、SSOT、文件白名单、失败语义、反例和验收命令。
2. 执行 Agent 实现并自测；发现任务书与事实冲突时停止扩张，提交证据。
3. 独立审查 Agent 映射“标准—证据—结论”，并运行新的对抗性反例。
4. 审查不通过时，主 Agent 形成最小返工任务，回到执行 Agent，再由独立 Agent 复验。
5. 主 Agent 整合后运行最终 Gate、检查跨模块不变量和文档一致性。
6. 高风险结果由人类明确接受；未验证的真实依赖或外部状态必须保持“阻塞/待验”，不能包装成通过。

返工问题应包含：现象、根因、违反的规则、最小复现、必须新增的测试和通过条件。不要由审查者顺手修改
生产代码，否则独立证据链会失效。

## 并行写入纪律

- 每个写入 Agent 都有互斥文件白名单；共享核心文件一律串行。
- 共享接口先冻结再并行，变化后通知所有受影响角色并重新验证。
- 报告保留命令、结果和产物位置，不回传无关的完整日志。
- 合流后必须重新运行整合验证，不能把各子任务“分别通过”等同于整体通过。
